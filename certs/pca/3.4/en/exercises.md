# Topic 3.4 — Push vs Pull: Guided Exercises

> **Exam domain:** Prometheus Fundamentals · **Reference:** [PCA Curriculum](https://github.com/cncf/curriculum/raw/master/PCA_Curriculum.pdf)
>
> These labs prove, with real processes and real HTTP traffic, *why* Prometheus is a **pull-based** system, what that buys you (target liveness, ad-hoc debugging, centralized config), where it breaks (short-lived jobs, unreachable targets), and how the **Pushgateway** bridges the gap without turning Prometheus into a push system. You will also see the two places Prometheus itself pushes: `remote_write` and, indirectly, the Pushgateway.

---

## Prerequisites & environment setup (Exercise 0)

You need `docker`, `docker compose`, `curl`, and `jq`. Everything below runs locally; nothing leaves your machine.

**Step 0.1 — Create the working directory and the Prometheus config.**

```bash
mkdir -p pca-3.4-push-pull && cd pca-3.4-push-pull
```

Create `prometheus.yml`:

```yaml
global:
  scrape_interval: 15s      # how often Prometheus pulls each target
  scrape_timeout: 10s       # must be <= scrape_interval

scrape_configs:
  # Prometheus scraping itself — the canonical pull example
  - job_name: prometheus
    static_configs:
      - targets: ["localhost:9090"]

  # A long-lived, always-on target: the textbook pull case
  - job_name: node
    static_configs:
      - targets: ["node-exporter:9100"]

  # The Pushgateway. honor_labels is REQUIRED here — see Exercise 4.
  - job_name: pushgateway
    honor_labels: true
    static_configs:
      - targets: ["pushgateway:9091"]
```

**Step 0.2 — Create `docker-compose.yml`.**

```yaml
services:
  prometheus:
    image: prom/prometheus:v2.53.1
    ports: ["9090:9090"]
    volumes:
      - ./prometheus.yml:/etc/prometheus/prometheus.yml:ro
    command:
      - --config.file=/etc/prometheus/prometheus.yml

  node-exporter:
    image: prom/node-exporter:v1.8.2
    ports: ["9100:9100"]

  pushgateway:
    image: prom/pushgateway:v1.10.0
    ports: ["9091:9091"]
```

**Step 0.3 — Bring the stack up and confirm all three are running.**

```bash
docker compose up -d
docker compose ps
```

Expected (abridged):

```
NAME             IMAGE                          STATUS         PORTS
node-exporter    prom/node-exporter:v1.8.2      Up 5 seconds   0.0.0.0:9100->9100/tcp
prometheus       prom/prometheus:v2.53.1        Up 5 seconds   0.0.0.0:9090->9090/tcp
pushgateway      prom/pushgateway:v1.10.0       Up 5 seconds   0.0.0.0:9091->9091/tcp
```

**Questions**

- **Q0.1** In this topology, which process opens the TCP connection when a metric is collected from `node-exporter` — Prometheus or the exporter?
- **Q0.2** `node-exporter` has no configuration telling it where Prometheus lives. How is that possible, and what does it imply about *who owns the collection schedule*?

## Exercise 1 — Watch the pull model happen

**Goal:** see that "scraping" is nothing more exotic than Prometheus issuing an HTTP `GET /metrics` on a schedule you control.

**Step 1.1 — Be Prometheus for a moment. Pull the exporter yourself:**

```bash
curl -s http://localhost:9100/metrics | grep -E '^node_cpu_seconds_total' | head -3
```

Expected (values vary):

```
node_cpu_seconds_total{cpu="0",mode="idle"} 48213.44
node_cpu_seconds_total{cpu="0",mode="system"} 611.28
node_cpu_seconds_total{cpu="0",mode="user"} 1875.02
```

**Step 1.2 — Confirm the exporter is a plain HTTP server with no memory of you:**

```bash
curl -s -o /dev/null -w "status=%{http_code} method=GET\n" http://localhost:9100/metrics
```

Expected:

```
status=200 method=GET
```

**Step 1.3 — Now let Prometheus do the same thing on its interval. Query the scrape health signal it synthesizes for every target:**

```bash
curl -s 'http://localhost:9090/api/v1/query?query=up' | jq -r '.data.result[] | "\(.metric.job)\t\(.metric.instance)\tup=\(.value[1])"'
```

Expected:

```
node          node-exporter:9100    up=1
prometheus    localhost:9090        up=1
pushgateway   pushgateway:9091      up=1
```

**Step 1.4 — Observe the metadata Prometheus attaches to *every* scrape (these are generated by the puller, not the target):**

```bash
curl -s 'http://localhost:9090/api/v1/query?query=scrape_duration_seconds{job="node"}' | jq -r '.data.result[0].value[1]'
```

Expected (seconds):

```
0.011473
```

**Step 1.5 — Change who controls the cadence. Edit `prometheus.yml`, override the interval for the `node` job only:**

```yaml
  - job_name: node
    scrape_interval: 5s        # <-- per-job override, faster than the 15s global
    static_configs:
      - targets: ["node-exporter:9100"]
```

Reload without a restart (Prometheus supports SIGHUP-style config reload over HTTP if started with `--web.enable-lifecycle`; here we just restart the container):

```bash
docker compose restart prometheus
```

**Questions**

- **Q1.1** Steps 1.1 and 1.3 hit the *same* endpoint. What does that tell you about how debuggable a pull target is compared with a push pipeline?
- **Q1.2** `up`, `scrape_duration_seconds`, and `scrape_samples_scraped` do not appear in the exporter's `/metrics` output. Where do they come from and why can only a *puller* produce them?
- **Q1.3** In Step 1.5 you changed the scrape frequency for `node` without touching `node-exporter`. In a push system, where would that knob live, and why is that operationally worse at scale?

## Exercise 2 — Pull gives you liveness for free

**Goal:** prove that the pull model detects a dead target *inherently*, and that this is a property push architectures must reimplement.

**Step 2.1 — Kill the target while Prometheus keeps trying to reach it:**

```bash
docker compose stop node-exporter
```

**Step 2.2 — Wait one scrape interval, then re-query `up`:**

```bash
sleep 20
curl -s 'http://localhost:9090/api/v1/query?query=up{job="node"}' | jq -r '.data.result[0] | "up=\(.value[1])"'
```

Expected:

```
up=0
```

**Step 2.3 — Inspect *why* the scrape failed (Prometheus records the failure cause):**

```bash
curl -s 'http://localhost:9090/api/v1/targets?state=active' \
  | jq -r '.data.activeTargets[] | select(.labels.job=="node") | "health=\(.health) lastError=\(.lastError)"'
```

Expected (message text varies by platform):

```
health=down lastError=Get "http://node-exporter:9100/metrics": dial tcp: connect: connection refused
```

**Step 2.4 — This is exactly what a production alert keys off of. The classic rule:**

```yaml
groups:
  - name: liveness
    rules:
      - alert: TargetDown
        expr: up == 0
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: "{{ $labels.job }} target {{ $labels.instance }} is down"
```

**Step 2.5 — Bring it back and confirm recovery:**

```bash
docker compose start node-exporter
sleep 20
curl -s 'http://localhost:9090/api/v1/query?query=up{job="node"}' | jq -r '.data.result[0].value[1]'
```

Expected:

```
1
```

**Questions**

- **Q2.1** Prometheus never received a "goodbye" from the exporter. How did it conclude the target was down within one interval?
- **Q2.2** In a pure push system, an application that dies simply *stops sending*. Why is "absence of data" a strictly weaker and more ambiguous failure signal than `up == 0`?
- **Q2.3** Name two *non-failure* reasons an application might stop pushing that would produce the same "no data" symptom, and explain why the pull model is immune to the ambiguity.

## Exercise 3 — Where pull breaks: the short-lived batch job

**Goal:** experience the one problem pull cannot solve on its own, motivating the Pushgateway.

**Step 3.1 — Simulate a nightly backup job: it starts, does work, records a result, and exits in under a second.** It exposes metrics only while alive:

```bash
docker run --rm --network pca-34-push-pull_default python:3.12-slim sh -c '
  echo "backup ran, exit code 0";  # the whole process lives ~0.3s and is gone
'
```

Expected:

```
backup ran, exit code 0
```

**Step 3.2 — Try to make Prometheus scrape a job like this.** With `scrape_interval: 15s`, the probability the job is even *alive* during a scrape is tiny, and its network endpoint disappears when it exits. There is no stable `instance` to pull.

Reason about it rather than configure it: a target that exists for 300 ms cannot be reliably hit by a 15 s poller, and by the time an alert would fire on `up == 0`, the job was *supposed* to be gone.

**Step 3.3 — Enumerate the two structural mismatches** (write them down before checking answers):

1. **Lifetime:** the job's lifetime is shorter than the scrape interval.
2. **Addressability:** the job has no long-lived, discoverable network address to pull from.

**Questions**

- **Q3.1** For a *service* (web server, database) that lives for weeks, why is pull the natural fit? Which of the two mismatches above simply does not occur?
- **Q3.2** Would shortening `scrape_interval` to 1 s fix the batch-job problem? Explain what it would and would not solve.
- **Q3.3** What single piece of data about a backup job do you most want to survive the job's death — a value you cannot capture with pull because the source is already gone?

## Exercise 4 — The Pushgateway: push in, pull out

**Goal:** use the Pushgateway correctly, understand that it is a *metrics cache* Prometheus still **pulls**, and internalize its three sharp edges: `honor_labels`, staleness, and lost liveness.

**Step 4.1 — Push a batch-job result the way a real job would, from a shell hook:**

```bash
cat <<'EOF' | curl --data-binary @- http://localhost:9091/metrics/job/backup/instance/db01
# TYPE backup_last_success_timestamp_seconds gauge
backup_last_success_timestamp_seconds 1754640000
# TYPE backup_duration_seconds gauge
backup_duration_seconds 42.7
# TYPE backup_records_processed gauge
backup_records_processed 1875002
EOF
```

The URL path `/metrics/job/backup/instance/db01` is the **grouping key**: it becomes the `job` and `instance` labels on every pushed series. A trailing newline is required — `cat`/`echo` provide it. Returns HTTP 200 with an empty body.

**Step 4.2 — Read the Pushgateway's own `/metrics` (this is what Prometheus will pull):**

```bash
curl -s http://localhost:9091/metrics | grep -E 'backup_|push_time_seconds' 
```

Expected:

```
backup_duration_seconds{instance="db01",job="backup"} 42.7
backup_last_success_timestamp_seconds{instance="db01",job="backup"} 1.754640000e+09
backup_records_processed{instance="db01",job="backup"} 1875002
push_time_seconds{instance="db01",job="backup"} 1.7546401e+09
push_failure_time_seconds{instance="db01",job="backup"} 0
```

Note `push_time_seconds` — the Pushgateway synthesizes it per group. It is your only handle on *freshness* (see Step 4.6).

**Step 4.3 — Confirm Prometheus pulled the pushed data with the original job label intact:**

```bash
sleep 20
curl -s 'http://localhost:9090/api/v1/query?query=backup_records_processed' \
  | jq -r '.data.result[0] | "job=\(.metric.job) instance=\(.metric.instance) value=\(.value[1])"'
```

Expected:

```
job=backup instance=db01 value=1875002
```

**Step 4.4 — Prove why `honor_labels: true` matters.** Temporarily remove `honor_labels` from the `pushgateway` scrape config, restart Prometheus, and re-query:

```bash
# after editing prometheus.yml to drop honor_labels, then:
docker compose restart prometheus && sleep 20
curl -s 'http://localhost:9090/api/v1/query?query=backup_records_processed' \
  | jq -r '.data.result[0].metric | "job=\(.job) exported_job=\(.exported_job) instance=\(.instance)"'
```

Expected **without** `honor_labels`:

```
job=pushgateway exported_job=backup instance=pushgateway:9091
```

Restore `honor_labels: true` and restart before continuing.

**Step 4.5 — Discover the liveness caveat.** Query `up` and note *which* thing it describes:

```bash
curl -s 'http://localhost:9090/api/v1/query?query=up{job="backup"}' | jq '.data.result'
curl -s 'http://localhost:9090/api/v1/query?query=up{job="pushgateway"}' | jq -r '.data.result[0].value[1]'
```

Expected:

```
[]        # there is NO up series for the backup job
1         # up only exists for the Pushgateway itself
```

**Step 4.6 — Discover the staleness caveat.** The job pushed once and exited. Wait, then re-read Prometheus — the value is *still there, unchanged, and looks fresh* because Prometheus re-scrapes the same cached sample every interval:

```bash
sleep 30
curl -s 'http://localhost:9090/api/v1/query?query=backup_records_processed' | jq -r '.data.result[0].value[1]'
```

Expected (identical to before — no new backup ran, yet the series is "current"):

```
1875002
```

The correct alert is therefore on **age**, not on `up`:

```yaml
- alert: BackupStale
  expr: time() - backup_last_success_timestamp_seconds > 86400
  # or, using the gateway's own signal:
  # expr: time() - push_time_seconds{job="backup"} > 86400
  for: 10m
  annotations:
    summary: "No successful backup for db01 in over 24h"
```

**Step 4.7 — Clean up the group (the gateway never forgets on its own):**

```bash
curl -X DELETE http://localhost:9091/metrics/job/backup/instance/db01
curl -s http://localhost:9091/metrics | grep -c 'backup_records_processed'
```

Expected:

```
0
```

**Questions**

- **Q4.1** After Step 4.1, does the data flow "job → Prometheus" or "job → Pushgateway → Prometheus"? Which hop is push and which is pull, and is Prometheus still a pull system?
- **Q4.2** In Step 4.4, without `honor_labels`, the pushed `job="backup"` became `exported_job="backup"` and the series was tagged `job="pushgateway"`. Explain the label-conflict rule that produces this, and why federation and Pushgateway scraping specifically need `honor_labels: true`.
- **Q4.3** In Step 4.5, `up{job="backup"}` returned nothing. Explain precisely what `up{job="pushgateway"}=1` *does* and *does not* guarantee about your backups.
- **Q4.4** In Step 4.6 the series looked fresh forever. Why does this happen mechanically, and why is `time() - push_time_seconds` the right staleness signal instead of `up == 0`?
- **Q4.5** The Pushgateway docs warn it is "not a way to turn Prometheus into a push-based system" and "not an aggregator." If ten backup runs push to the *same* grouping key, what happens to the earlier values, and what does that tell you about how to design the grouping key?

## Exercise 5 — The other direction: Prometheus itself pushes (`remote_write`)

**Goal:** avoid the common misconception that "Prometheus only pulls." It *collects* by pull but can *forward* by push, and knowing the distinction is exam-relevant.

**Step 5.1 — Reason about the data path.** `remote_write` makes a Prometheus server stream samples it has already scraped to a remote endpoint (Grafana Mimir, Thanos Receive, Cortex, VictoriaMetrics) over HTTP. Configuration shape:

```yaml
remote_write:
  - url: "https://mimir.example.com/api/v1/push"
    queue_config:
      capacity: 10000
      max_shards: 50
      max_samples_per_send: 2000
    metadata_config:
      send: true
```

You do not need a live receiver for this exercise — read the config and answer the questions.

**Step 5.2 — Place each mechanism on the push/pull axis.** Fill in the table (answers below):

| Mechanism | Prometheus collects by… | Prometheus forwards by… |
|---|---|---|
| Scraping node-exporter | ? | — |
| Pushgateway | pull (from the gateway) | — |
| `remote_write` | pull (locally) | ? |
| OpenTelemetry Collector `prometheus` receiver | ? | — |

**Questions**

- **Q5.1** Ingestion (getting metrics *into* Prometheus) and shipping (getting them *out* to long-term storage) sit on opposite sides of the push/pull axis. State which is which and why the pull model for ingestion is unaffected by using `remote_write`.
- **Q5.2** A teammate says "we'll skip scraping and just have every app `remote_write` straight into our central Prometheus, push-style." What core guarantees from Exercises 1–2 do you lose, and when is that trade-off nonetheless justified (hint: think NAT, serverless, edge)?
- **Q5.3** From the Prometheus FAQ's own framing, is pull *fundamentally* superior to push, or is it a fit for Prometheus's operational model? Give one concrete advantage from each of the labs above.

## Answers

<details>
<summary>Click to reveal all answers</summary>

**Q0.1** Prometheus opens the connection. In a pull model the *monitoring server* is the HTTP client; it issues `GET /metrics` to the target. The exporter is a passive HTTP server that only responds.

**Q0.2** The exporter is stateless with respect to monitoring: it just exposes `/metrics` and answers whoever asks. The collection schedule (interval, timeout, which targets, relabeling, service discovery) lives entirely on the Prometheus side. Implication: *the puller owns the schedule*, so you can add/remove Prometheus servers, run a second one for staging, change intervals, or curl the target by hand — all without touching or coordinating with the workload.

**Q1.1** Both hit `GET /metrics`, so a pull target is trivially debuggable: any human or script can reproduce *exactly* what Prometheus sees with a single `curl`, with no special agent, credentials, or replaying of a push stream. In a push pipeline you can only inspect what the app decided to emit, after it left, wherever it landed.

**Q1.2** They are **synthetic samples generated by Prometheus at scrape time**, not exposed by the target. `up` is 1 if the scrape (connection + HTTP 200 + parse) succeeded and 0 otherwise; `scrape_duration_seconds` and `scrape_samples_scraped` describe the scrape event. Only the party performing the scrape can measure whether it worked and how long it took — a pushed sample carries no equivalent "did the collection succeed" signal.

**Q1.3** In a push system the cadence lives *inside every application/agent* (the push interval is client-side). Changing it means reconfiguring and redeploying N workloads instead of editing one server config. At scale that is a fleet-wide rollout versus a one-line central change; it also makes it impossible for the monitoring team to unilaterally throttle load during an incident.

**Q2.1** Prometheus attempted its scheduled `GET /metrics` and the TCP connect was refused (target process gone). A failed scrape deterministically sets `up=0` for that interval. Liveness is a side effect of *actively trying to pull*: the very act of collection is also the health check.

**Q2.2** With push, a dead app just stops sending, so you infer failure from **absence of data** — but absence is ambiguous. It could mean the app died, the network dropped, the push agent crashed, a firewall changed, the app was intentionally scaled to zero, or it's simply between push intervals. `up == 0` is an unambiguous, timestamped, per-target boolean that says "I tried to reach this specific instance right now and could not."

**Q2.3** Examples: (1) the service was intentionally scaled to zero / undergoing a deploy; (2) a network partition or firewall change between app and monitoring backend; (3) the client-side push agent (not the app) crashed while the app is fine; (4) the app is alive but simply hasn't reached its next push tick. Pull is immune because Prometheus decides *when* to check and records success/failure of that specific attempt, distinguishing "I reached it and it's down/misconfigured" from "I couldn't reach it," rather than conflating everything into silence.

**Q3.1** A long-lived service violates *neither* mismatch: it lives far longer than the scrape interval (so it is reliably alive during scrapes) and it has a stable, discoverable network address (so there is a fixed `instance` to pull). That is precisely the shape pull was designed for.

**Q3.2** No. A 1 s interval reduces but does not eliminate the *lifetime* mismatch (a 300 ms job can still be missed), and it does nothing for the *addressability* mismatch — the job still has no persistent endpoint to scrape, and it's gone before the next tick. It also multiplies scrape load 15× fleet-wide for a case pull is structurally wrong for.

**Q3.3** The **outcome/result of the run** — e.g. success timestamp, exit status, duration, records processed. Because the process exits, there is no endpoint left to pull; the value must be captured *at the moment of completion* and stored somewhere durable (the Pushgateway) for Prometheus to pull later.

**Q4.1** The flow is **job → Pushgateway (push) → Prometheus (pull)**. The job pushes once at completion; Prometheus still *pulls* the Pushgateway on its normal scrape interval like any other target. Prometheus remains a pure pull system — the Pushgateway is just a target that happens to cache pushed samples. It does not make Prometheus push-based.

**Q4.2** Label-conflict rule: when scraped data already contains a label Prometheus would attach server-side (like `job`/`instance`), `honor_labels: false` (default) *renames* the scraped label to `exported_<label>` and applies the server-side value — hence `job="pushgateway"`, `exported_job="backup"`. `honor_labels: true` keeps the scraped labels and drops the conflicting server-side ones. Federation and Pushgateway scraping carry the *original* targets' identities inside the payload, so you must preserve them — otherwise every federated/pushed series would be mislabeled as coming from the federation endpoint or the gateway.

**Q4.3** `up{job="pushgateway"}=1` guarantees only that **Prometheus can reach and scrape the Pushgateway process**. It says nothing about whether any backup ran, succeeded, or is recent. There is no `up` series for `job="backup"` because nothing is being scraped *from the backup job* — only its cached values from the gateway. Liveness of the original job is exactly what you lose when you route through a Pushgateway.

**Q4.4** The Pushgateway holds the last pushed value indefinitely, and Prometheus re-scrapes it every interval, minting a *new sample with the same value and a current timestamp* each time — so the series never goes stale in Prometheus even though the job ran once and died. `up == 0` never fires (the gateway is healthy). The correct freshness signal is the *age of the data itself*: `time() - push_time_seconds{...}` (or a job-emitted `*_last_success_timestamp_seconds`), which grows without bound once pushes stop.

**Q4.5** Each push to a given grouping key **replaces** the previous content of that group (the gateway is a cache/last-write-wins per group, not an aggregator or a log). Ten runs pushing to the same `job/instance` leave only the tenth run's values. Design implication: put whatever must remain distinct into the grouping key (e.g. a stable `instance` per host), and never rely on the gateway to sum, average, or retain history — it does none of that. Also, groups persist until explicitly `DELETE`d (or lost on restart when `--persistence.file` is unset), so stale groups must be cleaned up.

**Q5.2 table**

| Mechanism | Prometheus collects by… | Prometheus forwards by… |
|---|---|---|
| Scraping node-exporter | **pull** | — |
| Pushgateway | pull (from the gateway) | — |
| `remote_write` | pull (locally) | **push** |
| OTel Collector `prometheus` receiver | **pull** (the Collector scrapes) | — |

**Q5.1** *Ingestion* (scraping targets → local TSDB) is **pull**; *shipping* (`remote_write` → remote store) is **push**. They are independent stages. Turning on `remote_write` changes only how already-collected samples leave Prometheus; every target is still scraped exactly as before, so all pull-side guarantees (`up`, ad-hoc curl, central schedule) are untouched.

**Q5.2** Bypassing scraping to have every app `remote_write` directly loses: per-target liveness (`up`), the ability to reproduce a target's exposition with `curl`, centralized control of cadence/relabeling, and natural back-pressure/rate-limiting by the server. You inherit the push ambiguities from Q2.2. It is nonetheless justified when pull is *impossible or impractical*: targets behind NAT/firewalls Prometheus cannot reach, serverless/FaaS and edge/IoT workloads with no stable scrapeable endpoint, or ephemeral CI jobs — the same niche the Pushgateway serves, at ingestion scale.

**Q5.3** Neither is universally superior; pull is a *fit* for Prometheus's model (dynamic, service-discovered, self-monitoring server that owns its own load). Concrete advantages seen in the labs: pull gives free per-target liveness (`up == 0`, Ex. 2) and trivial reproducibility (`curl /metrics`, Ex. 1); push (via Pushgateway) is the right tool exactly where pull structurally fails — short-lived batch jobs with no scrapeable endpoint (Ex. 3–4).
