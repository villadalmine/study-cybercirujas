# 3.3 — `kyverno jp`: JMESPath as the Debugging Surface of Kyverno

**Certification:** Kyverno Certified Associate (KCA) · **Domain 3 — Kyverno CLI** · **Topic weight: 3.0**

This topic covers the `jp` subcommand family of the Kyverno CLI — `kyverno jp query`, `kyverno jp parse` and `kyverno jp function` — and, inseparably, the JMESPath dialect those commands expose: the same expression engine that resolves every `{{ ... }}` in a `ClusterPolicy`, every `context[].apiCall.jmesPath`, every `preconditions` key, and every `deny.conditions` operand.

---

## 1. The production problem: your policy language has no REPL, and its runtime is the admission path

### 1.1 Where JMESPath actually executes

A Kyverno `ClusterPolicy` is not evaluated against your resource. It is evaluated against a synthetic JSON document — the **policy context** — that Kyverno assembles per admission request. Understanding this document is the whole topic; everything `kyverno jp` does is let you hold that document still and interrogate it offline.

```
                        kube-apiserver
                              │
                  AdmissionReview (JSON)
                              │
                              ▼
        ┌───────────────────────────────────────────┐
        │ Kyverno admission webhook (kyverno-svc)   │
        │                                           │
        │  1. Policy cache lookup (match/exclude)   │
        │  2. Build POLICY CONTEXT:                 │
        │       request.{operation,object,oldObject,│
        │                userInfo,namespace,...}    │
        │       serviceAccountName                  │
        │       serviceAccountNamespace             │
        │       images.{containers,initContainers,  │
        │               ephemeralContainers}        │
        │       element / elementIndex  (foreach)   │
        │       @  (current value, in patterns)     │
        │  3. Resolve context[] entries IN ORDER    │
        │       configMap | apiCall | imageRegistry │
        │       | variable | globalReference        │
        │       ...each may apply a jmesPath        │
        │  4. Substitute {{ }}  ← JMESPath engine   │
        │  5. Evaluate preconditions ← JMESPath     │
        │  6. Evaluate rule                         │
        │       validate.pattern  ← JMESPath in @   │
        │       validate.deny.conditions ← JMESPath │
        │       mutate.patchStrategicMerge ← {{ }}  │
        │       generate.data ← {{ }}               │
        └───────────────────────────────────────────┘
                              │
                    AdmissionResponse (allow/deny)
```

Steps 3–6 are all one language. A single mistyped key, an unquoted `kubernetes.io/arch`, a projection that flattens one level too many — and the rule either fails open (audit, silent), fails closed (`Enforce`, and now `CREATE Pod` is broken cluster-wide), or errors during substitution and takes the whole policy out of service.

### 1.2 Why iterating in-cluster is the wrong loop

The naive debugging loop for a broken expression is: edit the policy → `kubectl apply` → create a test Pod → read `kubectl describe polr` or the Kyverno logs → repeat. Every property of that loop is hostile:

| Property of the in-cluster loop | Consequence |
|---|---|
| Round-trip is 10–60 s (webhook config reconcile + policy cache refresh) | 5 iterations on a quoting bug costs a coffee break |
| `failurePolicy: Fail` + `Enforce` | A malformed expression on a broad `match` blocks real workloads while you debug |
| Webhook timeout (default `--webhookTimeout=10`, max 30 s) | An `apiCall` you added to *test* an expression is now on the critical path of every CREATE |
| Errors are reported as a substitution failure, not as a JMESPath position | `variable substitution failed` tells you *that* it broke, not *where* |
| The context document is never printed | You are guessing at the input, so you cannot tell a wrong expression from a wrong assumption about the input |
| Policy Reports are eventually consistent | You may read a `PolicyReport` generated by the *previous* revision of the policy |

`kyverno jp` collapses all of that into a sub-second, offline, zero-cluster loop where **the input is a file you control**. This is the same reason SREs prefer `promtool query instant` over clicking in Grafana: you want the evaluation isolated from the delivery mechanism.

### 1.3 The architectural claim worth internalising

> In Kyverno, JMESPath is not a convenience for reading fields. It is the type system, the null-handling strategy, the arithmetic layer, and the control flow of your policies. Nearly every "Kyverno bug" filed by a platform team is a JMESPath bug, and `kyverno jp` is the only tool that can prove it in isolation.

## 2. `kyverno jp` — anatomy of the three subcommands

```
$ kyverno jp --help
Provides a command-line interface to JMESPath, enhanced with Kyverno specific custom functions.

Usage:
  kyverno jp [command]

Available Commands:
  function    Provides function informations.
  parse       Parses jmespath expression and shows corresponding AST.
  query       Provides a command-line interface to JMESPath, enhanced with Kyverno specific custom functions.

Flags:
  -h, --help   help for jp

Use "kyverno jp [command] --help" for more information about a command.
```

| Subcommand | Answers the question | Reads a resource? | Typical use |
|---|---|---|---|
| `kyverno jp function [name...]` | "Does this function exist in **my** build, and what is its exact signature?" | No | Version-drift check; discovering the custom function set |
| `kyverno jp parse '<expr>'` | "How does the parser *group* my expression?" | No | Precedence bugs, quoting bugs, pipe-vs-subexpression confusion |
| `kyverno jp query -i <file> '<expr>'` | "What does this expression actually return for this input?" | Yes (file or stdin) | 95 % of real work |

### 2.1 `kyverno jp query`

```
$ kyverno jp query --help
Provides a command-line interface to JMESPath, enhanced with Kyverno specific custom functions.

Usage:
  kyverno jp query [-i input] [-q query|query]... [flags]

Examples:
  # Evaluate query
  kyverno jp query -i object.yaml 'request.object.metadata.name'

  # Evaluate query
  echo '{ "foo": "bar" }' | kyverno jp query 'foo'

  # Evaluate multiple queries
  kyverno jp query -i object.yaml 'request.object.metadata.name' 'request.object.metadata.namespace'

  # Evaluate query from a file
  kyverno jp query -i object.yaml -q query-file

Flags:
      --compact          Produce compact JSON output that omits non essential whitespace
  -h, --help             help for query
  -i, --input string     Input file or data (json or yaml)
  -q, --query strings    Query file (multiple can be passed)
  -u, --unquoted         Print unquoted strings
```

Four behaviours that matter operationally:

1. **Input is JSON *or* YAML.** YAML is converted to JSON before evaluation, so `spec.containers[].image` works directly against a `pod.yaml`. This is why you can `jp query` a manifest straight out of git.
2. **stdin is a first-class input.** Omit `-i` and pipe. This is what makes `kubectl get --raw` prototyping possible (see §5.2).
3. **`-u/--unquoted`** strips the JSON quotes from a scalar string result — mandatory when you want to embed the result in a shell variable, useless (and ignored) for arrays/objects.
4. **Multiple queries** may be passed positionally or via repeated `-q`; when more than one is evaluated, each result is preceded by a `#`-prefixed header naming the query.

### 2.2 `kyverno jp parse`

`parse` prints the abstract syntax tree without evaluating anything. Its only job is to answer *"did the parser read what I meant?"* — which is exactly the failure mode of `|` (pipe) versus `.` (subexpression) and of operator precedence around `&&`, `||`, `!` and comparisons.

### 2.3 `kyverno jp function`

The authoritative enumeration of every function **in the binary you are holding**. Kyverno's function set is the union of two moving targets — the JMESPath *community edition* built-ins and Kyverno's own custom functions — and both grow between minor releases. Never trust a blog post's function list; trust `kyverno jp function`.

## 3. The dialect: JMESPath community edition + Kyverno custom functions

### 3.1 Two layers, one namespace

| Layer | Provided by | Examples | Stability |
|---|---|---|---|
| Base language + built-ins | `jmespath-community/go-jmespath` | `length`, `keys`, `values`, `contains`, `starts_with`, `ends_with`, `join`, `sort_by`, `map`, `max_by`, `to_number`, `to_string`, `type`, `not_null`, `items`, `from_items`, `group_by`, `zip`, `let` | Tracks the community spec (JEPs); Kyverno bumps it on minor releases |
| Kyverno custom functions | `kyverno/pkg/engine/jmespath` | `parse_json`, `parse_yaml`, `time_*`, `semver_compare`, `regex_match`, `label_match`, `x509_decode`, `add`/`subtract`/`divide`/`multiply`/`modulo`, `base64_*`, `path_canonicalize`, `image_normalize`, `lookup`, `random`, `truncate`, `split`, `to_upper`, `to_lower`, `trim*`, `replace*`, `compare`, `equal_fold`, `object_from_lists` | Added per Kyverno minor release |

Because both layers share one namespace, **name collisions and shadowing are real**: the community edition added `split`, `replace`, `trim`, `lower`/`upper`, `items` and `pad_left`/`pad_right` after Kyverno had already shipped custom equivalents. On a given build, only `kyverno jp function <name>` tells you which signature won.


> **Exam-grade habit.** When a question or a task says "which function converts a JSON-encoded string into an object", the answer is `parse_json` — but the reflex you want is `kyverno jp function | grep -i json`, because the same reflex is what saves you in production against a version you did not install.

### 3.2 The custom functions that carry real policy weight

| Function | Signature | Why a platform team needs it |
|---|---|---|
| `parse_json` | `parse_json(string) any` | ConfigMap values are strings. Any structured allowlist stored in a ConfigMap must pass through this before it can be indexed. |
| `parse_yaml` | `parse_yaml(string) any` | Same, for YAML-encoded ConfigMap keys — very common for per-tenant configuration blobs. |
| `add` / `subtract` / `multiply` / `divide` / `modulo` | `(any, any) any` | Operate on **numbers, Kubernetes quantities (`100m`, `2Gi`) and Go durations (`1h30m`)**. This is the only sane way to compare `resources.requests.memory` against a budget. |
| `semver_compare` | `semver_compare(string, string) boolean` | Constraint matching on image tags / chart versions: `semver_compare('1.28.3', '>=1.27.0 <2.0.0')`. |
| `regex_match` | `regex_match(string, string\|number) boolean` | RE2 matching; the workhorse for naming conventions and registry prefixes. |
| `pattern_match` | `pattern_match(string, string\|number) boolean` | Kyverno's *wildcard* matcher (`*`, `?`), not regex — matches the semantics used by `match.resources.names`. |
| `label_match` | `label_match(object, object) boolean` | Subset comparison of label maps — avoids hand-rolling per-key `&&` chains. |
| `time_now_utc` / `time_before` / `time_after` / `time_diff` / `time_since` / `time_add` / `time_to_cron` | see `jp function` | Expiry annotations, maintenance windows, "no deploys on Friday" rules. |
| `x509_decode` | `x509_decode(string) object` | Decodes a PEM/DER certificate into a structured object — rotate-before-expiry policies on `kubernetes.io/tls` Secrets. |
| `image_normalize` | `image_normalize(string) string` | Expands `nginx` → `docker.io/nginx:latest`-style canonical references so prefix checks cannot be bypassed by shorthand. |
| `path_canonicalize` | `path_canonicalize(string) string` | Normalises `/etc/../etc/passwd` before hostPath allow/deny decisions — a genuine bypass class. |
| `lookup` | `lookup(object\|array, string\|number) any` | Dynamic key indexing — JMESPath has no `obj[expr]`; `lookup` is the escape hatch. |
| `object_from_lists` | `object_from_lists(array, array) object` | Builds a map from parallel arrays, e.g. zipping container names to images. |

## 4. Building the input: the single highest-value technique

### 4.1 The context document, reconstructed by hand

Your policy says `{{ request.object.spec.containers[].image }}`. Your `pod.yaml` has no `request` key. Beginners therefore strip the prefix when testing with `jp` — and then ship the untested expression. **Do not strip the prefix. Build the wrapper.**

`request-create-pod.yaml` — a faithful, minimal reconstruction of the Kyverno policy context for a `CREATE Pod` in namespace `prod-payments`:

```yaml
# request-create-pod.yaml
# A hand-built Kyverno policy context. Query it with the EXACT expressions
# that appear inside {{ }} in the policy under test.
request:
  operation: CREATE
  namespace: prod-payments
  userInfo:
    username: system:serviceaccount:prod-payments:deployer
    groups:
      - system:serviceaccounts
      - system:serviceaccounts:prod-payments
      - system:authenticated
  oldObject: null
  object:
    apiVersion: v1
    kind: Pod
    metadata:
      name: web-frontend-6d4c9f8b7-2xk9p
      namespace: prod-payments
      labels:
        app.kubernetes.io/name: web-frontend
        acme.io/cost-center: cc-4417
        acme.io/tier: frontend
      annotations:
        acme.io/owner: payments-platform@acme.example
        acme.io/expires-at: "2026-09-30T00:00:00Z"
        kubectl.kubernetes.io/last-applied-configuration: |
          {"apiVersion":"v1","kind":"Pod"}
    spec:
      serviceAccountName: web-frontend
      nodeSelector:
        kubernetes.io/arch: amd64
      initContainers:
        - name: migrate
          image: ghcr.io/acme/db-migrate:2.4.1
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 200m
              memory: 256Mi
      containers:
        - name: app
          image: ghcr.io/acme/web-frontend:1.28.3
          resources:
            requests:
              cpu: 500m
              memory: 512Mi
            limits:
              cpu: "1"
              memory: 1Gi
          securityContext:
            allowPrivilegeEscalation: false
            runAsNonRoot: true
        - name: envoy-sidecar
          image: docker.io/envoyproxy/envoy:v1.29.1
          resources:
            requests:
              cpu: 250m
              memory: 256Mi
            limits:
              cpu: 500m
              memory: 512Mi
          securityContext:
            allowPrivilegeEscalation: false
            runAsNonRoot: true

# Kyverno also injects these at the top level of the context:
serviceAccountName: deployer
serviceAccountNamespace: prod-payments
```

Now every expression is testable verbatim:

```
$ kyverno jp query -i request-create-pod.yaml 'request.object.metadata.name'
"web-frontend-6d4c9f8b7-2xk9p"
```

```
$ kyverno jp query -i request-create-pod.yaml -u 'request.object.metadata.name'
web-frontend-6d4c9f8b7-2xk9p
```

```
$ kyverno jp query -i request-create-pod.yaml 'request.object.spec.[containers, initContainers, ephemeralContainers][].image'
[
  "ghcr.io/acme/web-frontend:1.28.3",
  "docker.io/envoyproxy/envoy:v1.29.1",
  "ghcr.io/acme/db-migrate:2.4.1"
]
```

That last expression is the canonical Kyverno idiom for "every image in the Pod, including init and ephemeral containers". Note what it survives: `ephemeralContainers` is **absent** from the input. The multiselect-list produces a `null` element, flatten keeps it, and the `.image` projection silently drops it. A naïve `[]` concatenation in most other languages would throw.

### 4.2 Generating the context from a live cluster instead of by hand

```
$ kubectl get pod web-frontend-6d4c9f8b7-2xk9p -n prod-payments -o json \
    | jq '{request: {operation: "CREATE", namespace: .metadata.namespace, object: .}}' \
    > request-live.yaml
```

```
$ kyverno jp query -i request-live.yaml 'request.object.spec.containers[].name'
[
  "app",
  "envoy-sidecar"
]
```

For live objects, remember that the API server has already populated defaults (`serviceAccountName`, `terminationGracePeriodSeconds`, `imagePullPolicy`, the `kube-api-access-*` volume). A policy that passes against a live object may still fail against the *submitted* object at admission time, and vice versa. When the distinction matters, capture the real payload from the Kyverno logs at `-v 4` rather than from `kubectl get`.

## 5. Working sessions: from expression to policy

### 5.1 Session 1 — a registry allowlist, proven before it is shipped

**Requirement:** every image must come from `ghcr.io/acme/` or `docker.io/envoyproxy/`.

Step 1 — get the raw list (done above). Step 2 — find the *violations*, not the matches, because the deny condition needs a non-empty violation set:

```
$ kyverno jp query -i request-create-pod.yaml \
    'request.object.spec.[containers, initContainers, ephemeralContainers][].image | [?!starts_with(@, '"'"'ghcr.io/acme/'"'"') && !starts_with(@, '"'"'docker.io/envoyproxy/'"'"')]'
[]
```

Empty — this Pod passes. Now prove the rule actually *fires*. Mutate the input in place and re-run:

```
$ sed 's|docker.io/envoyproxy/envoy:v1.29.1|quay.io/envoyproxy/envoy:v1.29.1|' request-create-pod.yaml > request-bad.yaml
$ kyverno jp query -i request-bad.yaml \
    'request.object.spec.[containers, initContainers, ephemeralContainers][].image | [?!starts_with(@, `"ghcr.io/acme/"`) && !starts_with(@, `"docker.io/envoyproxy/"`)] | length(@)'
1
```

Two literal styles appear above: `'raw string'` and `` `"json string"` ``. Both are valid JMESPath; §5.5 explains when the shell forces your hand.

> **The bypass you just missed.** `starts_with` against a bare `nginx` returns `false`, so `nginx` would be *reported as a violation* — correct here. But a policy written as an **allowlist of prefixes with `contains`** would let `evil.example/ghcr.io/acme/x` through. And a short reference like `acme/web:1.0` resolves at runtime to `docker.io/acme/web:1.0`, which your prefix check never sees. Normalise first:

```
$ echo '{"images":["nginx","acme/web:1.0","ghcr.io/acme/web-frontend:1.28.3"]}' \
    | kyverno jp query 'images[].image_normalize(@)'
[
  "docker.io/nginx:latest",
  "docker.io/acme/web:1.0",
  "ghcr.io/acme/web-frontend:1.28.3"
]
```

### 5.2 Session 2 — prototyping a `context.apiCall.jmesPath` against the live API

The `apiCall` context entry is the single most dangerous construct in Kyverno: it puts a live API-server round-trip on the admission path. Getting its `jmesPath` wrong means either a substitution failure (policy out of service) or a silent `null` (rule fails open). Prototype it against the *same* endpoint the webhook will call:

```
$ kubectl get --raw "/api/v1/namespaces/prod-payments/resourcequotas" \
    | kyverno jp query 'items[].{name: metadata.name, hardMem: status.hard."limits.memory", usedMem: status.used."limits.memory"}'
[
  {
    "hardMem": "64Gi",
    "name": "prod-payments-quota",
    "usedMem": "41Gi"
  }
]
```

Now reduce it to the single scalar the policy needs, and verify the arithmetic:

```
$ kubectl get --raw "/api/v1/namespaces/prod-payments/resourcequotas" \
    | kyverno jp query -u 'items[0] | subtract(status.hard."limits.memory", status.used."limits.memory")'
23Gi
```

`subtract` on two Kubernetes quantities returns a quantity. This is exactly why hand-rolling the maths in `deny.conditions` with `to_number` fails: `to_number('64Gi')` is not 68719476736.

The `.` before a quoted key is mandatory: `status.hard."limits.memory"`. Without the quotes, JMESPath reads `limits` and `memory` as two nested fields and returns `null` — a silent, fail-open `null`.

```
$ kubectl get --raw "/api/v1/namespaces/prod-payments/resourcequotas" \
    | kyverno jp query 'items[0].status.hard.limits.memory'
null
```

> `null` is the enemy. It is never an error, it propagates, and in `Audit` mode it looks exactly like "no violations".

Two more `apiCall` prototypes worth memorising:

```
$ kubectl get --raw "/api/v1/namespaces/prod-payments/pods" \
    | kyverno jp query 'items | length(@)'
14
```

```
$ kubectl get --raw "/apis/networking.k8s.io/v1/namespaces/prod-payments/ingresses" \
    | kyverno jp query 'items[].spec.rules[].host | sort(@)'
[
  "api.acme.example",
  "checkout.acme.example",
  "www.acme.example"
]
```

### 5.3 Session 3 — a ConfigMap allowlist and `parse_json`

`configMap` context entries expose the ConfigMap under `<name>.data.<key>`, and **every value is a string**. Structured data must be parsed.

```yaml
# allowed-registries-cm.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: acme-registry-policy
  namespace: kyverno
data:
  # Deliberately stored as a JSON string: ConfigMap values are always strings.
  allowlist: |
    {
      "prod-payments":  ["ghcr.io/acme/", "docker.io/envoyproxy/"],
      "prod-search":    ["ghcr.io/acme/"],
      "_default":       ["ghcr.io/acme/"]
    }
  maxCpuPerContainer: "2"
```

Prototype the exact chain the policy will use — parse, then index dynamically with `lookup`, with a fallback:

```
$ kubectl get cm acme-registry-policy -n kyverno -o json \
    | kyverno jp query 'parse_json(data.allowlist)'
{
  "_default": [
    "ghcr.io/acme/"
  ],
  "prod-payments": [
    "ghcr.io/acme/",
    "docker.io/envoyproxy/"
  ],
  "prod-search": [
    "ghcr.io/acme/"
  ]
}
```

```
$ kubectl get cm acme-registry-policy -n kyverno -o json \
    | kyverno jp query "lookup(parse_json(data.allowlist), 'prod-payments')"
[
  "ghcr.io/acme/",
  "docker.io/envoyproxy/"
]
```

```
$ kubectl get cm acme-registry-policy -n kyverno -o json \
    | kyverno jp query "lookup(parse_json(data.allowlist), 'sandbox-ci') || lookup(parse_json(data.allowlist), '_default')"
[
  "ghcr.io/acme/"
]
```

That `||` is the null-safety idiom. JMESPath's or-expression treats `null`, `false`, `""`, `[]` and `{}` as false, so it doubles as a default operator — and it is what keeps Kyverno from raising `variable substitution failed` on a namespace absent from the map.

`lookup` exists because JMESPath has **no computed-key syntax**: you cannot write `map[key]` where `key` is an expression. Every attempt to write `parse_json(data.allowlist).{{request.namespace}}` is a string-concatenation hack that breaks on the first namespace containing a dash.

### 5.4 Session 4 — time, semver and certificates

Expiry annotation:

```
$ kyverno jp query -i request-create-pod.yaml -u \
    'request.object.metadata.annotations."acme.io/expires-at"'
2026-09-30T00:00:00Z
```

```
$ kyverno jp query -i request-create-pod.yaml \
    'time_before(time_now_utc(), request.object.metadata.annotations."acme.io/expires-at")'
true
```

```
$ kyverno jp query -i request-create-pod.yaml -u \
    'time_diff(time_now_utc(), request.object.metadata.annotations."acme.io/expires-at")'
1152h0m0s
```

Tag-based version floor — note the split of `image` on `:` before comparing:

```
$ kyverno jp query -i request-create-pod.yaml \
    "request.object.spec.containers[?name=='app'].image | [0] | split(@, ':') | [1] | semver_compare(@, '>=1.27.0')"
true
```

Certificate expiry — **discover the shape, do not memorise it**:

```
$ kubectl get secret acme-ingress-tls -n prod-payments -o json \
    | kyverno jp query 'x509_decode(base64_decode(data."tls.crt")) | keys(@)'
[
  "AuthorityKeyId",
  "BasicConstraintsValid",
  "Extensions",
  "IsCA",
  "Issuer",
  "PublicKey",
  "PublicKeyAlgorithm",
  "SerialNumber",
  "Signature",
  "SignatureAlgorithm",
  "Subject",
  "SubjectKeyId",
  "Validity"
]
```

```
$ kubectl get secret acme-ingress-tls -n prod-payments -o json \

{
  "NotAfter": "2026-11-14T09:12:44Z",
  "NotBefore": "2026-08-16T09:12:44Z"

```

The output shape of `x509_decode` has changed across Kyverno releases. `keys(@)` against your own binary is a two-second check that outlives any documentation you copy.

### 5.5 The escaping matrix — where most `jp` sessions actually die

Three layers of quoting stack: **shell → YAML → JMESPath**. They disagree about `'`, `"` and `` ` ``.

| JMESPath construct | Meaning | Inside a `bash` double-quoted arg | Inside a `bash` single-quoted arg | Inside a YAML policy |
|---|---|---|---|---|
| `'text'` (raw string literal) | Literal string, no escapes | Safe: `"... 'text' ..."` | Must break out: `'"'"'text'"'"'` | Safe inside a YAML double-quoted scalar |
| `` `"text"` `` (JSON literal) | Literal, JSON-typed | **DANGEROUS** — backticks are command substitution | Safe | Safe, but YAML dislikes a leading `` ` ``; quote the scalar |
| `` `true` `` / `` `42` `` | JSON boolean/number literal | **DANGEROUS** | Safe | Safe when the scalar is quoted |
| `"key.with.dots"` (quoted identifier) | Field name containing `.`, `/`, `-` | Must escape: `\"key\"` | Safe | Use YAML single quotes around the whole expression |
| `\|` (pipe) | Stops a projection | Safe if quoted | Safe | Safe |

Practical rule that removes the whole class of bugs:

> **Wrap the JMESPath expression in shell single quotes; use `'raw literals'` only when you must, otherwise prefer double-quoted identifiers.** When you need both, put the expression in a file and use `-q`.

```
$ cat > q-registry.jmespath <<'EOF'
request.object.spec.[containers, initContainers, ephemeralContainers][].image
  | [?!starts_with(@, `"ghcr.io/acme/"`) && !starts_with(@, `"docker.io/envoyproxy/"`)]
EOF
$ kyverno jp query -i request-bad.yaml -q q-registry.jmespath
[
  "quay.io/envoyproxy/envoy:v1.29.1"
]
```

A query file removes the shell from the equation entirely and is reviewable in git next to the policy.

### 5.6 `kyverno jp parse` — reading precedence instead of guessing it

```
$ kyverno jp parse 'request.object.metadata.name'
ASTSubexpression {
  children: {
    ASTSubexpression {
      children: {
        ASTField {
          value: "request"
        }
        ASTField {
          value: "object"
        }
    ASTField {
      value: "metadata"
    }
    ASTField {
      value: "name"
    }
}
```

The value of `parse` is comparative. Consider the classic pipe bug:

```
$ kyverno jp query -i request-create-pod.yaml 'request.object.spec.containers[].name | length(@)'
2
```

```
$ kyverno jp query -i request-create-pod.yaml 'request.object.spec.containers[].length(@)'
[
  3,
  14
]
```

Identical-looking, completely different: without the pipe, `length(@)` is applied *inside* the projection to each element (the length of each container **name**); with the pipe, the projection is closed first and `length` applies to the array. `parse` shows the structural difference — `ASTPipe` at the root versus `ASTProjection` — before you ship a policy that counts characters instead of containers.

**This is the number-one cause of "my `deny` condition compares the wrong thing" in Kyverno.** Any time a function follows a `[]` or `[*]`, ask whether you meant to close the projection.

## 6. From verified expression to production policy

Every `{{ }}` below has been produced by the sessions above. That is the discipline being taught: **no expression enters a manifest until `kyverno jp query` has printed its value.**

### 6.1 A validating policy with a ConfigMap-backed, per-namespace allowlist

```yaml
# policy-registry-allowlist.yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: restrict-image-registries
  annotations:
    policies.kyverno.io/title: Restrict Image Registries
    policies.kyverno.io/category: Supply Chain Security
    policies.kyverno.io/severity: high
    policies.kyverno.io/subject: Pod
    policies.kyverno.io/description: >-
      Images must originate from a registry prefix allowlisted for the target
      namespace. The allowlist is read from a ConfigMap so it can be changed
      without re-deploying the policy. References are normalised with
      image_normalize() so that short forms such as "nginx" cannot bypass the
      prefix check.
spec:
  background: true
  # Kyverno >= 1.12: failureAction lives on the rule. On Kyverno <= 1.11 use
  # the policy-level `spec.validationFailureAction: Enforce` instead.
  rules:
    - name: validate-registry-prefix
      match:
        any:
          - resources:
              kinds:
                - Pod
      # Do not police the platform's own namespaces.
      exclude:
        any:
          - resources:
              namespaces:
                - kube-system
                - kyverno
      context:
        # 1. Load the allowlist ConfigMap.
        - name: registryPolicy
          configMap:
            name: acme-registry-policy
            namespace: kyverno
        # 2. Parse the JSON string and select this namespace's entry,
        #    falling back to "_default". Verified in §5.3.
        - name: allowedPrefixes
          variable:
            jmesPath: >-
              lookup(parse_json(registryPolicy.data.allowlist), '{{ request.namespace }}')
              || lookup(parse_json(registryPolicy.data.allowlist), '_default')
            default: []
        # 3. Normalise every image reference in the Pod. Verified in §5.1.
        - name: allImages
          variable:
            jmesPath: >-
              request.object.spec.[containers, initContainers, ephemeralContainers][].image_normalize(@)
            default: []
      preconditions:
        all:
          - key: "{{ request.operation || 'BACKGROUND' }}"
            operator: AnyIn
            value:
              - CREATE
              - UPDATE
          - key: "{{ length(allowedPrefixes) }}"
            operator: GreaterThan
            value: 0
      validate:
        failureAction: Enforce
        message: >-
          Image(s) {{ allImages[?!starts_with(@, allowedPrefixes[0])] | join(', ', @) }}
          are not from an allowlisted registry for namespace {{ request.namespace }}.
          Allowed prefixes: {{ join(', ', allowedPrefixes) }}.
        foreach:
          - list: "allImages"
            deny:
              conditions:
                all:
                  # element is the current image; count how many allowlisted
                  # prefixes it matches. Zero matches => deny.
                  - key: >-
                      {{ length(allowedPrefixes[?starts_with('{{ element }}', @)]) }}
                    operator: Equals
                    value: 0
```

Two engineering notes a KCA candidate is expected to make:

* `context` entries resolve **in declaration order**, and later entries may reference earlier ones (`allowedPrefixes` reads `registryPolicy`). Reorder them and you get `Unknown key "registryPolicy" in path`.
* `variable.default` is the supported way to make a context entry null-safe. Without it, a namespace missing from the ConfigMap turns a validation into a **substitution error**, and a substitution error in `Enforce` mode is a denial with an unhelpful message.

### 6.2 A mutating policy driven by quantity arithmetic

```yaml
# policy-default-memory-limit.yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: default-memory-limit-from-request
  annotations:
    policies.kyverno.io/title: Default Memory Limit From Request
    policies.kyverno.io/category: Resource Management
    policies.kyverno.io/severity: medium
    policies.kyverno.io/description: >-
      Containers that declare a memory request but no memory limit receive a
      limit of 1.5x their request. The multiplication is performed by the
      JMESPath multiply() function, which understands Kubernetes quantities;
      to_number() would silently mis-handle the Gi/Mi suffixes.
spec:
  background: false
  rules:
    - name: set-memory-limit
      match:
        any:
          - resources:
              kinds:
                - Pod
      mutate:
        foreach:
          - list: "request.object.spec.containers"
            preconditions:
              all:
                - key: "{{ element.resources.requests.memory || '' }}"
                  operator: NotEquals
                  value: ""
                - key: "{{ element.resources.limits.memory || '' }}"
                  operator: Equals
                  value: ""
            patchStrategicMerge:
              spec:
                containers:
                  - name: "{{ element.name }}"
                    resources:
                      limits:
                        memory: "{{ multiply(element.resources.requests.memory, `1.5`) }}"
```

Verify the arithmetic before trusting it:

```
$ echo '{"req":"512Mi"}' | kyverno jp query -u 'multiply(req, `1.5`)'
768Mi
```

```
$ echo '{"req":"1Gi"}' | kyverno jp query -u 'multiply(req, `1.5`)'
1536Mi
```

Contrast with the wrong instinct, which a `jp` session exposes in seconds:

```
$ echo '{"req":"512Mi"}' | kyverno jp query 'to_number(req) * `1.5`'
Error: SyntaxError: Unknown char: '*'
```

```
$ echo '{"req":"512Mi"}' | kyverno jp query 'multiply(to_number(req), `1.5`)'
Error: invalid type for: 512Mi, expected: [number]
```

### 6.3 A validating policy on certificate expiry

```yaml
# policy-tls-secret-expiry.yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-tls-secret-validity-window
  annotations:
    policies.kyverno.io/title: Require Minimum TLS Certificate Validity
    policies.kyverno.io/category: Security
    policies.kyverno.io/severity: high
    policies.kyverno.io/description: >-
      Rejects kubernetes.io/tls Secrets whose certificate expires in less than
      14 days, so that a short-lived or already-expired certificate is never
      installed on an Ingress.
spec:
  background: false
  rules:
    - name: check-notafter
      match:
        any:
          - resources:
              kinds:
                - Secret
              selector:
                matchLabels:
                  acme.io/managed-tls: "true"
      preconditions:
        all:
          - key: "{{ request.object.type || '' }}"
            operator: Equals
            value: kubernetes.io/tls
      context:
        - name: notAfter
          variable:
            jmesPath: >-
              x509_decode(base64_decode(request.object.data."tls.crt")).Validity.NotAfter
            default: ""
        - name: minValidUntil
          variable:
            jmesPath: "time_add(time_now_utc(), '336h')"
      validate:
        failureAction: Enforce
        message: >-
          Certificate in this Secret expires at {{ notAfter }}, which is less
          than 14 days away (threshold {{ minValidUntil }}).
        deny:
          conditions:
            any:
              - key: "{{ notAfter }}"
                operator: Equals
                value: ""
              - key: "{{ time_before(notAfter, minValidUntil) }}"
                operator: Equals
                value: true
```

```
$ kyverno jp query -u 'time_add(time_now_utc(), `"336h"`)' <<< '{}'
2026-08-27T14:22:09Z
```

## 7. The verification ladder

`jp` is rung one. A policy is not verified until it has climbed all four, and each rung catches a class the rung below cannot see.

| Rung | Command | Proves | Cannot prove |
|---|---|---|---|
| 1. Expression | `kyverno jp query -i ctx.yaml '<expr>'` | The expression parses and returns the value/type you expect for a given input | That Kyverno builds that context; that the rule matches |
| 2. Policy vs. resource | `kyverno apply policy.yaml --resource pod.yaml` | Match/exclude, preconditions, substitution, rule outcome — offline, no cluster | Behaviour against context entries needing a live API (unless mocked) |
| 3. Regression suite | `kyverno test .` | Expected pass/fail per (policy, rule, resource) tuple, in CI, forever | Real admission ordering, webhook timeouts, RBAC of the Kyverno SA |
| 4. Cluster | `kubectl apply --dry-run=server -f pod.yaml` | The real webhook, real RBAC, real `apiCall` latency | Nothing — but it is the slowest and most disruptive rung |

## 8. Failure diagnosis: symptom → cause → `jp` reproduction

| Symptom in cluster | Root cause | Reproduce / fix with `jp` |
|---|---|---|
| Rule never fires; report shows `skip` | Precondition evaluates to `null`/`false` because a key is absent | `kyverno jp query -i ctx.yaml '<precondition key expr>'` → if `null`, add `\|\| 'default'` or a `variable.default` |
| `variable substitution failed: Unknown key "x" in path` | Expression references a key that does not exist and has no fallback | Same query; fix with `\|\| ''`, `not_null()`, or `context[].variable.default` |
| `Error: SyntaxError: Expected tRbracket, received: tOr` (or similar) | Malformed expression — usually mismatched `[]`, `()` or quotes | `kyverno jp parse '<expr>'`; bisect by shortening the expression until it parses |
| `unknown function: to_uppr` | Typo, or the function does not exist in **this** Kyverno version | `kyverno jp function \| grep -i upp` |
| `invalid type for: <nil>, expected: [array object string]` | `length()`/`keys()` applied to a `null` from a failed lookup | Query the sub-expression alone; the last non-null step is where it breaks |
| Deny condition with `GreaterThan` errors or never triggers | Comparing a **string** to a **number**; or comparing quantities as numbers | `kyverno jp query '...\| type(@)'` — must be `number` for arithmetic operators, or use quantity/duration-aware `add`/`subtract` |
| Condition compares character counts instead of item counts | `length(@)` inside a projection instead of after a pipe | `kyverno jp parse` both forms; look for `ASTPipe` vs `ASTProjection` |
| Rule passes for a Pod that clearly violates it | Projection dropped `null`s and produced `[]`, so the filter found nothing | Query the intermediate list; assert `length(@)` is what you expect |
| Works on a live object, fails at admission (or vice-versa) | API-server defaulting differs between submitted and stored object | Capture the real payload from `kubectl logs -n kyverno deploy/kyverno-admission-controller -v 4`, rebuild the context file |
| `apiCall` returns `null` and the policy fails open | Wrong `urlPath`, or Kyverno's ServiceAccount lacks RBAC for that resource | `kubectl get --raw "<urlPath>" \| kyverno jp query '<jmesPath>'`, then `kubectl auth can-i --as=system:serviceaccount:kyverno:kyverno-admission-controller get <resource>` |
| Field with a `/` or `.` always resolves to `null` | Unquoted identifier | `... .annotations."acme.io/owner"` — quote the segment |
| Backtick literal became empty in the shell | `` ` `` triggered command substitution inside `"` | Re-run with single quotes, or move the expression into a `-q` file |

### 8.1 A worked diagnosis

Reported: *"the cost-center label policy passes for Pods that have no such label."*

```
$ kyverno jp query -i request-create-pod.yaml 'request.object.metadata.labels."acme.io/cost-center"'
"cc-4417"
```

```
$ kyverno jp query -i request-no-labels.yaml 'request.object.metadata.labels."acme.io/cost-center"'
null
```

```
$ kyverno jp query -i request-no-labels.yaml 'regex_match(`"^cc-[0-9]{4}$"`, request.object.metadata.labels."acme.io/cost-center" || `""`)'
false
```

```
$ kyverno jp query -i request-no-labels.yaml 'regex_match(`"^cc-[0-9]{4}$"`, request.object.metadata.labels."acme.io/cost-center")'
Error: invalid type for: <nil>, expected: [string number]
```

Diagnosis complete in three commands: the original policy used the second, un-defaulted form, the engine raised a substitution error, and the rule was recorded as `error` rather than `fail` — which the team's dashboard counted as "not a violation". The fix is the `|| \`""\`` guard, plus alerting on the `error` result type, not just `fail`.

## 9. Trade-offs a Platform Architect must be able to defend

### 9.1 `kyverno jp query` versus the neighbours

| Tool | Dialect | Kyverno custom functions | Reads YAML | Right when |
|---|---|---|---|---|
| `kyverno jp query` | JMESPath (community) + Kyverno | **Yes** | Yes | Prototyping anything that will live inside a `ClusterPolicy` |
| `jp` (upstream JMESPath CLI) | JMESPath | No | No (JSON only) | Learning base JMESPath; will reject `parse_json`, `time_*`, `semver_compare` |
| `jq` | jq language | No | No | Ad-hoc shell data wrangling; **cannot** validate a Kyverno expression |
| `yq` | jq-like over YAML | No | Yes | Manifest editing, not policy prototyping |
| `kubectl -o jsonpath` | JSONPath | No | n/a | Quick field extraction; different grammar, different null semantics |
| `kubectl -o custom-columns` | JSONPath subset | No | n/a | Tabular reporting |

The trap: `jq` will happily evaluate something *resembling* your expression and give you confidence you have not earned. A JMESPath projection and a `jq` `.[]` differ in null handling, and Kyverno's arithmetic on `2Gi` exists in neither `jq` nor upstream `jp`.

### 9.2 JMESPath versus CEL inside Kyverno

Recent Kyverno releases (1.14+) added CEL-based policy types (`ValidatingPolicy` and friends) alongside the classic `ClusterPolicy`/`Policy`. Both engines ship in the same binary; only one is reachable from `kyverno jp`.

| Dimension | JMESPath (`ClusterPolicy` / `Policy`) | CEL (`ValidatingPolicy`, `ValidatingAdmissionPolicy`) |
|---|---|---|
| Offline REPL | **`kyverno jp query`** | No equivalent `jp` subcommand |
| Kubernetes-quantity arithmetic | `add`/`subtract`/`multiply`/`divide` on `2Gi`, `100m`, `1h` | `quantity()` library |
| Null handling | Silent `null`, propagates — fail-open risk | Errors are explicit; `has()` / `optional` types |
| Cost/complexity bounds | None — an expensive expression is your problem | Cost budget enforced by the runtime |
| Offloading to the API server | Kyverno can *generate* a `ValidatingAdmissionPolicy` from a subset of rules | Native |
| Mutation, generation, image verification | Full support | Narrower (per policy type / K8s version) |
| KCA exam surface | **This is what is tested** | Peripheral |

The pragmatic architecture in 2026: author simple, high-volume validations so they can be offloaded to `ValidatingAdmissionPolicy` (no webhook hop), and keep JMESPath `ClusterPolicy` for mutation, generation, `imageRegistry` context and anything needing `apiCall`. `kyverno jp` remains the debugging tool for the second half.

### 9.3 The cost of an expression on the admission path

| Construct in a rule | Added latency per admission request | Failure blast radius |
|---|---|---|
| Pure JMESPath over `request.object` | microseconds | None beyond the rule |
| `configMap` context entry | ~0 (informer-cached) | Stale value if the informer lags |
| `variable` + `parse_json` of a large blob | sub-millisecond, but per request | CPU on the admission controller |
| `apiCall` (in-cluster) | 1 API-server round-trip, typically 2–20 ms | Counts against `--webhookTimeout`; API-server slowness becomes admission slowness |
| `apiCall` to an external `service` | Network RTT, unbounded in practice | With `failurePolicy: Fail`, an external outage becomes a cluster-wide admission outage |
| `imageRegistry` context | Registry round-trip, 50–500 ms | Registry outage blocks Pod creation |
| `globalReference` (GlobalContextEntry) | ~0 at admission; refreshed on an interval | Staleness window equal to the refresh interval |

This table is why the `jp` workflow matters beyond convenience: **every `apiCall` you prototype offline with `kubectl get --raw` is one you did not iterate on inside the admission path.** And when a heavy `apiCall` is unavoidable, the `globalReference` context entry moves the cost off the request path entirely — but you still prototype its `jmesPath` with `jp`.

## 10. Command reference to have in muscle memory

```
# Discover the function set of the binary you actually have
$ kyverno jp function
$ kyverno jp function parse_json
$ kyverno jp function | grep -i time

# Evaluate against a file (JSON or YAML)
$ kyverno jp query -i request.yaml 'request.object.metadata.name'
$ kyverno jp query -i request.yaml -u 'request.object.metadata.name'     # no quotes
$ kyverno jp query -i request.yaml --compact 'request.object.spec.containers[].name'

# Evaluate against stdin — the live-cluster prototyping loop
$ kubectl get pod NAME -n NS -o json | kyverno jp query 'spec.containers[].image'
$ kubectl get --raw "/api/v1/namespaces/NS/resourcequotas" | kyverno jp query 'items[0].status.hard'

# Several queries at once
$ kyverno jp query -i request.yaml 'request.operation' 'request.namespace'

# Query from a file — no shell quoting at all
$ kyverno jp query -i request.yaml -q query.jmespath

# Inspect the parse tree when precedence is suspect
$ kyverno jp parse 'spec.containers[].name | length(@)'

# Climb the ladder
$ kyverno apply policy.yaml --resource pod.yaml --values-file values.yaml
$ kyverno test .
$ kubectl apply --dry-run=server -f pod.yaml
```

### Checklist before any Kyverno expression is merged

1. `kyverno jp function <name>` for every non-obvious function used — confirms it exists in your target version.
2. `kyverno jp query` against a **passing** input *and* a **failing** input. A rule proven only against the happy path is not proven.
3. `kyverno jp query` against an input where the field is **absent**. If the result is `null`, add `|| default` or `variable.default`.
4. `kyverno jp parse` if the expression contains a function after `[]`, or mixes `&&`/`||`/`!` with comparisons.
5. `type(@)` on any operand feeding `GreaterThan`/`LessThan`/arithmetic.
6. Move the expression into a `-q` file if the shell quoting required more than one level of escaping.
7. Only then: `kyverno apply` → `kyverno test` → server-side dry run.
