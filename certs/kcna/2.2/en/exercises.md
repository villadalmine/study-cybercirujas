# 2.2 Debugging

## Exercise 1: Pod stuck in `ImagePullBackOff`

1. Create a file named `bad-pod.yaml` with the following content:
   ```yaml
   apiVersion: v1
   kind: Pod
   metadata:
     name: broken-image
   spec:
     containers:
       - name: app
         image: nginx:this-tag-no-existe
   ```
2. Apply the manifest: `kubectl apply -f bad-pod.yaml`
3. List the Pods: `kubectl get pods`. You will see a `STATUS` that changes between `ErrImagePull` and `ImagePullBackOff`.
4. Run `kubectl describe pod broken-image` and pay attention to the `Events` section at the end of the output.
5. Fix the manifest by changing the `image` to `nginx:latest`, apply again with `kubectl apply -f bad-pod.yaml` and confirm that the Pod transitions to `Running`.

**Comprehension questions:**
- Why is `kubectl get pods` not enough to find the root cause of the problem, and which command does show it?
- What is the difference between `ErrImagePull` and `ImagePullBackOff` in terms of what the kubelet is doing at that moment?

## Exercise 2: `CrashLoopBackOff` and log inspection

1. Create `crash-pod.yaml`:
   ```yaml
   apiVersion: v1
   kind: Pod
   metadata:
     name: crash-demo
   spec:
     containers:
       - name: app
         image: busybox
         command: ["sh", "-c", "echo 'simulated failure' && exit 1"]
   ```
2. Apply the manifest and observe the `STATUS` with `kubectl get pods -w` (the `-w` flag watches for changes).
3. Once `CrashLoopBackOff` appears, view the logs from the last attempt: `kubectl logs crash-demo`.
4. If the container has restarted more than once, compare with the logs from the previous attempt: `kubectl logs crash-demo --previous`.
5. Check the restart count and exponential backoff in `kubectl describe pod crash-demo` (field `Restart Count` and the `BackOff` events).

**Comprehension questions:**
- What does the `CrashLoopBackOff` state mean, and why does the interval between retries increase over time?
- When is it essential to use `--previous` with `kubectl logs` instead of the simple command?

## Exercise 3: Inspect a running container with `kubectl exec`

1. Deploy a healthy Pod: `kubectl run debug-target --image=nginx`
2. Wait for it to be `Running`: `kubectl get pod debug-target`
3. Open an interactive shell inside the container: `kubectl exec -it debug-target -- sh`
4. Inside the shell, verify connectivity and relevant environment variables (e.g., `env` and `cat /etc/resolv.conf`), then exit with `exit`.
5. Run a specific command without entering an interactive shell: `kubectl exec debug-target -- ls /usr/share/nginx/html`

**Comprehension questions:**
- What limitation does `kubectl exec` have when the container image does not include a shell or diagnostic tools?
- What alternative does Kubernetes offer to debug a "distroless" container without a shell, without modifying the original image?

## Exercise 4: Failures of `readiness` and `liveness probes`

1. Create `probe-pod.yaml`:
   ```yaml
   apiVersion: v1
   kind: Pod
   metadata:
     name: probe-demo
   spec:
     containers:
       - name: app
         image: nginx
         readinessProbe:
           httpGet:
             path: /no-existe
             port: 80
           periodSeconds: 5
   ```
2. Apply the manifest and run `kubectl get pod probe-demo`. Notice that the Pod stays `Running` but with `READY 0/1`.
3. Run `kubectl describe pod probe-demo` and look for the `Unhealthy` events generated by the probe.
4. Fix the `path` to `/` and re-apply the manifest.
5. Confirm that `READY` changes to `1/1` with `kubectl get pod probe-demo -w`.

**Comprehension questions:**
- Why can a Pod be `Running` and at the same time not receive traffic from a Service?
- What is the practical difference between a failed `readinessProbe` and a failed `livenessProbe` in terms of the action Kubernetes takes?

## Exercise 5: `OOMKilled` and resource limits

1. Create `oom-pod.yaml`:
   ```yaml
   apiVersion: v1
   kind: Pod
   metadata:
     name: oom-demo
   spec:
     containers:
       - name: app
         image: polinux/stress
         resources:
           limits:
             memory: "20Mi"
         command: ["stress"]
         args: ["--vm", "1", "--vm-bytes", "50M", "--vm-hang", "1"]
   ```
2. Apply the manifest and wait a few seconds.
3. Run `kubectl get pod oom-demo` and observe the `STATUS` (`OOMKilled` inside the container's last state).
4. Confirm the cause with `kubectl describe pod oom-demo`, checking `Last State: Terminated, Reason: OOMKilled`.
5. Increase `limits.memory` to `"100Mi"`, reapply and verify that the Pod stays `Running`.

**Comprehension questions:**
- Which component kills the container when it exceeds its `memory limit`, and why does this not depend on the `CPU limit`?
- How do you distinguish in `kubectl describe pod` between an `OOMKilled` and a `CrashLoopBackOff` caused by an application error?

## Exercise 6: Cluster events and resource usage with `kubectl top`

1. List all recent events in the current namespace, sorted by timestamp: `kubectl get events --sort-by=.lastTimestamp`
2. Filter events of type `Warning` only: `kubectl get events --field-selector type=Warning`
3. If `metrics-server` is installed, check the resource usage of Pods: `kubectl top pods`
4. Also check usage per Node: `kubectl top nodes`
5. Cross-reference this information with `kubectl describe node <node-name>` to see if the Node is under resource pressure (`Conditions` like `MemoryPressure` or `DiskPressure`).

**Comprehension questions:**
- Why is `kubectl get events` useful for debugging even when the problematic Pod has already been deleted or recreated?
- What infrastructure requirement does the cluster need for `kubectl top` to work?

**Exercise 1**
- `kubectl get pods` only shows the summary status (`STATUS`), not the reason behind it. `kubectl describe pod` exposes the `Events` section, where the kubelet records the exact cause of the failure (e.g., "manifest unknown" when trying to pull a non-existent tag).
- `ErrImagePull` is the first failed attempt to pull the image; `ImagePullBackOff` is the subsequent state, where Kubernetes waits an increasing interval (backoff) before retrying, to avoid saturating the registry with consecutive failed pulls.

**Exercise 2**
- `CrashLoopBackOff` indicates that the container started, terminated (in this case with `exit 1`) and Kubernetes restarts it according to the `restartPolicy`, but waits longer between retries (exponential backoff) to avoid immediate infinite restarts that consume Node resources.
- `--previous` is necessary when the container has already restarted and the logs from the current process do not contain the original failure information, because each restart launches a new process whose logs are shown separately from the previous one.

**Exercise 3**
- If the image does not have a shell (`sh`, `bash`) or utilities like `ls` or `cat`, `kubectl exec -it ... -- sh` fails because there is no binary to run inside the container.
- Kubernetes offers `ephemeral containers` (`kubectl debug`), which temporarily inject a container with diagnostic tools into the Pod (or share its process namespace), without needing to modify or rebuild the original image.

**Exercise 4**
- A Pod can be `Running` (the container process is still alive) but not `Ready` if its `readinessProbe` fails; in that case, the Endpoint controller removes it from the list of endpoints of the Service, so it does not receive traffic even though the container is active.
- A failed `readinessProbe` only removes the Pod from the Service's Endpoints (the container is not restarted); a failed `livenessProbe` causes the kubelet to kill and restart the container, because it is interpreted as the process having entered an unrecoverable state.

**Exercise 5**
- The Linux kernel's `OOM killer` is what terminates the container when it exceeds its `memory limit`, because memory is not a "compressible" resource: when exhausted, the process must die. CPU, on the other hand, is compressible (it can be limited through *throttling* without killing the process), so exceeding a `CPU limit` does not terminate the container.
- In `kubectl describe pod`, an `OOMKilled` is identified in `Last State: Terminated` with `Reason: OOMKilled` and `Exit Code: 137`; a `CrashLoopBackOff` due to an application error shows `Reason: Error` with a different exit code (usually defined by the application itself) and no mention of memory.

**Exercise 6**
- Cluster events have a `Reason` and `Message` associated with the object that generated them, and persist for a while (default one hour) in `etcd` even if the Pod that originated them no longer exists, allowing reconstruction of what happened after the fact.
- `kubectl top` requires the cluster to have `metrics-server` (or another Metrics API provider) deployed, because `kubectl` does not calculate CPU/memory usage by itself but queries that API.
