# KCSA Study Guide — Topic 6.3: Supply Chain Compliance

---

## 1. Motivation & Production Architectural Problem

### 1.1 The Software Supply Chain Attack Vector in Kubernetes
Modern cloud-native applications rely heavily on multi-stage build pipelines, external base images, third-party binary dependencies, and open-source packages. This complex dependency graph exposes cluster workloads to severe supply-chain attack vectors, including:

- **Source Code Tampering:** Unintended or malicious commits introduced into upstream dependencies or source repositories.
- **CI/CD Build Pipeline Compromise:** Hijacking build agents to inject backdoors or altered binaries into container images after compilation without changing source control history.
- **Registry & Image Tampering:** Unauthorized modification or overwriting of image tags (`latest`, `v1.2.0`) inside container registries.
- **Dependency Confusion & Typosquatting:** Fetching malicious public packages that shadow internal private scope packages during build time.

```
+---------------------------------------------------------------------------------------------------+
|                                 SOFTWARE SUPPLY CHAIN THREAT MODEL                                 |
+---------------------------------------------------------------------------------------------------+
|  [Source Code] ---> [Build / CI Pipeline] ---> [Container Registry] ---> [Kubernetes Admission]   |
|        |                    |                         |                          |                |
|  * Malicious Code    * Build Tampering         * Image Overwriting       * Deployment of Untrusted|
|  * Compromised Deps  * Key Exfiltration        * Registry Poisoning        / Non-compliant Artifacts|
+---------------------------------------------------------------------------------------------------+
```

### 1.2 Compliance Mandates & Regulatory Drivers
Organizations deploying workloads into production are governed by strict regulatory frameworks and security directives:
- **US Executive Order 14028 & NIST SP 800-218 (SSDF):** Mandates verifiable cryptographic provenance and explicit Software Bill of Materials (SBOM) for all software running in critical environments.
- **SLSA (Supply-chain Levels for Software Artifacts):** Defines a non-frangible checklist of standards (Levels 1 through 3+) guaranteeing build integrity, hermeticity, and source traceability.
- **PCI-DSS 4.0 & SOC 2 Type II:** Requires auditability of software integrity, automated vulnerability management, and strict access controls over production deployments.

### 1.3 The Architectural Problem
The core architectural challenge for SRE and Platform teams is establishing **zero-trust software ingestion**. Merely scanning container images for known vulnerabilities (CVEs) at rest is insufficient. 

A resilient supply chain compliance architecture must guarantee that:
1. **Every container image running in Kubernetes is cryptographically signed** by an authorized, verifiable identity (Keyless OIDC / PKI).
2. **Software Bill of Materials (SBOM)** exists, is signed, and is linked to the exact cryptographic digest (`sha256:...`) of the image.
3. **Build Provenance** (such as SLSA Level 3 provenance) is generated by an isolated, non-falsifiable build platform and validated at runtime.
4. **Kubernetes Dynamic Admission Webhooks** deterministically reject any pod deployment attempting to run images lacking valid signatures, required attestations, or compliance certificates—without degrading API server performance or causing cascading deployment outages.

## 2. Technical Comparisons & Trade-off Tables

### 2.1 Software Bill of Materials (SBOM) Standards

| Feature / Criteria | SPDX (Software Package Data Exchange) | CycloneDX | SWID (Software Identification Tags) |
| :--- | :--- | :--- | :--- |
| **Governing Body** | Linux Foundation (ISO/IEC 5962:2021) | OWASP Foundation | ISO/IEC 19770-2:2015 / NIST |
| **Primary Design Focus** | License compliance, open-source governance, intellectual property analysis. | Application Security (AppSec), vulnerability tracking, dependency analysis, cryptography tracking. | Software asset management, installed software inventory tracking. |
| **JSON/YAML/XML Support** | JSON, YAML, TV (Tag:Value), RDF/XML. | JSON, XML, Protobuf. | XML natively. |
| **Vulnerability Exchange Format (VEX)** | Integrated via OpenVEX or SPDX 3.0 extension profiles. | Native integration (CycloneDX VEX spec). | Requires external mapping extensions. |
| **Tooling Ecosystem** | Syft, Trivy, Kubernetes `bom`, SPDX tools. | Syft, Trivy, Dependency-Check, OWASP suite. | Windows/Linux OS package management integrations. |
| **Production Recommendation** | **High** for legal/license auditing & broad open-source compatibility. | **High** for active security operations, AppSec, and real-time CVE correlation. | Low for modern containerized cloud-native supply chains. |

### 2.2 Cryptographic Signing Protocols & Trust Models

| Feature / Criteria | Traditional Private Key Signing (GPG / Static RSA) | Keyless Sigstore (Fulcio + Rekor + OIDC) | Cosign Static KMS (AWS KMS, GCP KMS, Vault) |
| :--- | :--- | :--- | :--- |
| **Key Lifecycle** | Long-lived asymmetric key pairs; high risk of key exposure or loss. | Ephemeral short-lived keys (valid for minutes); no private key management. | Managed KMS keys; asymmetric key rotated via cloud provider. |
| **Identity Identity Provider** | Self-signed or internal CA certificate chains. | OIDC Identity Tokens (GitHub Actions, SPIFFE/SPIRE, Google/Microsoft Workplace). | Cloud IAM Role / Policy bindings. |
| **Non-Repudiation & Auditability**| Local signature verification; audit trail relies on private logs. | **Immutable Public Ledger (Rekor)** provides cryptographically verifiable transparency. | Cloud Audit Logs (CloudTrail / Cloud Logging). |
| **Revocation Handling** | CRL / OCSP complexity; difficult in air-gapped environments. | Handled via short-lived cert expiry + Rekor transparency timestamps. | Managed via IAM policy revocation and KMS key disabling. |
| **Operational Overhead** | Extremely High (secure key distribution, HSMs, rotation procedures). | **Very Low** for platform engineers (automates PKI via short-lived certs). | Medium (Requires cloud credential access at CI/CD time). |

### 2.3 Kubernetes Admission Policy Engines for Supply Chain Verification

| Metric / Dimension | Kyverno | OPA Gatekeeper | Cosign CLI / Policy Controller |
| :--- | :--- | :--- | :--- |
| **Policy Language** | Declarative Kubernetes YAML (Native CRDs). | Rego (Declarative query language). | YAML Policy CRDs (Cosign-focused). |

| **Vulnerability Threshold Enforcement** | Native matching on Cosign vulnerability attestation payloads. | Complex custom Rego scripts evaluating JSON attestation blobs. | Supported via image policy CRD matching. |
| **Multi-Resource Validation** | Excellent (Validates, mutates, generates K8s resources). | Excellent (Validates objects across arbitrary K8s context). | Limited primarily to Container Image supply chain verification. |

## 3. Production-Ready Manifests & Configurations

### 3.1 CI/CD Automated Supply Chain Pipeline (GitHub Actions)
This production pipeline builds a container image, generates a **CycloneDX SBOM**, signs the image using **Sigstore Keyless**, and attaches an **in-toto SLSA Level 3 Provenance attestation** to the OCI registry.

```yaml
name: Supply Chain Compliance Pipeline

on:
  push:
    branches:
      - main
    tags:
      - 'v*'

permissions:
  contents: read
  packages: write
  id-token: write # Required for Sigstore OIDC keyless signing

jobs:
  build-sign-attest:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout Source Code
        uses: actions/checkout@v4

      - name: Install Cosign
        uses: sigstore/cosign-installer@v3.5.0

      - name: Install Syft
        uses: anchore/sbom-action/download-syft@v0.16.0

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v3

      - name: Log in to GitHub Container Registry (GHCR)
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Extract Image Metadata
        id: meta
        uses: docker/metadata-action@v5
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=semver,pattern={{version}}
            type=sha,format=long

      - name: Build and Push OCI Container Image
        id: build-image
        uses: docker/build-push-action@v5
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}

      - name: Generate CycloneDX SBOM with Syft
        run: |
          IMAGE_DIGEST="ghcr.io/${{ github.repository }}@${{ steps.build-image.outputs.digest }}"
          syft "${IMAGE_DIGEST}" -o cyclonedx-json=sbom.cyclonedx.json

      - name: Sign Container Image (Keyless Sigstore)
        run: |
          IMAGE_DIGEST="ghcr.io/${{ github.repository }}@${{ steps.build-image.outputs.digest }}"
          cosign sign --yes "${IMAGE_DIGEST}"

      - name: Attest SBOM to OCI Registry
        run: |
          IMAGE_DIGEST="ghcr.io/${{ github.repository }}@${{ steps.build-image.outputs.digest }}"
          cosign attest --yes \
            --type cyclonedx \
            --predicate sbom.cyclonedx.json \
            "${IMAGE_DIGEST}"

      - name: Attest SLSA Provenance to OCI Registry
        run: |
          IMAGE_DIGEST="ghcr.io/${{ github.repository }}@${{ steps.build-image.outputs.digest }}"
          cosign attest --yes \
            --type slsaprovenance \
            --predicate <(cat <<EOF
          {
            "builder": { "id": "https://github.com/actions/runner" },
            "buildType": "https://actions.github.io/build-types/v1",
            "invocation": {
              "configSource": {
                "uri": "git+https://github.com/${{ github.repository }}@${{ github.sha }}",
                "digest": { "sha1": "${{ github.sha }}" }
              }
            }
          }
          EOF
          ) "${IMAGE_DIGEST}"
```

### 3.2 Kyverno ClusterPolicy: Enforce Image Signature, SLSA Provenance, & SBOM Verification
This production-grade `ClusterPolicy` validates that all workloads targeting the `production` namespace meet three non-negotiable criteria:
1. Valid **Keyless Sigstore signature** issued by the specific GitHub repository workflow.
2. Verified **SLSA Provenance attestation**.
3. Verified **CycloneDX SBOM attestation** attached to the container image.

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: enforce-supply-chain-compliance
  annotations:
    policies.kyverno.io/title: Enforce Image Signatures, Provenance, and SBOM
    policies.kyverno.io/category: Supply Chain Security
    policies.kyverno.io/severity: critical
    policies.kyverno.io/subject: Pod, Deployment, StatefulSet
    description: >-
      Verifies that container images deployed to production namespaces are signed via
      Sigstore Keyless OIDC, contain an authenticated SLSA Provenance attestation,
      and have an attached CycloneDX SBOM attestation.
spec:
  validationFailureAction: Enforce
  background: true
  webhookTimeoutSeconds: 15
  failurePolicy: Fail
  rules:
    - name: verify-image-signature-and-attestations
      match:
        any:
          - resources:
              kinds:
                - Pod
              namespaces:
                - production
      verifyImages:
        - imageReferences:
            - "ghcr.io/my-org/*"
          mutateDigest: true
          verifyDigest: true
          required: true
          keyless:
            issuer: "https://token.actions.githubusercontent.com"
            subject: "https://github.com/my-org/*/.github/workflows/*@refs/heads/main"
            rekor:
              url: "https://rekor.sigstore.dev"
          attestations:
            - type: https://slsa.dev/provenance/v0.2
              attestors:
                - entries:
                    - keyless:
                        issuer: "https://token.actions.githubusercontent.com"
                        subject: "https://github.com/my-org/*/.github/workflows/*@refs/heads/main"
                        rekor:
                          url: "https://rekor.sigstore.dev"
            - type: https://cyclonedx.org/schema/bom-1.4.json
              attestors:
                - entries:
                    - keyless:
                        issuer: "https://token.actions.githubusercontent.com"
                        subject: "https://github.com/my-org/*/.github/workflows/*@refs/heads/main"
                        rekor:
                          url: "https://rekor.sigstore.dev"
```

### 3.3 Gatekeeper OPA Constraint & ConstraintTemplate for Supply Chain Verification
For clusters leveraging **OPA Gatekeeper**, the following `ConstraintTemplate` defines an assertion mechanism to block unhashed/unresolved image tags, enforcing immutable digest referencing (`sha256:`).

```yaml
apiVersion: templates.gatekeeper.sh/v1beta1
kind: ConstraintTemplate
metadata:
  name: k8sdisallowtagsonly
  annotations:
    metadata.gatekeeper.sh/title: Disallow Mutable Image Tags
    description: Requires all container images to specify an explicit sha256 digest reference to protect against image mutation attacks.
spec:
  crd:
    spec:
      names:
        kind: K8sDisallowTagsOnly
  targets:
    - target: admission.k8s.gatekeeper.sh
      rego: |
        package k8sdisallowtagsonly

        violation[{"msg": msg}] {
          container := input.review.object.spec.template.spec.containers[_]
          not contains(container.image, "@sha256:")
          msg := sprintf("Container '%v' uses a mutable image reference '%v'. Supply chain compliance requires pinned immutable sha256 digests.", [container.name, container.image])
        }
---
apiVersion: constraints.gatekeeper.sh/v1beta1
kind: K8sDisallowTagsOnly
metadata:
  name: enforce-immutable-digests-production
spec:
  enforcementAction: deny
  match:
    kinds:
      - apiGroups: ["apps"]
        kinds: ["Deployment", "StatefulSet", "DaemonSet"]
    namespaces:
      - "production"
```

## 5. Verification & Failure Diagnostics Guide

```
+---------------------------------------------------------------------------------------------------+
|                               SUPPLY CHAIN DIAGNOSTIC FLOWCHART                                   |
+---------------------------------------------------------------------------------------------------+
| Pod Admission Rejected                                                                            |
|        |                                                                                          |
|        +---> 1. Check Image Reference: Is it using tag or @sha256 digest?                         |
|        |                                                                                          |
|        +---> 2. Run Cosign CLI: `cosign verify --certificate-identity ...`                        |
|        |       |-- Failure: Signature missing or Rekor entry non-existent                          |
|        |       +-- Failure: OIDC SAN Mismatch (Workflow/Repo mismatch)                             |
|        |                                                                                          |
|        +---> 3. Run Cosign Attestation: `cosign verify-attestation --type ...`                    |
|        |       |-- Failure: Predicate schema invalid (e.g. SPDX vs CycloneDX spec)               |
|        |                                                                                          |
|        +---> 4. Inspect Admission Controller Logs (Kyverno/Gatekeeper Webhook)                    |
|                +-- Failure: Webhook timeout (Check API server latency / Rekor availability)       |
+---------------------------------------------------------------------------------------------------+
```

### 5.1 Common Production Failures & Root Causes

#### 1. Failure: `no matching signatures found` / OIDC Subject Mismatch
- **Symptom:** Admission controller blocks deployment; `cosign verify` returns exit code `1`.
- **Root Cause:** The OIDC subject identity printed in the Fulcio certificate (`https://github.com/my-org/repo/.github/workflows/main.yml@refs/heads/main`) does not match the strict regex defined in the Kyverno/Gatekeeper Policy.
- **Diagnostic Command:**
  ```bash
  # Inspect exact SAN certificate extensions embedded in the signature bundle
  cosign verify-option \
    --keyless \
    ghcr.io/my-org/payment-service@sha256:e3b0c... | jq '.[].optional.Subject'
  ```

#### 2. Failure: Admission Webhook Timeout (`webhookTimeoutSeconds`)
- **Symptom:** Pod creation hangs for 10–15 seconds and returns `Internal error occurred: failed calling webhook`.
- **Root Cause:** The admission controller is making synchronous external HTTP calls to public Rekor/Fulcio servers (`rekor.sigstore.dev`) or the OCI Registry to fetch `.att` or `.sig` image manifests, hitting network latency or rate limits.
- **Remediation:** 
  1. Cache public key/cert bundles locally inside the cluster via Kyverno `imageVerification` caching settings.
  2. Increase webhook timeout setting to 15 seconds (`webhookTimeoutSeconds: 15`).
  3. Deploy a private, self-hosted Sigstore instance (TUF root, Rekor, Fulcio) inside enterprise infrastructure boundaries.

#### 3. Failure: `Attestation Predicate Type Mismatch`
- **Symptom:** Image signature is valid, but attestation verification fails.
- **Root Cause:** The tool generated a `slsaprovenance/v0.1` statement, but the admission policy strictly mandates `https://slsa.dev/provenance/v0.2` or `CycloneDX` schema version `1.4`.
- **Diagnostic Command:**
  ```bash
  # Query registry for all attached attestations and inspect predicateType
  cosign tree ghcr.io/my-org/payment-service@sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
  ```

### 5.2 Step-by-Step Diagnostic Runbook for SREs

1. **Verify Local Image Digest Resolution:**
   Ensure local machine and cluster API server resolve the exact same container image digest:
   ```bash
   crane digest ghcr.io/my-org/payment-service:v1.2.0
   ```

2. **Validate Sigstore Rekor Log Entry Existence:**
   Query Rekor directly using the signature bundle UUID:
   ```bash
   rekor-cli search --sha256 e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855
   ```

3. **Inspect Kyverno Admission Logs in Real-time:**
   ```bash
   kubectl logs -n kyverno -l app=kyverno -f --tail=100 | grep -i "imageverify"
   ```

4. **Audit Non-Compliant Running Workloads:**
   Identify any workloads currently running in the cluster that violate the supply chain policy:
   ```bash
   kubectl get clusterpolicyreport -o json | jq '.reports[].results[] | select(.result=="fail")'
   ```
