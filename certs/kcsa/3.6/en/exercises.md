## Technical Deep-Dive: Mechanics & Architecture

Kubernetes Audit Logging provides a security-relevant, chronological set of records documenting the sequence of actions in a cluster. The API server audits activities generated by users, applications that utilize the Kubernetes API, and the control plane components themselves.

```
       +-------------------------------------------------------------------------+
       |                         kube-apiserver Pipeline                         |
       |                                                                         |
       |  +--------------------+    +-------------------+    +----------------+  |
Client ---> | Authentication &   | -> | Audit Evaluation  | -> | Authorization  | ---> Storage /
       |  | Impersonation      |    | Engine            |    | & Admission    |      etcd
       |  +--------------------+    +---------+---------+    +----------------+  |
       +--------------------------------------|----------------------------------+
                                              | Emits Audit Event
                                              v
                                   +---------------------+
                                   | Audit Policy Filter |
                                   | (First Match Wins)  |
                                   +----------+----------+
                                              |
                                              v
                                   +---------------------+
                                   | Backend & Buffer    |
                                   | (Batch / Blocking)  |
                                   +----------+----------+
                                              |
                        +---------------------+---------------------+
                        |                                           |
                        v                                           v
            +-----------------------+                   +-----------------------+
            | Log File Backend      |                   | Webhook Backend       |
            | (/var/log/kube-audit) |                   | (External SIEM / HTTP)|
            +-----------------------+                   +-----------------------+
```

### 1. Audit Stages
Each request to `kube-apiserver` can trigger audit events at distinct lifecycle stages:
* **`RequestReceived`**: Generated as soon as the API server receives the request, prior to delegating down the handler chain.
* **`ResponseStarted`**: Generated after response headers are sent, but before the response body is sent. (Applicable only to long-running requests like `watch`, `exec`, `portforward`).
* **`ResponseComplete`**: Generated when the response body is complete and no more bytes will be sent.
* **`Panic`**: Generated when a panic state occurs while processing the request.

### 2. Audit Levels
Audit levels dictate the granularity of data captured:
* **`None`**: Do not log events matching this rule.
* **`Metadata`**: Log request metadata (requesting user, timestamp, resource, verb, namespace, etc.) but omit request and response bodies.
* **`Request`**: Log request metadata and request body, but omit response body.
* **`RequestResponse`**: Log metadata, request body, and response body.

### 3. Policy Evaluation Semantics
* Rules are evaluated in **top-to-bottom order**.
* The **first matching rule** dictates the audit level for the event.
* If a request does not match any rule in the policy, it defaults to **`None`** (no audit log emitted).

### 4. Buffering and Delivery Modes
* **`batch`**: Asynchronously buffers events in memory and writes them in batches. Higher throughput; risk of event loss if `kube-apiserver` crashes before buffer flush.
* **`blocking`**: Synchronously blocks API request processing until the audit backend acknowledges the event write. Zero data loss; severe performance impact on API latency.
* **`blocking-strict`**: Similar to `blocking`, but if writing to the audit backend fails during `RequestReceived`, the entire API request fails immediately.

### Exercise 1: Designing and Applying a Production-Grade Audit Policy

#### Step 1.1: Create the Policy File
Log in to your control-plane node. Create the audit policy directory and write a hardened, production-ready `AuditPolicy` manifest to `/etc/kubernetes/audit-policy.yaml`.

Execute the following shell command:

```bash
sudo mkdir -p /etc/kubernetes/audit
cat <<'EOF' | sudo tee /etc/kubernetes/audit/policy.yaml
apiVersion: audit.k8s.io/v1
kind: Policy
omitStages:
  - "RequestReceived"
rules:
  # 1. Do not log noisy read-only system events
  - level: None
    users: ["system:kube-proxy"]
    verbs: ["watch"]
    resources:
      - group: ""
        resources: ["endpoints", "services", "endpointslices"]

  # 2. Do not log status checks from kubelet
  - level: None
    userGroups: ["system:nodes"]
    verbs: ["get"]
    resources:
      - group: ""
        resources: ["nodes", "nodes/status"]

  # 3. Log Secret and ConfigMap mutations at Metadata level to avoid exposing sensitive data in logs
  - level: Metadata
    resources:
      - group: ""
        resources: ["secrets", "configmaps"]
    verbs: ["create", "update", "patch", "delete"]

  # 4. Log high-risk actions (RBAC, Pod Exec, Attach) at RequestResponse level
  - level: RequestResponse
    resources:
      - group: "rbac.authorization.k8s.io"
        resources: ["roles", "rolebindings", "clusterroles", "clusterrolebindings"]
      - group: ""
        resources: ["pods/exec", "pods/attach", "pods/portforward"]

  # 5. Default catch-all for remaining workloads: log metadata only
  - level: Metadata
    omitStages:
      - "ResponseStarted"
EOF
```

Expected Output:
```text
apiVersion: audit.k8s.io/v1
kind: Policy
omitStages:
  - "RequestReceived"
...
```

### Exercise 2: Configuring `kube-apiserver` Log Backend & Storage Mounts

#### Step 2.1: Update `kube-apiserver` Static Pod Manifest
Edit `/etc/kubernetes/manifests/kube-apiserver.yaml` to include audit logging command-line flags and volume mounts.

First, take a backup of the static pod manifest:
```bash
sudo cp /etc/kubernetes/manifests/kube-apiserver.yaml /etc/kubernetes/manifests/kube-apiserver.yaml.bak
```

Now add the required flags under `spec.containers[0].command` and declare the host mounts under `volumeMounts` and `volumes`.

Run the following script to verify the required changes or apply them:

```bash
# Verify flags to add to /etc/kubernetes/manifests/kube-apiserver.yaml:
cat <<'EOF'
--audit-policy-file=/etc/kubernetes/audit/policy.yaml
--audit-log-path=/var/log/kubernetes/audit/audit.log
--audit-log-maxage=30
--audit-log-maxbackup=10
--audit-log-maxsize=100
--audit-log-mode=batch
--audit-log-batch-max-size=100
--audit-log-batch-max-wait=5s
EOF
```

Add the corresponding `volumeMounts` and `volumes` in `/etc/kubernetes/manifests/kube-apiserver.yaml`:

```yaml
    volumeMounts:
    - mountPath: /etc/kubernetes/audit
      name: audit-policy
      readOnly: true
    - mountPath: /var/log/kubernetes/audit
      name: audit-logs
      readOnly: false
  volumes:
  - hostPath:
      path: /etc/kubernetes/audit
      type: DirectoryOrCreate
    name: audit-policy
  - hostPath:
      path: /var/log/kubernetes/audit
      type: DirectoryOrCreate
    name: audit-logs
```

Ensure `/var/log/kubernetes/audit` exists on the host:
```bash
sudo mkdir -p /var/log/kubernetes/audit
```

### Exercise 4: Advanced Webhook Backend Diagnostics & Failure Strategies

#### Step 4.1: Analyze Webhook Backend Configuration Flags
When streaming audit events to a SIEM (e.g., Falco, Splunk, Elastic) via Webhook, `kube-apiserver` relies on a kubeconfig formatted configuration file.

Examine the required flags:
```bash
cat <<'EOF'
--audit-webhook-config-file=/etc/kubernetes/audit/webhook-kubeconfig.yaml
--audit-webhook-initial-backoff=10s
--audit-webhook-mode=batch
--audit-webhook-batch-max-wait=5s
EOF
```

#### Step 4.2: Webhook Failure Policy Mechanics
Unlike admission webhooks which explicitly support `failurePolicy: Ignore` or `failurePolicy: Fail`, the audit webhook behavior is controlled via `--audit-log-mode` / `--audit-webhook-mode`:
* **`batch`**: Webhook endpoint unreachable -> events dropped silently in memory once batch queue buffer fills up (`--audit-webhook-batch-buffer-wait`). API server latency remains unaffected.
* **`blocking-strict`**: Webhook endpoint unreachable -> API server returns `500 Internal Server Error` for incoming client requests, preventing un-audited operations.

## Solutions & Architectural Explanations

<details>
<summary><strong>Click to Expand Answers to Exercise Questions</strong></summary>

### Answers to Exercise 1
1. **Secrets at `Metadata` level:** Logging `Secrets` or `ConfigMaps` at `Request` or `RequestResponse` level writes the unencrypted payload (base64 data) into `/var/log/kubernetes/audit/audit.log`. Any entity with read access to the node host filesystem or log aggregation pipeline could compromise credentials. `Metadata` captures who modified the secret and when, without leaking plain-text payload values.
2. **`kubectl exec` matching rule:** Rule 4 (`level: RequestResponse`) matches because `pods/exec` is explicitly listed under subresources for group `""`. Both request metadata and response details will be logged.

### Answers to Exercise 2
1. **`batch` vs `blocking` impact:** Under `blocking` mode, `kube-apiserver` synchronously writes each audit event to disk before responding to the HTTP client. Under heavy workload churn, disk I/O bottlenecks directly degrade Kubernetes API response times and can lead to client-side request timeouts (`504 Gateway Timeout`).
2. **Invalid Policy YAML behavior:** If the audit policy path is specified via `--audit-policy-file` but contains invalid syntax or unknown API versions, `kube-apiserver` fails during startup validation and crashes. The container will enter a `CrashLoopBackOff` or fail static pod initialization, rendering the API server unavailable until fixed.

### Answers to Exercise 3
1. **Verifying payload omission:** In the `jq` output for `db-credentials`, the field `requestObject` is completely absent, and `"level": "Metadata"` is explicitly present. Only metadata such as `user`, `sourceIPs`, `verb`, and `objectRef` exist.
2. **Audit on `403 Forbidden`:** Yes. Audit evaluation occurs before authorization failure response generation. The event will be logged at `ResponseComplete` stage, capturing the requesting identity and showing `"responseStatus": {"code": 403, "status": "Failure", "reason": "Forbidden"}`.

### Answers to Exercise 4
1. **PCI-DSS Webhook Mode Choice:** `blocking-strict` (or `blocking`) is required to guarantee strict auditability without gaps. The severe trade-off is **availability**: if the SIEM or Webhook endpoint experiences an outage or network partition, `kube-apiserver` will reject API requests, causing cluster management and deployment pipelines to fail.

</details>

## Quick Reference Summary Table

| Audit Level | Includes Metadata? | Includes Request Body? | Includes Response Body? | Recommended Target Resources |
|---|---|---|---|---|
| **`None`** | No | No | No | High-volume status polls (`endpoints`, `nodes/status`, `kube-proxy` watches) |
| **`Metadata`** | Yes | No | No | `Secrets`, `ConfigMaps`, general workload pods (`create`/`delete`) |
| **`Request`** | Yes | Yes | No | Non-sensitive mutations where request payload is needed for audit, but responses are large |
| **`RequestResponse`** | Yes | Yes | Yes | `RBAC` (Roles, Bindings), `pods/exec`, `pods/attach`, Authentication mutations |
