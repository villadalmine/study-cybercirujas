# Topic 1.3: Open Source Software and Licensing

参考文献: https://learning.lpi.org/en/learning-materials/010-160/1/1.3/

## 演習 1: Free Software と Open Source の定義を比較する

Free Software Foundation (FSF) が提唱する「four freedoms」と、Open Source Initiative (OSI) が定める「Open Source Definition」は、似ているようで力点が異なります。この演習では、自分の言葉でその違いを整理します。

1. ターミナルを開き、作業用のディレクトリを作成する。
   ```
   mkdir -p ~/lpi-1.3 && cd ~/lpi-1.3
   ```
2. `nano freedoms.txt`(または好きなエディタ)でファイルを開き、FSF が定義する four freedoms を自分の言葉で書き出す。
   - Freedom 0: 目的を問わずプログラムを実行する自由
   - Freedom 1: プログラムがどう動作するか研究し、必要に応じて改変する自由(source code へのアクセスが前提)
   - Freedom 2: コピーを再配布して隣人を助ける自由
   - Freedom 3: 改変したバージョンを公衆に配布する自由
3. 同じファイルに、OSI の Open Source Definition が強調する点(source code の公開、派生物の許可、差別の禁止など)を1〜2行でまとめる。
4. ファイルを保存し、内容を `cat freedoms.txt` で確認する。

### 理解度チェック
- Q1. FSF の立場と OSI の立場は、最終的にどちらも「同じライセンスの集合」を実質的に許容する傾向がありますが、両者が強調する「軸」の違いは何か、一文で説明してください。
- Q2. Freedom 1 が実行可能であるために技術的に必須な条件は何ですか?

## 演習 2: インストール済みパッケージのライセンス情報を調べる

Linux ディストリビューションのパッケージマネージャは、各パッケージのライセンス情報やコピーライトを記録しています。

1. 使用しているディストリビューションを確認する。
   ```
   cat /etc/os-release
   ```
2. Debian/Ubuntu 系の場合、任意のパッケージ(例: `bash`)のコピーライトファイルを表示する。
   ```
   cat /usr/share/doc/bash/copyright
   ```
   Red Hat/Fedora 系の場合は `rpm` でライセンスフィールドを直接照会する。
   ```
   rpm -qi bash | grep -i license
   ```
3. 同じパッケージについて `apt show bash`(Debian系)または `dnf info bash`(Fedora系)を実行し、`License` の行を確認する。
4. 別のパッケージ(例: `vim` や `git`)でも同じ手順を繰り返し、ライセンスが異なるかどうかを比較する。

### 理解度チェック
- Q3. なぜ Linux ディストリビューションは、個々のパッケージごとにライセンス情報をローカルに保持する必要があるのですか?
- Q4. `/usr/share/doc/<package>/copyright` に記載されている情報と、パッケージマネージャの `License` フィールドは、必ずしも一言一句同じではないことがあります。その理由として考えられることを1つ挙げてください。

## 演習 3: Copyleft ライセンスと Permissive ライセンスの文言を比較する

GPL のような copyleft ライセンスと、MIT/BSD のような permissive ライセンスは、再配布時の義務が大きく異なります。

1. システムに含まれる GPL のフルテキストを表示する(多くの Debian系ディストリビューションに存在)。
   ```
   less /usr/share/common-licenses/GPL-3
   ```
   (存在しない場合は、任意の GPL 対象パッケージの copyright ファイルから参照する)
2. `/`(スラッシュ)を押して `must` という単語を検索し、再配布の際に課される義務(source code の提供、同一ライセンスでの配布など)がどこに書かれているか確認する。`q` で終了。
3. 演習4でクローンするリポジトリの `LICENSE` ファイル、または手元にある MIT/BSD ライセンスのプロジェクトのライセンス文を表示する。
   ```
   cat LICENSE
   ```
4. GPL と MIT/BSD のテキストを見比べ、「派生物にも同じライセンスを適用することを要求しているか」という観点でメモを取る。

### 理解度チェック
- Q5. Copyleft ライセンスの最大の特徴を、"派生物 (derivative work)" という語を使って説明してください。
- Q6. Permissive ライセンス(MIT/BSD など)で配布されたコードを、プロプライエタリ(非公開ソース)な製品に組み込むことは一般的に可能ですか?

## 演習 4: Git リポジトリのライセンスファイルを確認する

多くの Open Source プロジェクトは、リポジトリのルートに `LICENSE` または `COPYING` というファイルを置いています。

1. 任意の公開リポジトリをクローンする(例として Git 自体のソース)。
   ```
   git clone --depth 1 https://github.com/git/git.git
   cd git
   ```
2. ライセンス関連のファイルを探す。
   ```
   ls | grep -i -E "licen|copying"
   ```
3. 見つかったファイルの先頭部分を表示し、どのライセンス(GPLv2, MIT, Apache-2.0 など)が使われているか特定する。
   ```
   head -n 20 COPYING
   ```
4. リポジトリの `README` に、コントリビューション時のライセンス合意(Developer Certificate of Origin や Contributor License Agreement など)に関する記載がないか確認する。

### 理解度チェック
- Q7. リポジトリに `LICENSE` ファイルが存在しない場合、そのコードを自由に再利用してよいと判断できますか? 理由も述べてください。
- Q8. Developer Certificate of Origin (DCO) は何のために使われる仕組みですか?

## 演習 5: Open Source コミュニティの活動形態を観察する

Open Source プロジェクトは、企業のクローズドな開発と異なり、mailing list、issue tracker、wiki など公開されたチャネルで開発が進みます。

1. 演習4でクローンしたプロジェクト(または任意の有名プロジェクト)の GitHub ページを開き、`Issues` タブと `Pull requests` タブを確認する。
2. 直近でクローズされた issue を1つ選び、誰が報告し、誰が修正したパッチを提出したかを確認する(会社名ではなく個人アカウントであることが多い点に注目)。
3. プロジェクトに `CONTRIBUTING.md` があればその内容を表示する。
   ```
   cat CONTRIBUTING.md
   ```
4. そこに書かれているコミュニティ運営のルール(コーディング規約、行動規範 = Code of Conduct、レビュープロセスなど)を1〜2点メモする。

### 理解度チェック
- Q9. プロプライエタリソフトウェアのサポート体制(ベンダーによる有償サポート)と、Open Source コミュニティ主体のサポート体制の違いを1つ挙げてください。
- Q10. `Code of Conduct` がプロジェクトに存在することの目的は何ですか?

<summary>解答例</summary>

**演習 1**
- A1. FSF は「ユーザーの自由(倫理・哲学的な権利)」を軸に議論し、OSI は「開発プロセスにおける実用上のメリット(品質・協業のしやすさ)」を軸に議論する傾向がある。両者が許容するライセンスの集合はほぼ重なるが、強調点が異なる。
- A2. Freedom 1(改変のためにプログラムの動作を研究する自由)を行使するには、source code へのアクセスが技術的に不可欠である。

**演習 2**
- A3. 各パッケージには異なる作者・異なるライセンスが設定されている可能性があり、配布物全体を再配布する際に個々の義務(著作権表示の保持、ライセンス文の同梱など)を果たすため、ローカルに正確な記録を保持する必要があるため。
- A4. パッケージマネージャの `License` フィールドはメンテナが要約・分類したタグ(例: GPL-2+)であり、`copyright` ファイルはファイル単位・モジュール単位で異なる複数のライセンスが混在している詳細な一次情報であるため、表現が一致しないことがある。

**演習 3**
- A5. Copyleft ライセンスは、元のコードから派生した derivative work を再配布する場合、その派生物にも元と同一(または互換性のある)ライセンスを適用することを義務付ける点が最大の特徴である。
- A6. 一般的に可能。Permissive ライセンスは、著作権表示とライセンス文の保持といった最小限の条件を満たせば、ソースを非公開にしたプロプライエタリ製品への組み込みを許可している。

**演習 4**
- A7. 判断できない。多くの法域では、明示的なライセンスがない場合、著作権法によりデフォルトで「All rights reserved」の状態(無断使用不可)とみなされるため、LICENSE ファイルがなければ自由な再利用は前提にできない。
- A8. DCO は、コントリビューターが提出するパッチについて「自分にはそれを提出する権利があり、プロジェクトのライセンスの下で配布されることに同意する」という宣言に、コミットへの署名(Signed-off-by)という形で行う仕組みである。

**演習 5**
- A9. プロプライエタリソフトウェアは通常、契約に基づくベンダーの有償サポート(SLA保証など)が中心であるのに対し、Open Source コミュニティのサポートは、mailing list や issue tracker を通じたボランティアベースの相互扶助が中心となる(有償サポートを提供する企業が別途存在する場合もある)。
- A10. 参加者が互いに敬意を持って協力できる環境を保つための行動規範を明文化し、ハラスメントなどの問題行動を未然に防ぎ、コミュニティの健全性を維持することが目的である。
