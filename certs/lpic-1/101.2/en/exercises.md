# LPIC-1 101.2 — Boot the system
## Guided Exercises (Exam 101-500, syllabus v5.0 — weight 4.69)

> **Lab safety.** Every block that writes to `/etc/default/grub`, `/boot`, `/etc/fstab` or NVRAM boot entries can make a machine unbootable. Run these on a **disposable VM with a snapshot taken before you start**. Blocks marked *read-only* are safe on any host. Recovery instructions for each destructive step are included in the block itself.
>
> Reference platform: **Fedora 40 / RHEL 9** (GRUB 2 + BLS + dracut + systemd 255). Debian/Ubuntu equivalents are given inline, because the exam objectives are distribution-neutral.

---

## Block 1 — Establish the firmware path: BIOS/MBR vs UEFI/ESP *(read-only)*

Everything downstream — where the bootloader lives, how it is found, whether NVRAM matters — is decided by this one fact. Determine it empirically, never by assumption.

1. Ask the kernel whether it was handed an EFI system table:

```bash
[ -d /sys/firmware/efi ] && echo "UEFI mode" || echo "BIOS/Legacy (CSM) mode"
```

```
UEFI mode
```

2. If UEFI, read the firmware boot variables out of NVRAM:

```bash
sudo efibootmgr -v
```

**Comprehension check — Block 1**

- **Q1.1** — `/sys/firmware/efi` is populated by the kernel, not by the firmware. What does its *absence* prove, and what does it fail to prove about the machine's hardware?
- **Q1.2** — In the `efibootmgr -v` output, `Boot0002` points at `HD(1,GPT,4c1f2b7a-...)/File(\EFI\FEDORA\SHIMX64.EFI)`. Which component stores that string, and what happens to boot if you `dd` a fresh disk image onto the same machine but never touch NVRAM?
- **Q1.3** — Why must the ESP be `vfat` and not `xfs` or `ext4`?
- **Q1.4** — In step 6 the disk uses **GPT** yet boots via **BIOS**. What is the 1 MiB `bios_grub` partition for, and what did GRUB use on an MBR/DOS-labelled disk instead?
- **Q1.5** — The MBR is 512 bytes and holds a 64-byte partition table plus a 2-byte signature. How many bytes are left for boot code, and why is that number the reason GRUB is split into stages?

- **Q2.3** — In the `linux` line, `($root)/vmlinuz-...` has no `/boot` prefix, yet the file is at `/boot/vmlinuz-...` on the running system. Explain.

### Block 1 — Firmware path

**A1.1** — The absence of `/sys/firmware/efi` proves only that **the currently running kernel was not booted through UEFI boot services**; the kernel populates that directory from the EFI system table it receives at handoff. It does **not** prove the hardware lacks UEFI. The usual cause is a UEFI-capable board booting through its Compatibility Support Module (CSM/legacy), or a distro installed in legacy mode on a GPT disk. Modern firmware often also lacks a CSM entirely, in which case legacy boot is genuinely impossible — but you learn that from the firmware setup, not from `/sys`.

**A1.2** — The string lives in **NVRAM on the motherboard**, as a UEFI boot variable (`Boot0002` under `EFI_GLOBAL_VARIABLE`), not on disk. Consequences of restoring a disk image without touching NVRAM: the entry's device path contains the ESP's **partition GUID** (`4c1f2b7a-...`); if the restored image has a different partition GUID, the firmware cannot resolve the path and falls back to `BootOrder` successors — typically `Boot2001 EFI Hard Drive`, which looks for the removable-media fallback `\EFI\BOOT\BOOTX64.EFI`. If that file exists (step 4 shows it does), boot succeeds anyway; if it does not, you land in the firmware shell. Repair with `efibootmgr -c -d /dev/vda -p 1 -L Fedora -l '\EFI\fedora\shimx64.EFI'`.

**A1.3** — The UEFI specification mandates that firmware implement a FAT-based filesystem driver for the ESP (FAT12/16/32; FAT32 in practice for fixed disks). Firmware carries no ext4/XFS/Btrfs driver, so the ESP is the only filesystem it is guaranteed to read. That is the whole reason `/boot/efi` is a separate, small, `vfat` partition rather than part of `/boot`.

**A1.4** — On **GPT + BIOS**, there is no post-MBR "gap" you can rely on, because the GPT primary header and partition array occupy LBA 1–33. The `bios_grub` partition (GUID type `21686148-6449-6E6F-744E-656564454649`, `EF02` in gdisk) is unformatted space reserved for GRUB's **core image** (`core.img`, formerly "stage 1.5"). On **MBR/DOS** disks GRUB instead wrote `core.img` into the unpartitioned sectors between LBA 1 and the first partition — the "MBR gap", historically 62 sectors, now typically 2047.

**A1.5** — 512 − 64 (partition table) − 2 (`0x55AA` signature) = **446 bytes** of boot code. A filesystem driver, LVM/RAID support and a menu cannot fit in 446 bytes, so GRUB's `boot.img` in the MBR does exactly one thing: load the first sector of `core.img` from a hardcoded LBA and jump to it. `core.img` then contains the filesystem drivers needed to read `/boot/grub2/` as ordinary files. That is the entire rationale for multi-stage boot loaders.

### Block 2 — Bootloader configuration

**A2.1** — `/etc/default/grub` is an **input to a generator**, not a runtime configuration. Nothing reads it at boot. On a BLS system, two things must happen: (1) `grub2-mkconfig -o /boot/grub2/grub.cfg` regenerates the GRUB script, and (2) the per-kernel `options` line in `/boot/loader/entries/*.conf` must be updated — which `grub2-mkconfig` does **not** do for existing entries. The command that updates existing entries is `grubby --update-kernel=ALL --args="nosmt"`. On Debian/Ubuntu (no BLS) a single `update-grub` after editing `GRUB_CMDLINE_LINUX_DEFAULT` suffices.

**A2.2** — Editing with `e` is **one-shot and volatile**: GRUB copies the entry into memory, you edit the copy, `Ctrl-X` boots it, and nothing is written to disk. Editing `/boot/loader/entries/*.conf` is **persistent** and survives reboot — but it is per-kernel, so a kernel update installs a *new* `.conf` file generated from `/etc/kernel/cmdline` (or the current default's args) and your edit does not propagate. Only `/etc/default/grub` + `grubby --update-kernel=ALL`, or `/etc/kernel/cmdline`, survive both.

**A2.3** — GRUB's paths are relative to the **root of the filesystem it set as `$root`**, which here is the separate `/boot` partition (`hd0,gpt2`). Inside that filesystem the kernel is at `/vmlinuz-...`. Once Linux is running, that same filesystem is mounted at `/boot`, so the path acquires the prefix. If `/boot` were *not* a separate partition, `$root` would be the root filesystem and the GRUB line would read `/boot/vmlinuz-...`.

**A2.4** — In the **GRUB environment block**, `/boot/grub2/grubenv` — a fixed 1024-byte file that GRUB can rewrite in place without a filesystem driver capable of allocation. Read it with `grub2-editenv list`, write it with `grub2-editenv - set saved_entry=...`, or from a running system with `grub2-set-default <index-or-id>` / `grubby --set-default=/boot/vmlinuz-...`. `grub2-reboot <entry>` sets `next_entry` for exactly one boot.

**A2.5** — Disk enumeration is not stable. Add a second disk, change the SATA/NVMe port, boot the same image on different hardware, or have the firmware present the USB installer as `hd0` — and `(hd0,gpt2)` now points at the wrong partition, giving `error: file '/vmlinuz-...' not found`. `search --fs-uuid` scans every visible filesystem for the recorded UUID and sets `$root` to whatever device holds it, making the entry independent of enumeration order.

**A2.6** — On UEFI you do not embed anything in a boot sector; you install `.efi` binaries onto the ESP and register an NVRAM entry. The correct procedure is `dnf reinstall grub2-efi-x64 shim-x64` (or `grub2-install --target=x86_64-efi --efi-directory=/boot/efi` on distros that still support it) plus `efibootmgr -c ...`. `grub2-install` is discouraged under Secure Boot because it would write an **unsigned** `grubx64.efi` built on the local machine; the firmware will refuse it. The signed chain is `shimx64.efi` (signed by Microsoft) → `grubx64.efi` (signed by the distro, verified by shim against its embedded certificate) → kernel (verified by GRUB). Regenerating GRUB locally breaks that chain. On RHEL/Fedora, `grub2-install` on a UEFI system exits with an explicit error for this reason.

### Block 3 — Kernel command line

**A3.1** — The **initramfs mounts the real root read-only** (`ro`) so that a filesystem that may need repair is not written to before `fsck` has a chance to run. After `switch_root`, systemd's `systemd-remount-fs.service` (ordered before `local-fs.target`) reads `/etc/fstab` and remounts `/` with the options recorded there — normally `defaults`, hence `rw`. Deleting that service or booting with a root `fstab` entry marked `ro` leaves the root read-only.

**A3.2** — Not an error; it is informational. The kernel splits its command line three ways, and this message reports the tokens **it** did not claim:
1. Tokens matching a registered kernel parameter (`root=`, `ro`, `quiet`, `nosmt`) are consumed by the kernel.
2. Remaining tokens of the form `KEY=VALUE` are placed in **init's environment**.
3. Remaining tokens **without** `=` are passed as **argv to init** (this is how `single` and `3` historically reached SysV init, and how systemd still accepts them).
`BOOT_IMAGE` is set by GRUB for informational use; `rhgb` ("Red Hat Graphical Boot") is consumed by Plymouth in userspace. Both correctly fall through to userspace.

**A3.3** —

| | `rescue.target` | `emergency.target` |
|---|---|---|
| Filesystems | All of `/etc/fstab` mounted (`local-fs.target` reached) | Only `/`, and **read-only** |
| `sysinit.target` | Ran (udev, tmpfiles, journal, LVM/crypt) | Did **not** run |
| Services | None beyond sysinit; single root shell | None at all |
| Alias | `runlevel1.target`, `single`, `1`, `s` | `-b` / `emergency` |

For a **bad `/etc/fstab`**, use `emergency.target`: `rescue.target` depends on `local-fs.target`, which is exactly what the broken entry breaks, so rescue mode will fail the same way the normal boot did.

**A3.4** —
```bash
mount -o remount,rw /
mount -t proc  proc  /proc
mount -t sysfs sys   /sys
mount -t devtmpfs dev /dev      # only if /dev is empty
passwd root
touch /.autorelabel             # SELinux systems
sync
mount -o remount,ro /
exec /usr/lib/systemd/systemd   # or: exec /sbin/init
```
`exec` is essential: systemd must become **PID 1**, and `exec` replaces the shell's process image rather than forking a child. Without `/proc` mounted, `passwd` and most utilities misbehave. `sync` + remount-ro before handing over guards against losing the write.

**A3.5** — `systemctl isolate rescue.target` executes **immediately on the running system**: it stops every unit not required by rescue mode, including `sshd.service` and your own login session, so you disconnect yourself mid-command with no console access. `systemd.unit=rescue.target` only takes effect **on the next boot**, is one-shot (not persisted anywhere), and requires you to already have physical or out-of-band console access to use — which is precisely the access you need for rescue mode anyway. It also fails safe: if you cannot reach the console, you simply reboot normally.

**A3.6** — Most to least robust:
1. **`root=UUID=8f2c...`** — the identifier is stored inside the filesystem superblock and travels with the data across cloning, re-partitioning and controller changes. (`root=LABEL=` and `root=PARTUUID=` are comparable; `PARTUUID` lives in the partition table, so it survives a `mkfs` but not a re-partition.)
2. **`root=/dev/mapper/fedora-root`** — a device-mapper name, stable as long as the VG/LV names are stable, but it depends on the initramfs assembling LVM first (`rd.lvm.lv=`) and collides if you attach another disk whose VG is also named `fedora`.
3. **`root=/dev/sda2`** — kernel device names are assigned in **probe order**, which is asynchronous and not guaranteed stable. Concrete failure: you add a second SATA disk (or the SAS HBA enumerates faster on a cold boot than a warm one), the old `/dev/sda` becomes `/dev/sdb`, and the kernel panics with `VFS: Unable to mount root fs on unknown-block(8,2)` — or, far worse, mounts a *different* filesystem that happens to sit at `sda2` on the new disk.

### Block 4 — initramfs

**A4.1** — Mandatory when the root filesystem cannot be reached by built-in kernel code alone:
- Root on **LVM** (needs `lvm vgchange -ay` in userspace before the device node exists).
- Root on **software RAID** (`mdadm --assemble`) or **LUKS** (`cryptsetup luksOpen`, plus passphrase prompt).
- Root on **network storage** — NFS, iSCSI, FCoE, NBD — requiring a configured network stack.
- Root filesystem driver or storage-controller driver built as a **module** (`=m`) rather than built-in (`=y`) — the overwhelmingly common case in distribution kernels, which is why every distro ships an initramfs.
- Root needing a userspace helper before mount: Btrfs multi-device scan, ZFS pool import, `systemd-fsck` on a dirty root.

Not needed when: a monolithic custom kernel with the disk controller and filesystem compiled in (`=y`), root on a plain partition, `root=/dev/sda2` — e.g. embedded and appliance builds. This is what `CONFIG_BLK_DEV_INITRD=n` builds do.

**A4.2** — After decompressing and extracting the cpio archive into a **tmpfs that becomes the initial rootfs**, the kernel executes **`/init`** (configurable with `rd.init=` / historically `init=` for initrd). Here `/init` is a symlink to systemd, so systemd runs in "initrd mode" (`systemd --system` with `initrd.target` as default). Once the real root is mounted at `/sysroot`, the transition is **`switch_root`** — a `pivot_root`-plus-cleanup operation implemented by `systemd-shutdown`/`initrd-switch-root.service`: it moves `/proc`, `/sys`, `/dev`, `/run` into `/sysroot`, makes `/sysroot` the new `/`, deletes the old rootfs contents to free the tmpfs RAM, and `exec`s the real `/sbin/init` — keeping **PID 1**. (Note the terminology distinction: `initrd` was a *block device* image requiring `pivot_root`; `initramfs` is a *cpio into tmpfs* using `switch_root`. Filenames still say "initrd" for historical reasons.)

**A4.3** — CPU **microcode** must be applied by the kernel very early — before SMP bring-up and before the compression code for the main archive has necessarily been exercised, and critically before erratum-affected instructions are used. The kernel therefore looks for an **uncompressed cpio archive concatenated at the front** of the initramfs file, with the microcode at the fixed path `kernel/x86/microcode/GenuineIntel.bin` (or `AuthenticAMD.bin`). Keeping it uncompressed and first means the early-boot code can find and load it with a trivial cpio walk, with no decompressor involved. `skipcpio` (step 23) exists precisely to skip past this section so you can decompress the real archive behind it.

**A4.4** — The initramfs was built **host-only** (`hostonly=yes`, the distro default): it contains just the drivers and configuration for the storage layout that existed at build time, including the specific `rd.lvm.lv=` set. It has no knowledge of the new VG, so `dracut-initqueue` waits for a device that never appears and times out after 180 s. Fix: rebuild it — `sudo dracut --force /boot/initramfs-$(uname -r).img $(uname -r)` — and ensure the `options` line carries `rd.lvm.lv=<newvg>/<newlv>`. Recover in the meantime by booting the `0-rescue` entry, whose image is built `--no-hostonly` and contains everything. Debian/Ubuntu: `update-initramfs -u -k all`.

**A4.5** — `chroot` itself does not need `rw`, but everything you want to *do* inside it does: `passwd` rewrites `/etc/shadow`, and on a read-only mount it fails with `Authentication token manipulation error`. `/sysroot` is read-only because the initramfs deliberately mounts the real root `ro` (see A3.1) and `rd.break` stops before the remount ever happens.

`touch /.autorelabel` is needed because on SELinux systems a file created or replaced from within the initramfs chroot may receive a **wrong or missing security context** — the chroot's policy state is not the target system's. `/etc/shadow` with the wrong label makes `login`/`sshd` unable to read it, and the system becomes unloginable after "successfully" resetting the password. The flag file triggers a full filesystem relabel on the next boot (slow, but correct). The surgical alternative is `restorecon -v /etc/shadow` from inside the chroot, if the policy tools are available.

**A4.6** — Plain `rd.break` is equivalent to `rd.break=pre-pivot`: it stops **after** the real root has been mounted at `/sysroot` and after the cleanup hooks, immediately before `switch_root`. `rd.break=pre-mount` stops **before** the root is mounted — `/sysroot` exists but is empty. So `/sysroot` is populated only in the plain `rd.break` case; that is why password-reset procedures use plain `rd.break`. `pre-mount` is the right breakpoint for debugging device assembly (LVM not activating, LUKS not opening), where you want to run `lvm vgchange -ay` or `cryptsetup` by hand. Other stages: `cmdline`, `pre-udev`, `pre-trigger`, `initqueue`, `mount`, `cleanup`.

### Block 5 — PID 1

**A5.1** —
- `--switched-root`: this systemd instance did **not** start directly from the kernel; it was `exec`'d after `switch_root` from an earlier systemd running in the initramfs. Its absence would mean either no initramfs or a non-systemd initramfs.
- `--system`: it is the **system** manager (PID 1, managing system units), not a per-user `--user` instance.
- `--deserialize 31`: state was **serialized to file descriptor 31** by the initramfs instance and restored by this one. This is how systemd carries unit state, open sockets and job queues across the root transition without losing them — the same mechanism used by `systemctl daemon-reexec`.

**A5.2** — From the **target that is currently active**, mapped backwards through the `runlevelN.target` alias symlinks: `multi-user.target` ⇒ `3`, `graphical.target` ⇒ `5`, `rescue.target` ⇒ `1`. systemd also maintains `/run/utmp` records so `runlevel`, `who -r` and `telinit` keep working. The **`N`** in the first column means the **previous** runlevel is `N` = *None* — the system has not changed runlevel since boot. After a `telinit 5` you would see `3 5`.

**A5.3** —
- **`S`** = *Start*: `/etc/rc.d/rc 3` invokes the script as `/etc/init.d/sshd **start**`.
- **`K`** = *Kill*: invoked as `/etc/init.d/certmonger **stop**`.
- The **two digits** are a sort key. `rc` runs all `K??*` scripts first, in ascending numeric order, then all `S??*` scripts, in ascending numeric order — a plain `LC_ALL=C` sort of the filenames. So `S10network` starts before `S12rsyslog`, which starts before `S55sshd`. The numbers *are* the entire dependency system: there is no declared dependency graph, only a hand-maintained total order. This is why adding a service correctly requires knowing what everything else is numbered — and why `chkconfig` reads the `# chkconfig: 2345 55 25` header comment in the script to pick the numbers.

**A5.4** — `blame` reports each unit's **individual duration**, sorted descending, with no regard for whether the unit was on the **critical path**. A unit can take 5.4 s while running fully in parallel with the rest of the boot, contributing nothing to wall-clock time; conversely a 120 ms unit that everything waits on is the real bottleneck. The correct tool is **`systemd-analyze critical-chain`**, which walks the actual `After=`/`Requires=` chain from the default target and prints `@` (time the unit became active) and `+` (time it took). `systemd-analyze plot > boot.svg` shows the same information graphically, including overlap. In practice `NetworkManager-wait-online.service` *is* usually on the critical path (`network-online.target` is ordered before `multi-user.target` when anything pulls it in), so this particular case may well be real — but `blame` alone does not establish it.

**A5.5** —
1. **Declarative dependencies vs implicit ordering.** A unit states `After=`, `Requires=`, `Wants=`, `Before=`; systemd builds a dependency *graph* and can run every independent branch concurrently. SysV encodes ordering only as `S10`/`S55` filename prefixes — a total order, which by definition permits no parallelism.
2. **Readiness protocol.** A unit declares `Type=notify` / `Type=forking` / `Type=dbus`, so systemd knows *when* the service is genuinely ready and can release dependents at that exact moment. A SysV script returns from `start` and the next script runs; there is no readiness signal, so scripts insert `sleep`s and polling loops.
3. **Socket / bus activation and lazy start.** systemd can create the listening socket at `sockets.target` and start the daemon only when the first connection arrives, which removes the ordering constraint entirely — a client can connect before the server exists and simply block on the socket. SysV has no equivalent; a client must be ordered after its server.
(A fourth, structurally important: units are *data* parsed by PID 1, not shell scripts forked by it, so systemd can reason about them — `systemd-analyze verify`, dependency queries, resource limits, cgroup-based process tracking.)

**A5.6** — Runlevel-based ordering is replaced by **targets** (`multi-user.target`, `graphical.target`) combined with declarative `WantedBy=`/`After=` in the `[Install]` and `[Unit]` sections; event-driven starts are covered by **socket, path, device, timer and D-Bus activation** units. The equivalent of `initctl list` is **`systemctl list-units`** (add `--type=service --all` for the closest match); `initctl start/stop/status foo` maps to `systemctl start/stop/status foo.service`.

**A5.7** — The `firmware` and `loader` figures come from **UEFI variables** written by a boot loader that implements the systemd Boot Loader Interface: `LoaderTimeInitUSec`, `LoaderTimeExecUSec` and `LoaderTimeMenuUSec` in the vendor namespace `4a67b082-0a4c-41cf-b6c7-440b29bb8c4f`. **`systemd-boot`** sets them; **GRUB does not**, and legacy BIOS has no mechanism to. So on a GRUB or BIOS system `systemd-analyze` legitimately reports only `kernel + initrd + userspace`, and total boot time as measured from the power button is higher than the number printed.

### Block 6 — Boot logs

**A6.1** — The journal has, structurally, what the ring buffer cannot:
- **Persistence across reboots** (`/var/log/journal`), letting you read `-b -1`. The ring buffer is volatile kernel memory, wiped by every boot, and overwritten in place once full (`dmesg -c` / `--read-clear` even drains it deliberately).
- **Structured metadata and non-kernel sources.** Journal entries carry `_PID`, `_UID`, `_SYSTEMD_UNIT`, `_BOOT_ID`, `_COMM`, `_SELINUX_CONTEXT`, `_TRANSPORT`, and cover userspace services, not just the kernel. `dmesg` has severity + facility + timestamp and nothing else.
(Also: cryptographic sealing with `journalctl --setup-keys`, and rate-limiting/vacuum policy.)

What `dmesg` gives you regardless: it reads `/dev/kmsg` (or the `klogctl` syscall) **directly from the kernel**, so it works when journald has crashed, is not installed (SysVinit systems, containers, minimal initramfs), or before journald starts. In `dracut:/#` emergency shells `dmesg` works and `journalctl` may not.

**A6.2** — Ring-buffer timestamps are **monotonic** — nanoseconds since kernel start, taken from a clock that does not follow wall-clock adjustments and that **is suspended across suspend/resume**. `dmesg -T` converts them by subtracting the monotonic offset from the *current* wall-clock time. If the system clock was stepped since boot (NTP synchronizing after boot, an RTC in the wrong timezone, a VM resumed from a snapshot) or if the machine suspended, every converted timestamp is wrong by that drift — the man page documents it as "inaccurate". Avoid it by reading the journal instead: `journalctl -k -o short-precise` records both the monotonic *and* the realtime clock per entry, so the correlation is stored at write time rather than reconstructed after the fact.

**A6.3** — With `Storage=auto` (the default), journald writes to disk **only if `/var/log/journal` already exists**; otherwise it writes to `/run/log/journal`, which is a **tmpfs** and is destroyed at every reboot. So a fresh install with no `/var/log/journal` directory retains only the current boot, and `--list-boots` shows exactly index `0`. Fix by creating the directory (`mkdir -p /var/log/journal; systemd-tmpfiles --create --prefix /var/log/journal; systemctl restart systemd-journald`) or by setting `Storage=persistent` in `/etc/systemd/journald.conf`, which makes journald create the directory itself. Note that Debian/Ubuntu ship `/var/log/journal` present by default, Fedora/RHEL do too since F30 — but minimal and container images frequently do not.

**A6.4** —
```bash
journalctl -k -b -2 -p warning -o short-precise
```
`-k` restricts to kernel messages (`_TRANSPORT=kernel`), `-b -2` selects the boot two before the current one, `-p warning` matches priority ≤ 4, i.e. warning **and everything more severe** (err, crit, alert, emerg), and `-o short-precise` prints microsecond-resolution timestamps. (`-p warning..emerg` would be an explicit equivalent range.)

**A6.5** — With `kernel.dmesg_restrict = 1`, the `klogctl`/`/dev/kmsg` read operations are denied to unprivileged users, so `dmesg` as a normal user fails with `dmesg: read kernel buffer failed: Operation not permitted`. The rationale is that the ring buffer leaks kernel addresses, hardware topology and timing useful for exploitation. The capability that overrides it is **`CAP_SYSLOG`** (historically `CAP_SYS_ADMIN`, still accepted with a deprecation warning). Grant it narrowly with `setcap cap_syslog+ep /usr/bin/dmesg` rather than setting the sysctl to 0. Note that `journalctl -k` for a normal user is governed separately — by membership in the `systemd-journal`, `adm` or `wheel` groups via the ACLs on `/var/log/journal`.

**A6.6** — Two plausible reasons:
1. The unit was **restarted successfully** in the meantime — by `Restart=on-failure` with a `RestartSec=` backoff, by a `.timer`, or by a dependent unit — and `systemctl reset-failed` is implicit on a successful start, so it left the failed list.
2. Someone (or a `systemctl daemon-reload` + `reset-failed`, or a configuration-management run) explicitly cleared it, or the unit was stopped/disabled and is now `inactive (dead)` rather than `failed`.

The command that settles it, because the journal is the durable record:
```bash
journalctl -b -u <unit> --no-pager
```
and more broadly `journalctl -b -p err` for the whole boot, or `journalctl -b _SYSTEMD_UNIT=<unit>` to catch messages the unit's own processes emitted. `systemctl show <unit> -p NRestarts,ExecMainStartTimestamp,Result` confirms the restart hypothesis directly.

### Block 7 — Diagnostics

**A7.1** — systemd's **`fstab-generator`** turns every `/etc/fstab` line into a `.mount` unit and, by default, adds `RequiredBy=local-fs.target`. `local-fs.target` is `Requires=`-d by `sysinit.target`, which everything else is ordered after — so one failed mount fails `local-fs.target`, which fails the transaction, and systemd falls back to `emergency.target`. Whether anything *uses* `/data` is irrelevant; the dependency is on the mount succeeding, not on the data.

The two options:
- **`nofail`** — the generator emits `WantedBy=` instead of `RequiredBy=`. The mount is still attempted, but its failure does not propagate: the boot continues with `/data` unmounted. This addresses the *failure*.
- **`x-systemd.device-timeout=5s`** — caps how long systemd waits for the **backing device** to appear before giving up (default 90 s). This addresses the *90-second stall*, which `nofail` alone does not: without it, `nofail` still waits the full default timeout before deciding to give up.

Both are needed for the observed symptom. Related: `noauto` (do not mount at boot at all) and `x-systemd.automount` (mount lazily on first access).

**A7.2** — `sulogin` (which is what `emergency.service`/`rescue.service` run as their `ExecStart`) reads `/etc/shadow` for root. Behaviour depends on the build and configuration:
- If root's hash field is `!` or `!!` (**locked**, the Ubuntu/cloud-image default), stock `sulogin` refuses the login and prints `Cannot open access to console, the root account is locked.` followed by a reboot loop or an immediate exit — you cannot get a shell.
- If the field is `*` or empty, behaviour varies; `sulogin --force` (used by systemd when `SYSTEMD_SULOGIN_FORCE=1` is set) grants a root shell **without any password**, which is why that variable is a security-relevant setting on physically accessible machines.

Remaining recovery paths, in order of preference:
1. Reboot, edit the GRUB entry, append **`rd.break`** (Block 4 step 25) or **`init=/bin/bash`** (A3.4) — both bypass `sulogin` entirely because they act before or instead of systemd's userspace.
2. If GRUB itself is password-protected (`superusers` in `/etc/grub.d/01_users`), boot **external media** (distro live ISO / installer rescue mode), then `mount` the root filesystem, `chroot` into it, and repair.
3. On a VM, attach the disk to another instance and repair it out-of-band.

The general lesson: `sulogin`'s locked-root refusal is not a security boundary against someone with console access — GRUB password + firmware password + disk encryption are. It only stops the trivially lazy path.

**A7.3** — Because `/etc/fstab` is **not read at runtime by systemd**; it is compiled into `.mount` units at each reload by `systemd-fstab-generator`, one of the generators under `/usr/lib/systemd/system-generators/`. Until `daemon-reload` runs, the in-memory unit set still reflects the old file — so `systemctl start data.mount` would use the stale definition, and `mount -a` would use the new file, giving you two divergent views. `systemctl daemon-reload` re-runs **all** generators and re-parses every unit. (`systemd-analyze verify /etc/fstab` will also flag syntax problems before you commit to a reboot.)

**A7.4** — The kernel loaded and initialized fine — GRUB's `error: file not found` applied to the **initrd** line only, and GRUB proceeded to boot the kernel without one. Without an initramfs, the kernel had no `/init` to run and no userspace to activate LVM, so `/dev/mapper/fedora-root` never came into existence. `root=` could not be resolved, the kernel had no root to mount, and with nothing left to do it panicked: `VFS: Unable to mount root fs on unknown-block(0,0)` — `(0,0)` being the null major:minor, i.e. "no device at all".

The `0-rescue` entry survives because its initramfs is a separate file (`initramfs-0-rescue-<machine-id>.img`) built with **`--no-hostonly`**: it contains every storage and filesystem module, not just the ones this host needed at install time, and it is regenerated only at install time — so it is untouched by whatever broke the regular image. That is its entire purpose.

**A7.5** — The prompt names the process that owns the shell's root filesystem:
- **`dracut:/#`** — you are still **inside the initramfs**, on the tmpfs rootfs, *before* the real root was mounted. `/sysroot` is empty. Reached because device assembly failed (7C: no such LV).
- **`switch_root:/#`** — you are still inside the initramfs, but **after** `/sysroot` was successfully mounted, at the `pre-pivot` breakpoint just before `switch_root` executes. The real root is available under `/sysroot`.

So 7C failed strictly earlier than Block 4's deliberate breakpoint: in 7C the root device was never found; in Block 4 it was found, mounted, and we simply chose to pause.

**A7.6** — Earliest to latest:

| # | Prompt | Root filesystem at that moment | Component |
|---|---|---|---|
| 1 | `grub>` | None — no Linux kernel is running at all. GRUB reads `/boot` through its own filesystem driver. | GRUB 2 |
| 2 | `dracut:/#` | The **initramfs tmpfs**; real root not mounted, `/sysroot` empty. | dracut emergency hook, inside initramfs |
| 3 | `switch_root:/#` | Still the **initramfs tmpfs**, but real root is mounted read-only at `/sysroot`. | dracut `pre-pivot` breakpoint |
| 4 | `emergency mode` (systemd) | The **real root**, mounted read-only, after `switch_root`. PID 1 is the real systemd. | systemd `emergency.target` |

The practical use of the table: the prompt tells you which layer to debug. `grub>` ⇒ bootloader/partition problem. `dracut:/#` ⇒ storage assembly (LVM/RAID/LUKS/driver) or a wrong `root=`. `switch_root:/#` ⇒ you got there on purpose, or the pivot itself failed. systemd emergency ⇒ the problem is in `/etc/fstab` or a userspace unit, and the root filesystem is fine.

### Block 8 — Consolidation

**A8.1** —

| Order | Event | Responsible component |
|---|---|---|
| 1 | **POST** | Firmware (BIOS/UEFI) — hardware self-test, device enumeration |
| 2 | **MBR/ESP read** | Firmware — reads MBR sector 0 (BIOS) or `\EFI\...\shimx64.efi` from the FAT ESP per NVRAM `BootOrder` (UEFI) |
| 3 | **GRUB `boot` command** | GRUB 2 — after loading `vmlinuz` and `initramfs` into memory and setting up the boot protocol structures |
| 4 | **Kernel decompression** | The kernel's own self-extracting stub, then early init: memory map, `Command line:`, CPU bring-up, initramfs cpio extraction into tmpfs |
| 5 | **udev coldplug** | `systemd-udevd` running **inside the initramfs**; `udevadm trigger` replays device events, loads modules, assembles LVM/MD/LUKS |
| 6 | **`initrd-parse-etc.service`** | systemd (initrd instance) — reads `/sysroot/etc/fstab` and mounts anything flagged `x-initrd.mount` (e.g. a separate `/usr`) before the pivot |
| 7 | **`switch_root`** | `initrd-switch-root.service` — real root becomes `/`, initramfs tmpfs freed, real `/sbin/init` `exec`'d as PID 1 |
| 8 | **`basic.target` reached** | systemd (system instance) — after `sysinit.target` (udev, tmpfiles, journal, fsck, local-fs, swap) and `sockets.target` |
| 9 | **`default.target` reached** | systemd — `multi-user.target` or `graphical.target`; boot is complete, `systemd-analyze` prints its total |

Note that items 5 and 6 both occur *inside* the initramfs, and that udev runs **twice** — once in the initramfs (5) and again after the pivot, as part of `sysinit.target`.

**A8.2** —
- **Intended**: `/boot/loader/entries/<machine-id>-<version>.conf` on a BLS system (its `options` line), or the corresponding `menuentry` block in `/boot/grub2/grub.cfg` on a non-BLS system. `grubby --info=DEFAULT` reads this for you.
- **Actual**: **`/proc/cmdline`** — what the kernel genuinely received, straight from the boot protocol structure. (`dmesg | grep 'Command line'` is the same string, logged.)

They disagree whenever the on-disk configuration was not what was executed:
- Someone edited the entry with `e` at the menu (one-shot, never written to disk).
- A different entry booted than the default — `grub2-reboot` set `next_entry`, or the user picked another one, or `boot_success=0` triggered the fallback logic.
- The configuration was edited **after** boot but before you looked.
- GRUB appended things the file does not contain — `BOOT_IMAGE=` is always injected by GRUB itself.
- Two configurations exist and a stale one is being read (the classic UEFI trap: editing `/boot/grub2/grub.cfg` while the firmware loads `/boot/efi/EFI/<distro>/grub.cfg`).

Reading `/proc/cmdline` first, always, is the habit that prevents an hour of debugging a file nothing is using.

**A8.3** — **Not established, and probably not 5.4 seconds.** `systemd-analyze blame` sorts by each unit's own execution time, ignoring concurrency; a unit that runs entirely in parallel with the rest of the boot can top `blame` and contribute nothing to wall clock. The tool that answers the question is:

```bash
systemd-analyze critical-chain
systemd-analyze critical-chain multi-user.target
```

If `NetworkManager-wait-online.service` appears in that chain with a large `+` value, the saving is real; if it does not appear, masking it saves nothing measurable. (`systemd-analyze plot > boot.svg` visualizes the overlap and is the most persuasive artifact for this argument.)

Two further caveats worth raising before anyone masks it:
1. `NetworkManager-wait-online.service` exists to make `network-online.target` meaningful. Masking it does not remove the dependency — it makes `network-online.target` reachable **immediately**, so units that legitimately need a configured network (NFS mounts, `rsyslog` with a remote target, an application that binds a specific address) now start before it exists and fail intermittently. You convert a deterministic 5.4 s delay into a non-deterministic race.
2. The honest fix is usually to make it faster rather than absent: `nm-online -x` semantics via `NM_ONLINE_TIMEOUT`, `systemctl edit NetworkManager-wait-online.service` to lower the timeout, disabling DHCP on interfaces that have none, or removing `network-online.target` from units that do not actually need it.
