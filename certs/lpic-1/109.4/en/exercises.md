# LPIC-1 109.4 — Configure Client Side DNS

## Guided Exercises (Exam 102-500, v5.0)

**What you will be able to do when you finish:** read the whole client-side name resolution stack of a Linux host, predict what a given lookup will do *before* running it, change the resolver deliberately (and make the change survive a reboot), and diagnose a broken client with free, non-guessing tools.

---

### Environment and safety

These exercises **modify `/etc/hosts`, `/etc/resolv.conf` and `/etc/nsswitch.conf`**. Use a throwaway VM or container, never a workstation you need working, and never a server. Every destructive block ends with a restore step.

```bash
# Prerequisites — install once
# Debian/Ubuntu
sudo apt-get install -y dnsutils bind9-host iproute2 tcpdump
# RHEL/Fedora/Rocky
sudo dnf install -y bind-utils iproute tcpdump
# openSUSE
sudo zypper install -y bind-utils iproute2 tcpdump
```

Take a snapshot of the three files before you start. You will restore from this in Exercise 9:

```bash
sudo mkdir -p /root/109.4-backup
sudo cp -av /etc/hosts /etc/nsswitch.conf /root/109.4-backup/
sudo cp -av --no-dereference /etc/resolv.conf /root/109.4-backup/
```

> `--no-dereference` matters: on most modern systems `/etc/resolv.conf` is a **symlink**, and a plain `cp` would silently copy the target and destroy the evidence of what managed it.

> **Container caveat:** inside Docker/Podman, `/etc/resolv.conf` and `/etc/hosts` are bind-mounted from the host and may be read-only or reverted on restart. If `sed -i` fails with `Device or resource busy`, you are in a container — use a full VM for Exercises 3, 4 and 9.

## Exercise 1 — Map the resolution stack before you touch it

The single most common client-DNS mistake is editing `/etc/resolv.conf` on a host where nothing reads it. Establish the ground truth first.

1. Find out who answers `hosts` lookups, and in what order:

   ```bash
   grep '^hosts:' /etc/nsswitch.conf
   ```

   ```
   # representative output (yours will differ by distro)
   hosts:      files resolve [!UNAVAIL=return] myhostname dns
   ```

2. Determine whether `/etc/resolv.conf` is a real file or a symlink, and who owns it:

   ```bash
   ls -l /etc/resolv.conf
   ```

   ```
   # possibility A — managed by systemd-resolved (stub)
   lrwxrwxrwx 1 root root 39 Aug 12 09:11 /etc/resolv.conf -> ../run/systemd/resolve/stub-resolv.conf
   # possibility B — a plain file written by NetworkManager, dhclient or a human
   -rw-r--r-- 1 root root 112 Aug 12 09:11 /etc/resolv.conf
   ```

3. Read it, including the comment header — managers announce themselves there:

   ```bash
   cat /etc/resolv.conf
   ```

   ```
   # Generated by NetworkManager
   search corp.example.net
   nameserver 192.168.178.1
   ```

4. Check whether a local caching stub is listening:

   ```bash
   sudo ss -lnup 'sport = :53'; sudo ss -lntp 'sport = :53'
   systemctl is-active systemd-resolved 2>/dev/null || echo "systemd-resolved not present/active"
   ```

5. If `systemd-resolved` is active, get its real view of the world — this, not `resolv.conf`, is authoritative on such a host:

   ```bash
   resolvectl status
   ```

   ```
   Global
            Protocols: LLMNR=resolve -mDNS -DNSOverTLS DNSSEC=no/unsupported
     resolv.conf mode: stub

   Link 2 (enp1s0)
       Current Scopes: DNS LLMNR/IPv4
            Protocols: +DefaultRoute +LLMNR -mDNS -DNSOverTLS DNSSEC=no/unsupported
     Current DNS Server: 192.168.178.1
            DNS Servers: 192.168.178.1
             DNS Domain: corp.example.net
   ```

6. Record the two possible sources of truth side by side:

   ```bash
   for f in /etc/resolv.conf /run/systemd/resolve/stub-resolv.conf /run/systemd/resolve/resolv.conf; do
     printf '\n===== %s =====\n' "$f"; cat "$f" 2>/dev/null || echo "(absent)"
   done
   ```

**Check your understanding**

- **Q1.** On a host where `/etc/resolv.conf` is a symlink to `stub-resolv.conf` and contains `nameserver 127.0.0.53`, which process actually sends the UDP packet to the upstream DNS server?
- **Q2.** What is the practical difference between `/run/systemd/resolve/stub-resolv.conf` and `/run/systemd/resolve/resolv.conf`, and when would you deliberately symlink `/etc/resolv.conf` to the second one?
- **Q3.** Your `hosts:` line reads `files resolve [!UNAVAIL=return] myhostname dns`. `systemd-resolved` is running and returns NXDOMAIN for `db01.corp.example.net`. Is the `dns` source consulted afterwards? Explain the `[!UNAVAIL=return]` syntax precisely.
- **Q4.** Why is `resolvectl status` a better first command than `cat /etc/resolv.conf` on a systemd host?

## Exercise 2 — `/etc/hosts` and the NSS order

`/etc/hosts` is a static database, not a cache. It has no TTL, no negative answers, and it wins over DNS whenever `files` precedes `dns`.

1. Inspect the current file. Note the mandatory loopback entries:

   ```bash
   cat /etc/hosts
   ```

   ```
   127.0.0.1   localhost
   ::1         localhost ip6-localhost ip6-loopback
   127.0.1.1   lab01.corp.example.net lab01
   ```

2. Add a test record with a canonical name and two aliases. The format is `IP  canonical-name  [alias ...]`, whitespace-separated:

   ```bash
   printf '203.0.113.10\tapp1.lab.internal\tapp1\tdeploy\n' | sudo tee -a /etc/hosts
   ```

3. Resolve it through the C library, not through DNS:

   ```bash
   getent hosts app1.lab.internal
   getent hosts deploy
   ```

   ```
   203.0.113.10    app1.lab.internal app1 deploy
   203.0.113.10    app1.lab.internal app1 deploy
   ```

4. Now ask DNS directly for the same name and compare:

   ```bash
   host app1.lab.internal
   ```

   ```
   Host app1.lab.internal not found: 3(NXDOMAIN)
   ```

5. Prove that order in the file matters. Add a second, conflicting line and query again:

   ```bash
   printf '203.0.113.99\tapp1.lab.internal\n' | sudo tee -a /etc/hosts
   getent hosts app1.lab.internal
   getent ahosts app1.lab.internal
   ```

6. Prove that order in `nsswitch.conf` matters. Shadow a real public name locally:

   ```bash
   printf '203.0.113.55\twww.iana.org\n' | sudo tee -a /etc/hosts
   getent hosts www.iana.org     # → 203.0.113.55 (files wins)
   host www.iana.org             # → the real address (DNS, unaffected)
   ```

7. Temporarily invert the order and observe the change:

   ```bash
   sudo cp /etc/nsswitch.conf /etc/nsswitch.conf.bak
   sudo sed -i 's/^hosts:.*/hosts: dns files/' /etc/nsswitch.conf
   getent hosts www.iana.org     # → now the real address
   getent hosts app1.lab.internal
   ```

8. Restore, then clean up the test records:

   ```bash
   sudo mv /etc/nsswitch.conf.bak /etc/nsswitch.conf
   sudo sed -i '/lab.internal/d; /203.0.113.55/d' /etc/hosts
   getent hosts app1.lab.internal; echo "exit=$?"
   ```

**Check your understanding**

- **Q5.** In step 5, `getent hosts app1.lab.internal` returned only `203.0.113.10` even though two lines matched. Why, and what did `getent ahosts` show instead?
- **Q6.** After step 7 (`hosts: dns files`), a name present only in `/etc/hosts` still resolved. Did anything get *slower*? What is the cost of putting `dns` first?
- **Q7.** A colleague adds `10.0.0.5 db01` to `/etc/hosts` on 300 servers to "pin" a database. Give two concrete production failure modes this creates that a DNS record with a short TTL would not.
- **Q8.** Which of these does `/etc/hosts` support: TTLs, wildcards (`*.lab.internal`), CNAMEs, MX records, IPv6 addresses, multiple addresses for one name?

## Exercise 3 — `/etc/resolv.conf`: `nameserver`, `search`, `domain`, `ndots`

This block requires a host whose `/etc/resolv.conf` is a **real file** you may edit. If it is a symlink to `stub-resolv.conf`, either do this exercise in a plain VM without `systemd-resolved`, or temporarily replace the symlink and restore it in Exercise 9.

1. Write a controlled resolver configuration:

   ```bash
   sudo cp --no-dereference /etc/resolv.conf /etc/resolv.conf.109-4 2>/dev/null
   sudo rm -f /etc/resolv.conf
   sudo tee /etc/resolv.conf >/dev/null <<'EOF'
   nameserver 9.9.9.9
   nameserver 1.1.1.1
   search lab.internal corp.example.net
   options ndots:1 timeout:2 attempts:1
   EOF
   ```

2. Confirm the search list is actually applied. Watch the wire while resolving a short name:

   ```bash
   sudo timeout 6 tcpdump -ni any -c 6 'udp port 53' &
   sleep 1
   getent ahosts www >/dev/null 2>&1
   wait
   ```

   You should see queries for `www.lab.internal` and `www.corp.example.net` before (or instead of) `www.`.

3. Demonstrate `ndots` with a name that contains one dot:

   ```bash
   sudo sed -i 's/^options.*/options ndots:1 timeout:2 attempts:1/' /etc/resolv.conf
   sudo timeout 6 tcpdump -ni any -c 4 'udp port 53' & sleep 1
   getent ahosts www.iana >/dev/null 2>&1; wait
   ```

   With `ndots:1`, `www.iana` has ≥ 1 dot, so it is tried **absolute first**.

4. Now raise `ndots` and repeat — this is the configuration that makes Kubernetes clusters generate four useless queries per lookup:

   ```bash
   sudo sed -i 's/^options.*/options ndots:5 timeout:2 attempts:1/' /etc/resolv.conf
   sudo timeout 8 tcpdump -ni any -c 8 'udp port 53' & sleep 1
   getent ahosts www.iana >/dev/null 2>&1; wait
   ```

   Now `www.iana` (1 dot < 5) goes through the **search list first**: `www.iana.lab.internal`, `www.iana.corp.example.net`, and only then `www.iana.`.

5. Show the escape hatch — the trailing dot makes a name fully qualified and suppresses the search list entirely:

   ```bash
   sudo timeout 6 tcpdump -ni any -c 4 'udp port 53' & sleep 1
   getent ahosts www.iana.org. >/dev/null 2>&1; wait
   ```

6. Show that `search` and `domain` are mutually exclusive and last-one-wins:

   ```bash
   sudo tee /etc/resolv.conf >/dev/null <<'EOF'
   nameserver 9.9.9.9
   domain corp.example.net
   search lab.internal
   options ndots:1
   EOF
   sudo timeout 6 tcpdump -ni any -c 4 'udp port 53' & sleep 1
   getent ahosts www >/dev/null 2>&1; wait
   ```

7. Override the file without editing it, using the glibc environment variables:

   ```bash
   LOCALDOMAIN="example.org" getent ahosts www
   RES_OPTIONS="ndots:5 timeout:1" getent ahosts www.iana
   ```

8. Test the documented hard limit on nameservers:

   ```bash
   sudo tee /etc/resolv.conf >/dev/null <<'EOF'
   nameserver 192.0.2.1
   nameserver 192.0.2.2
   nameserver 192.0.2.3
   nameserver 9.9.9.9
   options timeout:1 attempts:1
   EOF
   time getent ahosts www.iana.org; echo "exit=$?"
   ```

**Check your understanding**

- **Q9.** In step 8, the only working resolver is the fourth entry. Did the lookup succeed? What is `MAXNS` and where is it defined?
- **Q10.** Explain the `ndots` rule in one sentence, in terms of "dots in the queried name" vs "search list first or absolute first".
- **Q11.** A microservice calls `http://payments.svc/health` and the platform sets `ndots:5` with four search domains. How many DNS queries does one failed A lookup generate on a dual-stack host, and what one-character change to the hostname eliminates them?
- **Q12.** In step 6, which suffix was actually appended, `corp.example.net` or `lab.internal`? State the rule for `domain` vs `search` appearing in the same file.
- **Q13.** `LOCALDOMAIN` and `RES_OPTIONS` are per-process overrides. Name one legitimate operational use and one reason they are useless for a daemon started by systemd unless you take an extra step.

## Exercise 4 — Failure behaviour: `timeout`, `attempts`, `rotate`, `single-request`

Client DNS problems are almost never "cannot resolve". They are "resolves, but takes 10 seconds", which the application reports as an unrelated timeout.

1. Point the resolver at a blackhole address (TEST-NET-1 is guaranteed unroutable) and measure the default cost of failure:

   ```bash
   sudo tee /etc/resolv.conf >/dev/null <<'EOF'
   nameserver 192.0.2.1
   nameserver 192.0.2.2
   EOF
   time getent ahosts www.iana.org; echo "exit=$?"
   ```

   Record the wall-clock time. This is the stall your application inherits, per lookup, with the **defaults** (`timeout:5`, `attempts:2`).

2. Now bound it explicitly and measure again:

   ```bash
   sudo tee /etc/resolv.conf >/dev/null <<'EOF'
   nameserver 192.0.2.1
   nameserver 192.0.2.2
   options timeout:1 attempts:1
   EOF
   time getent ahosts www.iana.org; echo "exit=$?"
   ```

3. Measure the "one dead server in front of a good one" case — the realistic outage:

   ```bash
   sudo tee /etc/resolv.conf >/dev/null <<'EOF'
   nameserver 192.0.2.1
   nameserver 9.9.9.9
   options timeout:1 attempts:1
   EOF
   time getent ahosts www.iana.org
   time getent ahosts www.kernel.org
   ```

   Note that **every** lookup pays the dead-server penalty: glibc's stub is stateless and always starts at the first entry.

4. Add `rotate` and observe the difference in the query source distribution:

   ```bash
   sudo sed -i 's/^options.*/options timeout:1 attempts:1 rotate/' /etc/resolv.conf
   sudo timeout 10 tcpdump -ni any -c 10 'udp port 53' & sleep 1
   for n in a b c d e; do getent ahosts $n.iana.org >/dev/null 2>&1; done
   wait
   ```

5. Observe the dual-stack query pattern that `single-request` exists to fix:

   ```bash
   sudo tee /etc/resolv.conf >/dev/null <<'EOF'
   nameserver 9.9.9.9
   options timeout:1 attempts:1
   EOF
   sudo timeout 6 tcpdump -ni any -c 4 -v 'udp port 53' & sleep 1
   getent ahosts www.iana.org >/dev/null; wait
   ```

   Two queries (A and AAAA) leave **in parallel from the same source port**.

6. Serialise them:

   ```bash
   sudo sed -i 's/^options.*/options timeout:1 attempts:1 single-request/' /etc/resolv.conf
   sudo timeout 6 tcpdump -ni any -c 4 -v 'udp port 53' & sleep 1
   getent ahosts www.iana.org >/dev/null; wait
   ```

7. Force TCP and confirm on the wire:

   ```bash
   sudo sed -i 's/^options.*/options timeout:1 attempts:1 use-vc/' /etc/resolv.conf
   sudo timeout 6 tcpdump -ni any -c 4 'port 53' & sleep 1
   getent ahosts www.iana.org >/dev/null; wait
   ```

**Check your understanding**

- **Q14.** Compare your measured times from steps 1 and 2. What are the default values of `timeout` and `attempts`, and what are their maximums?
- **Q15.** Step 3 shows that a *working* secondary does not make the client fast. Explain why, and name the mechanism (not in `resolv.conf`) that actually solves this in production.
- **Q16.** What exact symptom does `single-request` fix, and why does `single-request-reopen` exist as a separate, weaker option?
- **Q17.** A user reports "the site loads after about 10 seconds, every time, but eventually works". Which single `resolv.conf` symptom does this fingerprint, and what is the first command you run to confirm it?
- **Q18.** Why is `options use-vc` a poor permanent choice, and what legitimate diagnostic use does it have?

## Exercise 5 — `host` and `dig` as DNS-only probes

Both tools read `/etc/resolv.conf` **only to find a server address**. Neither consults `/etc/hosts` or `/etc/nsswitch.conf`. That property is exactly what makes them diagnostic tools.

1. Restore a working resolver first:

   ```bash
   sudo tee /etc/resolv.conf >/dev/null <<'EOF'
   nameserver 9.9.9.9
   options timeout:2 attempts:1 edns0
   EOF
   ```

2. Basic forward and reverse lookups with `host`:

   ```bash
   host www.iana.org
   host -t MX iana.org
   host -t NS iana.org
   host -t TXT iana.org
   host -t SOA iana.org
   host 8.8.8.8
   ```

   ```
   # representative
   www.iana.org has address 192.0.43.8            # the real address will differ — do not memorise it
   iana.org mail is handled by 10 mail.iana.org.
   8.8.8.8.in-addr.arpa domain name pointer dns.google.
   ```

3. The same with `dig`, plus the parts `host` hides:

   ```bash
   dig iana.org A
   ```

   Read the four sections and the header flags:

   ```
   ;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 51203
   ;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1
   ```

4. Learn the output filters you will actually use:

   ```bash
   dig +short iana.org A
   dig +noall +answer iana.org ANY
   dig +noall +authority +comments example.net NS
   ```

5. Query a specific server, bypassing `resolv.conf` entirely — this is how you separate "DNS is broken" from "this client is misconfigured":

   ```bash
   dig @1.1.1.1 +short www.iana.org
   dig @9.9.9.9  +short www.iana.org
   ```

6. Ask an authoritative server directly, with recursion off:

   ```bash
   NS=$(dig +short NS iana.org | head -1)
   dig @"$NS" +norecurse iana.org SOA
   ```

   Note the missing `ra` flag and the presence of `aa` in the answer.

7. Follow the delegation chain from the root:

   ```bash
   dig +trace www.iana.org | grep -E '^\S+\s+[0-9]+\s+IN\s+(NS|A|CNAME)' | head -20
   ```

8. Reverse lookups the explicit way, and see what `-x` expands to:

   ```bash
   dig -x 9.9.9.9 +short
   dig 9.9.9.9.in-addr.arpa PTR +short
   dig -x 2620:fe::fe +short
   ```

9. Inspect DNSSEC material and measure latency:

   ```bash
   dig +dnssec +multiline iana.org SOA | head -30
   dig www.iana.org | grep -E 'Query time|SERVER|MSG SIZE'
   ```

**Check your understanding**

- **Q19.** You add `10.0.0.9 api.corp.example.net` to `/etc/hosts`. What does `host api.corp.example.net` return, and what does `curl http://api.corp.example.net` connect to? Reconcile the two.
- **Q20.** In `dig` header flags, what do `qr`, `rd`, `ra`, `aa` and `ad` mean? Which one tells you the answer came from a server authoritative for that zone?
- **Q21.** `dig example.com` returns `status: NOERROR` with `ANSWER: 0`. Is the name non-existent? What is this case called, and how does it differ from `NXDOMAIN`?
- **Q22.** Why does `dig -x 9.9.9.9` return a name while `dig 9.9.9.9` returns `NXDOMAIN` for the "name" `9.9.9.9`?
- **Q23.** What does `+trace` do differently from a normal query, and what class of problem does it find that `dig @resolver name` cannot?
- **Q24.** `dig +short www.internal.corp` returns nothing, but `getent hosts www.internal.corp` returns an address. Give two distinct explanations, both of which are common in production.

## Exercise 6 — `getent` vs `dig`: proving that NSS ≠ DNS

This is the distinction the exam tests and the one that resolves real incidents.

1. Compare the two databases explicitly:

   ```bash
   getent hosts   www.iana.org
   getent ahosts  www.iana.org
   getent ahostsv4 www.iana.org
   getent ahostsv6 www.iana.org
   ```

   ```
   # getent ahosts — one line per address, per socket type
   192.0.43.8      STREAM www.iana.org
   192.0.43.8      DGRAM
   192.0.43.8      RAW
   2001:500:88:200::8 STREAM
   ```

2. Show that `getent` obeys `/etc/hosts` and `dig` does not:

   ```bash
   printf '198.51.100.7\ttest.iana.org\n' | sudo tee -a /etc/hosts
   getent hosts test.iana.org      # 198.51.100.7
   dig +short test.iana.org        # (nothing)
   sudo sed -i '/198.51.100.7/d' /etc/hosts
   ```

3. Show the non-DNS NSS sources in action:

   ```bash
   getent hosts localhost
   getent hosts "$(hostname)"
   getent ahosts _gateway          # provided by nss-myhostname
   getent hosts _outbound 2>/dev/null || echo "(_outbound needs systemd >= 249)"
   ```

4. Confirm that `_gateway` exists nowhere in DNS or `/etc/hosts`:

   ```bash
   grep -c _gateway /etc/hosts; dig +short _gateway; ip route show default
   ```

5. Use `getent` against other NSS databases to internalise that `hosts` is just one of them:

   ```bash
   getent passwd root
   getent services 53
   getent protocols udp
   getent networks
   ```

6. Use exit codes for scripting — `getent` returns 2 when the key is not found:

   ```bash
   getent hosts definitely-not-a-real-name.invalid; echo "exit=$?"
   getent hosts www.iana.org >/dev/null; echo "exit=$?"
   ```

7. Break `nsswitch.conf` and watch `getent` and `dig` diverge:

   ```bash
   sudo cp /etc/nsswitch.conf /etc/nsswitch.conf.bak
   sudo sed -i 's/^hosts:.*/hosts: files/' /etc/nsswitch.conf
   getent hosts www.iana.org; echo "getent exit=$?"
   dig +short www.iana.org
   ping -c1 www.iana.org
   sudo mv /etc/nsswitch.conf.bak /etc/nsswitch.conf
   ```

**Check your understanding**

- **Q25.** State the one-line rule that distinguishes when to use `getent hosts` and when to use `dig`, in terms of what each proves.
- **Q26.** In step 7, `dig` worked and `getent`/`ping` failed. Which file is at fault, and why is `dig` immune to it?
- **Q27.** `getent hosts` and `getent ahosts` differ in more than formatting. Which one performs address-family selection and RFC 6724 destination-address ordering, and why does that matter on a dual-stack host?
- **Q28.** `_gateway` resolves without any DNS record and without `/etc/hosts`. Which NSS module provides it, and what else does that same module provide?
- **Q29.** A monitoring script uses `if host "$NAME" >/dev/null; then ...`. Why is this the wrong check for "can this machine reach the service", and what should it use instead?

## Exercise 7 — `systemd-resolved`: stub, per-link DNS, split DNS, cache

Skip this exercise only if `systemd-resolved` is genuinely unavailable; on most current distributions it is the resolver you will be configuring.

1. Enable and inspect it:

   ```bash
   sudo systemctl enable --now systemd-resolved
   resolvectl status --no-pager
   resolvectl --version | head -1
   ```

2. Restore the stub symlink (the supported configuration):

   ```bash
   sudo ln -sf ../run/systemd/resolve/stub-resolv.conf /etc/resolv.conf
   ls -l /etc/resolv.conf; cat /etc/resolv.conf
   ```

3. Query through `resolved`'s own API rather than through the C library, and note where the answer came from:

   ```bash
   resolvectl query www.iana.org
   ```

   ```
   www.iana.org: 192.0.43.8                       -- link: enp1s0

   -- Information acquired via protocol DNS in 41.2ms.
   -- Data is authenticated: no; Data was acquired via local or encrypted transport: no
   ```

4. Prove the cache exists by repeating the query and comparing the reported time:

   ```bash
   resolvectl query www.kernel.org | tail -3
   resolvectl query www.kernel.org | tail -3     # now "cache"
   resolvectl statistics --no-pager | sed -n '/Cache/,/^$/p'
   ```

5. Flush it and confirm the counters move:

   ```bash
   sudo resolvectl flush-caches
   resolvectl statistics --no-pager | grep -A3 'Cache'
   resolvectl query www.kernel.org | tail -2
   ```

6. Configure **per-link** DNS at runtime, which is the whole point of `resolved`:

   ```bash
   IF=$(ip -o route get 1.1.1.1 | awk '{print $5}')
   sudo resolvectl dns "$IF" 9.9.9.9 1.1.1.1
   sudo resolvectl domain "$IF" lab.internal '~corp.example.net'
   resolvectl status "$IF"
   ```

7. Read the split-DNS routing you just created:

   ```bash
   resolvectl domain
   ```

   A domain written `~corp.example.net` is a **routing-only** domain: queries for it go to this link's servers, but it is *not* appended to short names. `lab.internal` without the tilde is both a search domain and a routing domain.

8. Set a persistent global configuration:

   ```bash
   sudo mkdir -p /etc/systemd/resolved.conf.d
   sudo tee /etc/systemd/resolved.conf.d/10-lab.conf >/dev/null <<'EOF'
   [Resolve]
   DNS=9.9.9.9#dns.quad9.net 1.1.1.1
   FallbackDNS=8.8.8.8
   Domains=lab.internal ~corp.example.net
   DNSSEC=allow-downgrade
   DNSOverTLS=no
   Cache=yes
   LLMNR=no
   MulticastDNS=no
   DNSStubListener=yes
   EOF
   sudo systemctl restart systemd-resolved
   resolvectl status --no-pager | head -20
   ```

9. Exercise DNSSEC validation and the two stub listeners:

   ```bash
   resolvectl query dnssec-failed.org 2>&1 | tail -3       # expect failure when DNSSEC=yes
   sudo ss -lnup 'sport = :53' | grep -E '127.0.0.53|127.0.0.54'
   dig @127.0.0.53 +short www.iana.org
   ```

**Q1.** `systemd-resolved`. `127.0.0.53` is its **stub listener**. The application resolves through glibc → the `dns` NSS module (or `nss-resolve`) → `127.0.0.53` → `systemd-resolved`, which then applies its own per-link server list, split-DNS routing, cache and optional DNSSEC/DoT, and sends the real query upstream. The upstream server address never appears in `/etc/resolv.conf` on such a host — which is precisely why editing that file there is futile.

**Q2.** `stub-resolv.conf` contains `nameserver 127.0.0.53` plus the search domains, and routes everything through `resolved` (cache, split DNS, DNSSEC, DoT). `/run/systemd/resolve/resolv.conf` contains the **actual upstream servers** that `resolved` learned, with no stub in the path. You symlink `/etc/resolv.conf` to the latter when a workload must bypass `resolved` — for example a resolver library that mishandles the 127.0.0.53 stub, or a container runtime that copies `/etc/resolv.conf` into containers where 127.0.0.53 is a different (empty) loopback namespace. The cost is losing the cache and split-DNS routing.

**Q3.** No — `dns` is **not** consulted. `[!UNAVAIL=return]` means: for any status *other than* `UNAVAIL`, return immediately. `!` negates the status list. So `SUCCESS`, `NOTFOUND` and `TRYAGAIN` all stop the search; only `UNAVAIL` (the `resolve` module could not be reached at all, i.e. `systemd-resolved` is not running) falls through to `dns`. This is deliberate: it makes `resolved` authoritative for the answer while keeping a fallback if the daemon is down. NSS action syntax is `[STATUS=ACTION]` with statuses `success|notfound|unavail|tryagain` and actions `return|continue|merge`.

**Q4.** Because on a systemd host `/etc/resolv.conf` may be a symlink to a stub file that tells you nothing about the real upstream servers, and because per-link DNS means there is no single global answer. `resolvectl status` shows the actual servers per interface, the routing domains, the search domains, the protocols in use and the `resolv.conf mode` — the complete picture in one command.

**Q5.** `getent hosts NAME` uses the `gethostbyname2`-style path, which returns the **first matching entry** in file order and stops. `getent ahosts NAME` uses `getaddrinfo(AF_UNSPEC)` and returns all matching addresses, one line per address per socket type (`STREAM`, `DGRAM`, `RAW`), so it shows both `203.0.113.10` and `203.0.113.99`. In `/etc/hosts`, the first matching line wins for simple lookups; duplicate names across lines are a silent hazard.

**Q6.** Yes. For `localhost` in particular this is a per-process latency tax and a hard dependency on DNS availability for names that are supposed to be local. `files` before `dns` is correct on essentially every system.

**Q14.** Defaults: `timeout:5` seconds and `attempts:2` retry rounds, per `resolv.conf(5)`. Maximums: `timeout` is capped at **30** and `attempts` at **5**. **Q15.** Because glibc's stub resolver is **stateless across calls**: it always starts from the first `nameserver` in the list, so every single lookup pays the first server's full timeout before falling through to the second. The production fix is a **local caching resolver** (`systemd-resolved`, `dnsmasq`, `unbound`) which does track upstream server health and latency, or an **anycast/VIP address** in front of the resolver pool so the client only ever knows one address.

**Q16.** glibc sends the A and AAAA queries for the same name **in parallel from the same UDP source port**. Some broken firewalls, load balancers and consumer NAT devices treat the second response as a duplicate or an unsolicited packet and drop it, producing a per-lookup stall of exactly one timeout period on dual-stack hosts. `single-request` serialises the two queries (correct but doubles best-case latency). `single-request-reopen` is the weaker, faster variant: it still sends them in parallel, but if only one answer arrives it reopens a **new socket** (new source port) for the missing query — this fixes the class of middleboxes that key on the port pair while keeping the parallel fast path.

**Q33.** `DNSSEC=no` (no validation), `DNSSEC=allow-downgrade` (validate when the upstream server supports DNSSEC, silently fall back when it does not), `DNSSEC=yes` (require validation; refuse unvalidatable answers). `allow-downgrade` is pragmatic because a large fraction of real-world resolvers — hotel and captive portals, ISP CPE, corporate middleboxes — mangle or strip DNSSEC records; with `yes` those networks become entirely unusable, whereas `allow-downgrade` degrades to plain DNS instead of failing closed. The honest trade-off: `allow-downgrade` provides no security guarantee against an active attacker, since the attacker can force the downgrade.

**Q34.** `127.0.0.54` is `systemd-resolved`'s **DNS proxy stub** (systemd ≥ 249). Unlike `127.0.0.53`, which is a full local resolver applying search domains, split-DNS routing, the local cache, LLMNR/mDNS and `/etc/hosts`-adjacent behaviours, the `127.0.0.54` listener forwards queries **verbatim** to the currently configured upstream servers and returns the response essentially untouched. It exists for clients that need raw upstream DNS semantics (their own resolver logic, DNSSEC validation, or full control of the query) while still benefiting from `resolved`'s upstream selection and encrypted transports.

**Q35.** You forgot `systemctl restart systemd-resolved` (or `systemctl reload`); `resolved.conf` and its drop-ins are read at start. **Q36.** `getent hosts www.kernel.org` (or `getent ahosts`) compared against `dig +short www.kernel.org`. **Q37.** *Unreachable*: no response at all, so glibc consumes the whole `timeout × attempts × servers` budget and finally reports failure; `dig` prints `;; communications error ... timed out` and then `no servers could be reached`. This implies a routing, firewall or "server is down" problem — the fault is between you and the resolver. *Reachable but refusing*: an **immediate** response with `status: REFUSED` (or `SERVFAIL`). This implies the server is alive and reachable and has made a policy or resolution decision — usually you are not in its allowed-clients ACL, or it is not authoritative and has recursion disabled for you. The latency alone distinguishes them before you read a single flag.

**Q38.** (a) Lower `ndots` to `1` (or `2`) so that names containing a dot are tried absolutely first; (b) shorten the `search` list to the domains that are genuinely needed. A third, per-application fix is appending a trailing dot to fully qualified names. On a container platform you do not control, you cannot edit the node's `resolv.conf` — you set `dnsConfig.options` (`ndots`) and `dnsConfig.searches` in the pod specification, which is the supported per-workload override. Note that the trailing-dot fix must be verified per client library.

**Q39.** Correct line: `hosts: files dns` (or, with `systemd-resolved`: `hosts: files resolve [!UNAVAIL=return] myhostname dns`). `[NOTFOUND=return]` after `files` means "if the `files` source did not find the key, stop the whole search and return not-found" — so DNS is only ever reached when `files` returns some *other* status, which effectively never happens. `NOTFOUND` = the source worked and the key is genuinely absent. `UNAVAIL` = the source itself could not be consulted (service down, module missing). Returning on `NOTFOUND` is almost always a bug; returning on everything **except** `UNAVAIL` (`[!UNAVAIL=return]`) is the idiom you actually want when one source is meant to be authoritative with a fallback.

**Q40.** No. Flushing clears **your** cache; the record's 300 s TTL means other resolvers and clients across the fleet legitimately keep the old answer for up to five more minutes (plus any negative-caching TTL from the zone's SOA). Flushing local caches is a remediation for an unplanned change, not a substitute for TTL management. If `nscd` is the cache, `nscd -i hosts` invalidates the hosts table (and `nscd -g` shows statistics); `sssd` caches separately and needs `sss_cache`.

**Q41.** `systemd-resolved` (check `systemctl is-active systemd-resolved`, `ls -l /etc/resolv.conf`); `NetworkManager` (the `# Generated by NetworkManager` header, `nmcli general status`, the `dns=` setting in `NetworkManager.conf`); `resolvconf`/`openresolv` (`ls /etc/resolvconf/resolv.conf.d/`, `command -v resolvconf`); and the DHCP client `dhclient`/`dhcpcd` (`ps -ef | grep -E 'dhclient|dhcpcd'`, `/etc/dhcp/dhclient.conf`). A cloud-init or container runtime is a fifth candidate on cloud images.

**Q42.** It masks the real problem instead of fixing it: the managing daemon still believes it owns the file, so its write fails and the system's DNS state silently diverges from what the network actually provided. Concretely, VPN and DHCP-supplied search domains and servers never take effect, split DNS stops working, `resolvconf` and NetworkManager log write errors that nobody reads, and the next administrator cannot edit the file and has no obvious reason why. Configure the manager (`dns=none`, `resolved.conf.d`, `ipv4.ignore-auto-dns`) instead.

**Q43.** Setting `ipv4.dns` **adds** your servers to the connection's list; DHCP-supplied servers are still merged in (subject to `ipv4.dns-priority`), so a DHCP server can still be queried. `ipv4.ignore-auto-dns yes` tells NetworkManager to **discard** the DHCP-provided DNS servers and search domains entirely for that connection, leaving only what you configured. You normally set both together.

**Q44.** Nobody — `/etc/resolv.conf` becomes a plain, static, administrator-owned file, typically written by configuration management (Ansible, Puppet, an image build). That is a legitimate and common production configuration for servers with static addressing, precisely because it is deterministic. It is a poor choice for laptops and any host using VPNs or DHCP-supplied DNS, where the resolver must change with the network.

**Q45.** systemd-resolved host → `/etc/systemd/resolved.conf.d/*.conf` (then restart the service). NetworkManager `dns=default` host → the connection profile, via `nmcli connection modify ... ipv4.dns ... ipv4.ignore-auto-dns yes` (stored under `/etc/NetworkManager/system-connections/`). Debian `resolvconf` host → `/etc/resolvconf/resolv.conf.d/{head,base,tail}`, then `resolvconf -u`. Minimal `dhclient`-only server → `/etc/dhcp/dhclient.conf` with `supersede domain-name-servers` / `prepend domain-search`, or a static `/etc/resolv.conf` if the interface is statically configured. In none of these four is hand-editing `/etc/resolv.conf` the durable answer.

</details>
