# LPIC-1 109.4 — Configurar DNS del lado del cliente

## Ejercicios guiados (Examen 102-500, v5.0)

**Qué vas a poder hacer cuando termines:** leer toda la pila de resolución de nombres del lado del cliente de un host Linux, predecir qué va a hacer una consulta dada *antes* de ejecutarla, cambiar el resolver deliberadamente (y hacer que el cambio sobreviva a un reinicio), y diagnosticar un cliente roto con herramientas gratuitas y sin adivinar.

---

### Entorno y seguridad

Estos ejercicios **modifican `/etc/hosts`, `/etc/resolv.conf` y `/etc/nsswitch.conf`**. Usá una VM o un contenedor descartable, nunca una estación de trabajo que necesites funcionando, y nunca un servidor. Todo bloque destructivo termina con un paso de restauración.

```bash
# Prerequisites — install once
# Debian/Ubuntu
sudo apt-get install -y dnsutils bind9-host iproute2 tcpdump
# RHEL/Fedora/Rocky
sudo dnf install -y bind-utils iproute tcpdump
# openSUSE
sudo zypper install -y bind-utils iproute2 tcpdump
```

Sacá una copia de los tres archivos antes de empezar. Vas a restaurar desde acá en el Ejercicio 9:

```bash
sudo mkdir -p /root/109.4-backup
sudo cp -av /etc/hosts /etc/nsswitch.conf /root/109.4-backup/
sudo cp -av --no-dereference /etc/resolv.conf /root/109.4-backup/
```

> `--no-dereference` importa: en la mayoría de los sistemas modernos `/etc/resolv.conf` es un **symlink**, y un `cp` común copiaría silenciosamente el destino y destruiría la evidencia de qué lo administraba.

> **Advertencia sobre contenedores:** dentro de Docker/Podman, `/etc/resolv.conf` y `/etc/hosts` están montados por bind desde el host y pueden ser de solo lectura o revertirse al reiniciar. Si `sed -i` falla con `Device or resource busy`, estás en un contenedor — usá una VM completa para los Ejercicios 3, 4 y 9.

## Ejercicio 1 — Mapear la pila de resolución antes de tocarla

El error más común de DNS del lado del cliente es editar `/etc/resolv.conf` en un host donde nada lo lee. Establecé primero la verdad de base.

1. Averiguá quién responde las consultas de `hosts`, y en qué orden:

   ```bash
   grep '^hosts:' /etc/nsswitch.conf
   ```

   ```
   # representative output (yours will differ by distro)
   hosts:      files resolve [!UNAVAIL=return] myhostname dns
   ```

2. Determiná si `/etc/resolv.conf` es un archivo real o un symlink, y de quién es:

   ```bash
   ls -l /etc/resolv.conf
   ```

   ```
   # possibility A — managed by systemd-resolved (stub)
   lrwxrwxrwx 1 root root 39 Aug 12 09:11 /etc/resolv.conf -> ../run/systemd/resolve/stub-resolv.conf
   # possibility B — a plain file written by NetworkManager, dhclient or a human
   -rw-r--r-- 1 root root 112 Aug 12 09:11 /etc/resolv.conf
   ```

3. Leelo, incluyendo el encabezado de comentarios — los administradores se anuncian ahí:

   ```bash
   cat /etc/resolv.conf
   ```

   ```
   # Generated by NetworkManager
   search corp.example.net
   nameserver 192.168.178.1
   ```

4. Verificá si hay un stub cacheador local escuchando:

   ```bash
   sudo ss -lnup 'sport = :53'; sudo ss -lntp 'sport = :53'
   systemctl is-active systemd-resolved 2>/dev/null || echo "systemd-resolved not present/active"
   ```

5. Si `systemd-resolved` está activo, obtené su visión real del mundo — esto, y no `resolv.conf`, es lo autoritativo en un host así:

   ```bash
   resolvectl status
   ```

   ```
   Global
            Protocols: LLMNR=resolve -mDNS -DNSOverTLS DNSSEC=no/unsupported
     resolv.conf mode: stub

   Link 2 (enp1s0)
       Current Scopes: DNS LLMNR/IPv4
            Protocols: +DefaultRoute +LLMNR -mDNS -DNSOverTLS DNSSEC=no/unsupported
     Current DNS Server: 192.168.178.1
            DNS Servers: 192.168.178.1
             DNS Domain: corp.example.net
   ```

6. Registrá las dos posibles fuentes de verdad una al lado de la otra:

   ```bash
   for f in /etc/resolv.conf /run/systemd/resolve/stub-resolv.conf /run/systemd/resolve/resolv.conf; do
     printf '\n===== %s =====\n' "$f"; cat "$f" 2>/dev/null || echo "(absent)"
   done
   ```

**Verificá tu comprensión**

- **Q1.** En un host donde `/etc/resolv.conf` es un symlink a `stub-resolv.conf` y contiene `nameserver 127.0.0.53`, ¿qué proceso envía realmente el paquete UDP al servidor DNS upstream?
- **Q2.** ¿Cuál es la diferencia práctica entre `/run/systemd/resolve/stub-resolv.conf` y `/run/systemd/resolve/resolv.conf`, y cuándo enlazarías deliberadamente `/etc/resolv.conf` al segundo?
- **Q3.** Tu línea `hosts:` dice `files resolve [!UNAVAIL=return] myhostname dns`. `systemd-resolved` está corriendo y devuelve NXDOMAIN para `db01.corp.example.net`. ¿Se consulta después la fuente `dns`? Explicá la sintaxis `[!UNAVAIL=return]` con precisión.
- **Q4.** ¿Por qué `resolvectl status` es un mejor primer comando que `cat /etc/resolv.conf` en un host systemd?

## Ejercicio 2 — `/etc/hosts` y el orden de NSS

`/etc/hosts` es una base de datos estática, no una caché. No tiene TTL, ni respuestas negativas, y gana sobre DNS siempre que `files` preceda a `dns`.

1. Inspeccioná el archivo actual. Fijate en las entradas obligatorias de loopback:

   ```bash
   cat /etc/hosts
   ```

   ```
   127.0.0.1   localhost
   ::1         localhost ip6-localhost ip6-loopback
   127.0.1.1   lab01.corp.example.net lab01
   ```

2. Agregá un registro de prueba con un nombre canónico y dos alias. El formato es `IP  canonical-name  [alias ...]`, separado por espacios en blanco:

   ```bash
   printf '203.0.113.10\tapp1.lab.internal\tapp1\tdeploy\n' | sudo tee -a /etc/hosts
   ```

3. Resolvelo a través de la biblioteca C, no a través de DNS:

   ```bash
   getent hosts app1.lab.internal
   getent hosts deploy
   ```

   ```
   203.0.113.10    app1.lab.internal app1 deploy
   203.0.113.10    app1.lab.internal app1 deploy
   ```

4. Ahora preguntale a DNS directamente por el mismo nombre y compará:

   ```bash
   host app1.lab.internal
   ```

   ```
   Host app1.lab.internal not found: 3(NXDOMAIN)
   ```

5. Demostrá que el orden dentro del archivo importa. Agregá una segunda línea en conflicto y consultá de nuevo:

   ```bash
   printf '203.0.113.99\tapp1.lab.internal\n' | sudo tee -a /etc/hosts
   getent hosts app1.lab.internal
   getent ahosts app1.lab.internal
   ```

6. Demostrá que el orden en `nsswitch.conf` importa. Ensombrecé localmente un nombre público real:

   ```bash
   printf '203.0.113.55\twww.iana.org\n' | sudo tee -a /etc/hosts
   getent hosts www.iana.org     # → 203.0.113.55 (files wins)
   host www.iana.org             # → the real address (DNS, unaffected)
   ```

7. Invertí temporalmente el orden y observá el cambio:

   ```bash
   sudo cp /etc/nsswitch.conf /etc/nsswitch.conf.bak
   sudo sed -i 's/^hosts:.*/hosts: dns files/' /etc/nsswitch.conf
   getent hosts www.iana.org     # → now the real address
   getent hosts app1.lab.internal
   ```

8. Restaurá, y después limpiá los registros de prueba:

   ```bash
   sudo mv /etc/nsswitch.conf.bak /etc/nsswitch.conf
   sudo sed -i '/lab.internal/d; /203.0.113.55/d' /etc/hosts
   getent hosts app1.lab.internal; echo "exit=$?"
   ```

**Verificá tu comprensión**

- **Q5.** En el paso 5, `getent hosts app1.lab.internal` devolvió solo `203.0.113.10` aunque coincidían dos líneas. ¿Por qué, y qué mostró `getent ahosts` en cambio?
- **Q6.** Después del paso 7 (`hosts: dns files`), un nombre presente solo en `/etc/hosts` igual se resolvió. ¿Algo se volvió *más lento*? ¿Cuál es el costo de poner `dns` primero?
- **Q7.** Un colega agrega `10.0.0.5 db01` a `/etc/hosts` en 300 servidores para "fijar" una base de datos. Dá dos modos concretos de falla en producción que esto crea y que un registro DNS con un TTL corto no crearía.
- **Q8.** ¿Cuáles de estos soporta `/etc/hosts`: TTLs, comodines (`*.lab.internal`), CNAMEs, registros MX, direcciones IPv6, múltiples direcciones para un nombre?

## Ejercicio 3 — `/etc/resolv.conf`: `nameserver`, `search`, `domain`, `ndots`

Este bloque requiere un host cuyo `/etc/resolv.conf` sea un **archivo real** que puedas editar. Si es un symlink a `stub-resolv.conf`, o bien hacé este ejercicio en una VM simple sin `systemd-resolved`, o reemplazá temporalmente el symlink y restauralo en el Ejercicio 9.

1. Escribí una configuración de resolver controlada:

   ```bash
   sudo cp --no-dereference /etc/resolv.conf /etc/resolv.conf.109-4 2>/dev/null
   sudo rm -f /etc/resolv.conf
   sudo tee /etc/resolv.conf >/dev/null <<'EOF'
   nameserver 9.9.9.9
   nameserver 1.1.1.1
   search lab.internal corp.example.net
   options ndots:1 timeout:2 attempts:1
   EOF
   ```

2. Confirmá que la lista de búsqueda se aplica realmente. Mirá el cable mientras resolvés un nombre corto:

   ```bash
   sudo timeout 6 tcpdump -ni any -c 6 'udp port 53' &
   sleep 1
   getent ahosts www >/dev/null 2>&1
   wait
   ```

   Deberías ver consultas por `www.lab.internal` y `www.corp.example.net` antes (o en lugar) de `www.`.

3. Demostrá `ndots` con un nombre que contiene un punto:

   ```bash
   sudo sed -i 's/^options.*/options ndots:1 timeout:2 attempts:1/' /etc/resolv.conf
   sudo timeout 6 tcpdump -ni any -c 4 'udp port 53' & sleep 1
   getent ahosts www.iana >/dev/null 2>&1; wait
   ```

   Con `ndots:1`, `www.iana` tiene ≥ 1 punto, así que se prueba **primero como absoluto**.

4. Ahora subí `ndots` y repetí — esta es la configuración que hace que los clústeres de Kubernetes generen cuatro consultas inútiles por búsqueda:

   ```bash
   sudo sed -i 's/^options.*/options ndots:5 timeout:2 attempts:1/' /etc/resolv.conf
   sudo timeout 8 tcpdump -ni any -c 8 'udp port 53' & sleep 1
   getent ahosts www.iana >/dev/null 2>&1; wait
   ```

   Ahora `www.iana` (1 punto < 5) pasa **primero por la lista de búsqueda**: `www.iana.lab.internal`, `www.iana.corp.example.net`, y recién después `www.iana.`.

5. Mostrá la vía de escape — el punto final hace que un nombre sea completamente calificado y suprime la lista de búsqueda por completo:

   ```bash
   sudo timeout 6 tcpdump -ni any -c 4 'udp port 53' & sleep 1
   getent ahosts www.iana.org. >/dev/null 2>&1; wait
   ```

6. Mostrá que `search` y `domain` son mutuamente excluyentes y gana el último:

   ```bash
   sudo tee /etc/resolv.conf >/dev/null <<'EOF'
   nameserver 9.9.9.9
   domain corp.example.net
   search lab.internal
   options ndots:1
   EOF
   sudo timeout 6 tcpdump -ni any -c 4 'udp port 53' & sleep 1
   getent ahosts www >/dev/null 2>&1; wait
   ```

7. Sobrescribí el archivo sin editarlo, usando las variables de entorno de glibc:

   ```bash
   LOCALDOMAIN="example.org" getent ahosts www
   RES_OPTIONS="ndots:5 timeout:1" getent ahosts www.iana
   ```

8. Probá el límite duro documentado de nameservers:

   ```bash
   sudo tee /etc/resolv.conf >/dev/null <<'EOF'
   nameserver 192.0.2.1
   nameserver 192.0.2.2
   nameserver 192.0.2.3
   nameserver 9.9.9.9
   options timeout:1 attempts:1
   EOF
   time getent ahosts www.iana.org; echo "exit=$?"
   ```

**Verificá tu comprensión**

- **Q9.** En el paso 8, el único resolver que funciona es la cuarta entrada. ¿La búsqueda tuvo éxito? ¿Qué es `MAXNS` y dónde está definido?
- **Q10.** Explicá la regla de `ndots` en una oración, en términos de "puntos en el nombre consultado" vs "lista de búsqueda primero o absoluto primero".
- **Q11.** Un microservicio llama a `http://payments.svc/health` y la plataforma fija `ndots:5` con cuatro dominios de búsqueda. ¿Cuántas consultas DNS genera una búsqueda A fallida en un host dual-stack, y qué cambio de un solo carácter en el hostname las elimina?
- **Q12.** En el paso 6, ¿qué sufijo se agregó realmente, `corp.example.net` o `lab.internal`? Enunciá la regla para `domain` vs `search` apareciendo en el mismo archivo.
- **Q13.** `LOCALDOMAIN` y `RES_OPTIONS` son overrides por proceso. Nombrá un uso operativo legítimo y una razón por la que son inútiles para un demonio arrancado por systemd a menos que des un paso extra.

## Ejercicio 4 — Comportamiento ante fallas: `timeout`, `attempts`, `rotate`, `single-request`

Los problemas de DNS del lado del cliente casi nunca son "no puede resolver". Son "resuelve, pero tarda 10 segundos", que la aplicación reporta como un timeout no relacionado.

1. Apuntá el resolver a una dirección agujero negro (TEST-NET-1 está garantizada como no ruteable) y medí el costo por defecto de una falla:

   ```bash
   sudo tee /etc/resolv.conf >/dev/null <<'EOF'
   nameserver 192.0.2.1
   nameserver 192.0.2.2
   EOF
   time getent ahosts www.iana.org; echo "exit=$?"
   ```

   Registrá el tiempo de reloj. Este es el atasco que hereda tu aplicación, por búsqueda, con los **valores por defecto** (`timeout:5`, `attempts:2`).

2. Ahora acotalo explícitamente y medí de nuevo:

   ```bash
   sudo tee /etc/resolv.conf >/dev/null <<'EOF'
   nameserver 192.0.2.1
   nameserver 192.0.2.2
   options timeout:1 attempts:1
   EOF
   time getent ahosts www.iana.org; echo "exit=$?"
   ```

3. Medí el caso "un servidor muerto delante de uno bueno" — la caída realista:

   ```bash
   sudo tee /etc/resolv.conf >/dev/null <<'EOF'
   nameserver 192.0.2.1
   nameserver 9.9.9.9
   options timeout:1 attempts:1
   EOF
   time getent ahosts www.iana.org
   time getent ahosts www.kernel.org
   ```

   Fijate que **cada** búsqueda paga la penalidad del servidor muerto: el stub de glibc no tiene estado y siempre arranca en la primera entrada.

4. Agregá `rotate` y observá la diferencia en la distribución del origen de las consultas:

   ```bash
   sudo sed -i 's/^options.*/options timeout:1 attempts:1 rotate/' /etc/resolv.conf
   sudo timeout 10 tcpdump -ni any -c 10 'udp port 53' & sleep 1
   for n in a b c d e; do getent ahosts $n.iana.org >/dev/null 2>&1; done
   wait
   ```

5. Observá el patrón de consultas dual-stack que `single-request` existe para arreglar:

   ```bash
   sudo tee /etc/resolv.conf >/dev/null <<'EOF'
   nameserver 9.9.9.9
   options timeout:1 attempts:1
   EOF
   sudo timeout 6 tcpdump -ni any -c 4 -v 'udp port 53' & sleep 1
   getent ahosts www.iana.org >/dev/null; wait
   ```

   Dos consultas (A y AAAA) salen **en paralelo desde el mismo puerto de origen**.

6. Serializalas:

   ```bash
   sudo sed -i 's/^options.*/options timeout:1 attempts:1 single-request/' /etc/resolv.conf
   sudo timeout 6 tcpdump -ni any -c 4 -v 'udp port 53' & sleep 1
   getent ahosts www.iana.org >/dev/null; wait
   ```

7. Forzá TCP y confirmalo en el cable:

   ```bash
   sudo sed -i 's/^options.*/options timeout:1 attempts:1 use-vc/' /etc/resolv.conf
   sudo timeout 6 tcpdump -ni any -c 4 'port 53' & sleep 1
   getent ahosts www.iana.org >/dev/null; wait
   ```

**Verificá tu comprensión**

- **Q14.** Compará tus tiempos medidos de los pasos 1 y 2. ¿Cuáles son los valores por defecto de `timeout` y `attempts`, y cuáles son sus máximos?
- **Q15.** El paso 3 muestra que un secundario *que funciona* no hace rápido al cliente. Explicá por qué, y nombrá el mecanismo (que no está en `resolv.conf`) que realmente resuelve esto en producción.
- **Q16.** ¿Qué síntoma exacto arregla `single-request`, y por qué existe `single-request-reopen` como una opción separada y más débil?
- **Q17.** Un usuario reporta "el sitio carga después de unos 10 segundos, siempre, pero al final funciona". ¿Qué único síntoma de `resolv.conf` identifica esta huella, y cuál es el primer comando que ejecutás para confirmarlo?
- **Q18.** ¿Por qué `options use-vc` es una mala elección permanente, y qué uso diagnóstico legítimo tiene?

## Ejercicio 5 — `host` y `dig` como sondas exclusivas de DNS

Ambas herramientas leen `/etc/resolv.conf` **solo para encontrar una dirección de servidor**. Ninguna consulta `/etc/hosts` ni `/etc/nsswitch.conf`. Esa propiedad es exactamente lo que las hace herramientas de diagnóstico.

1. Restaurá primero un resolver funcional:

   ```bash
   sudo tee /etc/resolv.conf >/dev/null <<'EOF'
   nameserver 9.9.9.9
   options timeout:2 attempts:1 edns0
   EOF
   ```

2. Búsquedas directas e inversas básicas con `host`:

   ```bash
   host www.iana.org
   host -t MX iana.org
   host -t NS iana.org
   host -t TXT iana.org
   host -t SOA iana.org
   host 8.8.8.8
   ```

   ```
   # representative
   www.iana.org has address 192.0.43.8            # the real address will differ — do not memorise it
   iana.org mail is handled by 10 mail.iana.org.
   8.8.8.8.in-addr.arpa domain name pointer dns.google.
   ```

3. Lo mismo con `dig`, más las partes que `host` esconde:

   ```bash
   dig iana.org A
   ```

   Leé las cuatro secciones y los flags del encabezado:

   ```
   ;; ->>HEADER<<- opcode: QUERY, status: NOERROR, id: 51203
   ;; flags: qr rd ra; QUERY: 1, ANSWER: 1, AUTHORITY: 0, ADDITIONAL: 1
   ```

4. Aprendé los filtros de salida que vas a usar de verdad:

   ```bash
   dig +short iana.org A
   dig +noall +answer iana.org ANY
   dig +noall +authority +comments example.net NS
   ```

5. Consultá un servidor específico, evitando `resolv.conf` por completo — así es como separás "el DNS está roto" de "este cliente está mal configurado":

   ```bash
   dig @1.1.1.1 +short www.iana.org
   dig @9.9.9.9  +short www.iana.org
   ```

6. Preguntale a un servidor autoritativo directamente, con la recursión apagada:

   ```bash
   NS=$(dig +short NS iana.org | head -1)
   dig @"$NS" +norecurse iana.org SOA
   ```

   Fijate en la ausencia del flag `ra` y en la presencia de `aa` en la respuesta.

7. Seguí la cadena de delegación desde la raíz:

   ```bash
   dig +trace www.iana.org | grep -E '^\S+\s+[0-9]+\s+IN\s+(NS|A|CNAME)' | head -20
   ```

8. Búsquedas inversas de la forma explícita, y mirá a qué se expande `-x`:

   ```bash
   dig -x 9.9.9.9 +short
   dig 9.9.9.9.in-addr.arpa PTR +short
   dig -x 2620:fe::fe +short
   ```

9. Inspeccioná material DNSSEC y medí la latencia:

   ```bash
   dig +dnssec +multiline iana.org SOA | head -30
   dig www.iana.org | grep -E 'Query time|SERVER|MSG SIZE'
   ```

**Verificá tu comprensión**

- **Q19.** Agregás `10.0.0.9 api.corp.example.net` a `/etc/hosts`. ¿Qué devuelve `host api.corp.example.net`, y a qué se conecta `curl http://api.corp.example.net`? Reconciliá ambos.
- **Q20.** En los flags del encabezado de `dig`, ¿qué significan `qr`, `rd`, `ra`, `aa` y `ad`? ¿Cuál te dice que la respuesta vino de un servidor autoritativo para esa zona?
- **Q21.** `dig example.com` devuelve `status: NOERROR` con `ANSWER: 0`. ¿El nombre no existe? ¿Cómo se llama este caso, y en qué difiere de `NXDOMAIN`?
- **Q22.** ¿Por qué `dig -x 9.9.9.9` devuelve un nombre mientras que `dig 9.9.9.9` devuelve `NXDOMAIN` para el "nombre" `9.9.9.9`?
- **Q23.** ¿Qué hace `+trace` de manera distinta a una consulta normal, y qué clase de problema encuentra que `dig @resolver name` no puede?

## Ejercicio 6 — `getent` vs `dig`: probar que NSS ≠ DNS

Esta es la distinción que evalúa el examen y la que resuelve incidentes reales.

1. Compará las dos bases de datos explícitamente:

   ```bash
   getent hosts   www.iana.org
   getent ahosts  www.iana.org
   getent ahostsv4 www.iana.org
   getent ahostsv6 www.iana.org
   ```

   ```
   # getent ahosts — one line per address, per socket type
   192.0.43.8      STREAM www.iana.org
   192.0.43.8      DGRAM
   192.0.43.8      RAW
   2001:500:88:200::8 STREAM
   ```

2. Mostrá que `getent` obedece a `/etc/hosts` y `dig` no:

   ```bash
   printf '198.51.100.7\ttest.iana.org\n' | sudo tee -a /etc/hosts
   getent hosts test.iana.org      # 198.51.100.7
   dig +short test.iana.org        # (nothing)
   sudo sed -i '/198.51.100.7/d' /etc/hosts
   ```

3. Mostrá las fuentes NSS que no son DNS en acción:

   ```bash
   getent hosts localhost
   getent hosts "$(hostname)"
   getent ahosts _gateway          # provided by nss-myhostname
   getent hosts _outbound 2>/dev/null || echo "(_outbound needs systemd >= 249)"
   ```

4. Confirmá que `_gateway` no existe en ningún lado ni en DNS ni en `/etc/hosts`:

   ```bash
   grep -c _gateway /etc/hosts; dig +short _gateway; ip route show default
   ```

5. Usá `getent` contra otras bases de datos de NSS para internalizar que `hosts` es solo una de ellas:

   ```bash
   getent passwd root
   getent services 53
   getent protocols udp
   getent networks
   ```

6. Usá los códigos de salida para scripting — `getent` devuelve 2 cuando la clave no se encuentra:

   ```bash
   getent hosts definitely-not-a-real-name.invalid; echo "exit=$?"
   getent hosts www.iana.org >/dev/null; echo "exit=$?"
   ```

7. Rompé `nsswitch.conf` y mirá cómo `getent` y `dig` divergen:

   ```bash
   sudo cp /etc/nsswitch.conf /etc/nsswitch.conf.bak
   sudo sed -i 's/^hosts:.*/hosts: files/' /etc/nsswitch.conf
   getent hosts www.iana.org; echo "getent exit=$?"
   dig +short www.iana.org
   ping -c1 www.iana.org
   sudo mv /etc/nsswitch.conf.bak /etc/nsswitch.conf
   ```

**Verificá tu comprensión**

- **Q25.** Enunciá en una línea la regla que distingue cuándo usar `getent hosts` y cuándo usar `dig`, en términos de qué prueba cada uno.

**Q16.** glibc envía las consultas A y AAAA del mismo nombre **en paralelo desde el mismo puerto UDP de origen**. **Q22.** `-x` realiza la transformación de DNS inverso: invierte los octetos y agrega `in-addr.arpa`, produciendo una consulta `PTR` para `9.9.9.9.in-addr.arpa` (para IPv6, con los nibbles invertidos bajo `ip6.arpa`). Sin `-x`, `dig` trata `9.9.9.9` como un nombre de dominio literal y pide un registro A en el nombre (inexistente) `9.9.9.9`.

**Q23.** `+trace` deshabilita la recursión e **itera la cadena de delegación por su cuenta**, empezando en los servidores raíz y siguiendo las referencias NS hacia abajo hasta los servidores autoritativos, imprimiendo cada paso. Una consulta normal le pregunta a un resolver recursivo y muestra solo la respuesta final. `+trace` encuentra problemas a nivel de delegación que ninguna consulta a un solo resolver puede: delegaciones rotas o cojas (*lame*), una zona padre apuntando al conjunto NS equivocado, registros de glue faltantes, una zona inconsistente entre servidores autoritativos, y quiebres de la cadena DNSSEC en un corte de zona específico.

**Q24.** (a) El nombre está en `/etc/hosts` (u otra fuente NSS que no sea DNS, como `myhostname` o un mapa `hosts` de LDAP/SSSD) y no existe en DNS en absoluto. (b) `systemd-resolved` está aplicando **split DNS**: el nombre se rutea a un servidor específico de la VPN o del enlace que `getent` alcanza a través del stub `127.0.0.53`, mientras que tu `dig` fue a un resolver que no tiene visión de esa zona. Confirmalo con `resolvectl query <name>` — reporta qué enlace y protocolo produjeron la respuesta.

**Q25.** Usá `getent hosts`/`getent ahosts` para probar **qué van a obtener realmente las aplicaciones de esta máquina** (el camino completo de NSS: archivo hosts, mDNS, resolved, DNS). Usá `dig`/`host` para probar **qué dice el DNS en sí**, independientemente de la configuración local. Cuando ambos discrepan, la falla está en `/etc/hosts` o en `/etc/nsswitch.conf`; cuando coinciden y ambos están mal, la falla está upstream en el DNS.

**Q26.** `/etc/nsswitch.conf` — la línea `hosts:` se redujo a `files`, así que la biblioteca C nunca consulta DNS y todo nombre que no esté en `/etc/hosts` falla. `dig` es inmune porque implementa el protocolo DNS por su cuenta y lee `/etc/resolv.conf` solo para aprender una dirección de servidor; nunca llama a `getaddrinfo()` y por lo tanto nunca toca NSS.

**Q27.** `getent ahosts` — pasa por `getaddrinfo()`, que realiza la selección de familia de direcciones y aplica las reglas de selección/ordenamiento de direcciones de destino del RFC 6724 (opcionalmente ajustadas en `/etc/gai.conf`). Esto importa en hosts dual-stack porque determina si una aplicación intenta IPv6 o IPv4 **primero**; un host con un camino IPv6 roto pero una respuesta AAAA preferida va a parecer colgarse al conectar mientras `getent hosts` se ve perfectamente sano.

**Q28.** `nss-myhostname`. El mismo módulo también resuelve el **hostname local** (para que la máquina siempre pueda resolverse a sí misma incluso sin entrada en `/etc/hosts` y sin DNS), `localhost`/`localhost.localdomain` a las direcciones de loopback, y `_outbound` (systemd ≥ 249) a la dirección local que se usaría para el tráfico saliente. También provee las búsquedas inversas correspondientes.

**Q29.** Porque `host` prueba únicamente que el **DNS** tiene un registro — no prueba que las aplicaciones de esta máquina vayan a obtener esa dirección (archivo hosts, split DNS, NSS), y desde luego no prueba la alcanzabilidad del servicio. La verificación debería ser `getent ahosts "$NAME"` para "¿puede esta máquina resolverlo del modo en que lo harán las aplicaciones?", y un intento de conexión real (`curl`, `nc -z`, un endpoint de salud) para "¿puede esta máquina alcanzar el servicio?".

**Q30.** `Domains=lab.internal` es a la vez un **dominio de búsqueda y un dominio de ruteo**: a los nombres cortos se les agrega `.lab.internal`, y las consultas por `*.lab.internal` se rutean a los servidores de este enlace. `Domains=~corp.example.net` (prefijo tilde) es **solo de ruteo**: las consultas por `*.corp.example.net` van a los servidores de este enlace, pero nunca se agrega nada a los nombres cortos. Así que `ping app1` se ve afectado por el primero y no por el segundo. (El valor especial `~.` marca un enlace como la ruta por defecto para todas las consultas.)

**Q31.** Porque `resolvectl` le habla a `systemd-resolved` por su API de D-Bus/Varlink, y `resolved` mantiene **scopes por enlace** — cada interfaz tiene sus propios servidores, dominios y protocolos — así que puede decirte qué scope de qué enlace produjo la respuesta, si vino de la caché, y si DNSSEC validó. `dig` es una herramienta de protocolo: abre un socket a una dirección de servidor y reporta esa transacción. No tiene noción de enlaces, scopes ni cachés.

**Q32.** Al enlace de la VPN se le dio `~.` (`Domains=~.`, mostrado como `+DefaultRoute` en `resolvectl status`), haciéndolo la **ruta por defecto para todas las consultas DNS**. Mientras está levantado eso es lo previsto; que se rompa después de desconectar apunta a que el enlace físico perdió sus propios servidores o su estado de ruta por defecto — típicamente `ipv4.ignore-auto-dns yes` en la conexión física, o el cliente VPN reescribiendo el DNS global en vez del DNS por enlace. `resolvectl status` muestra `+DefaultRoute`/`-DefaultRoute` y la lista de servidores por enlace; `resolvectl domain` muestra los dominios de ruteo.

**Q33.** `DNSSEC=no` (sin validación), `DNSSEC=allow-downgrade` (validar cuando el servidor upstream soporta DNSSEC, caer silenciosamente cuando no), `DNSSEC=yes` (exigir validación; rechazar las respuestas no validables). `allow-downgrade` es pragmático porque una gran fracción de los resolvers del mundo real — portales cautivos de hoteles, CPE de ISP, middleboxes corporativos — alteran o eliminan los registros DNSSEC; con `yes` esas redes se vuelven totalmente inutilizables, mientras que `allow-downgrade` degrada a DNS plano en vez de fallar cerrado. La contrapartida honesta: `allow-downgrade` no ofrece ninguna garantía de seguridad frente a un atacante activo, ya que el atacante puede forzar la degradación.

**Q34.** `127.0.0.54` es el **stub proxy DNS** de `systemd-resolved` (systemd ≥ 249). A diferencia de `127.0.0.53`, que es un resolver local completo que aplica dominios de búsqueda, ruteo de split-DNS, la caché local, LLMNR/mDNS y comportamientos adyacentes a `/etc/hosts`, el listener de `127.0.0.54` reenvía las consultas **textualmente** a los servidores upstream configurados en ese momento y devuelve la respuesta esencialmente intacta. Existe para clientes que necesitan la semántica cruda del DNS upstream (su propia lógica de resolución, validación DNSSEC, o control total de la consulta) sin dejar de beneficiarse de la selección de upstream y los transportes cifrados de `resolved`.

**Q35.** Te olvidaste de `systemctl restart systemd-resolved` (o `systemctl reload`); `resolved.conf` y sus drop-ins se leen al arrancar. Editar `/etc/resolv.conf` no logra nada porque en este host es un symlink al `stub-resolv.conf` generado, que `resolved` regenera y que de todos modos solo apunta la biblioteca C a `127.0.0.53` — los servidores upstream viven en la configuración propia de `resolved` y en los datos por enlace que recibió de NetworkManager/DHCP.

**Q36.** `getent hosts www.kernel.org` (o `getent ahosts`) comparado contra `dig +short www.kernel.org`. El desacuerdo entre la respuesta de NSS y la de DNS localiza la falla en una fuente local en un solo paso. `ping` no cuenta como diagnóstico porque usa `getaddrinfo()` como cualquier otra aplicación y por lo tanto reporta la *misma* respuesta equivocada — reproduce el síntoma sin discriminar entre las causas posibles.

**Q37.** *Inalcanzable*: ninguna respuesta en absoluto, así que glibc consume todo el presupuesto de `timeout × attempts × servers` y finalmente reporta la falla; `dig` imprime `;; communications error ... timed out` y después `no servers could be reached`. Esto implica un problema de ruteo, firewall o "el servidor está caído" — la falla está entre vos y el resolver. *Alcanzable pero rechaza*: una respuesta **inmediata** con `status: REFUSED` (o `SERVFAIL`). Esto implica que el servidor está vivo y alcanzable y tomó una decisión de política o de resolución — normalmente no estás en su ACL de clientes permitidos, o no es autoritativo y tiene la recursión deshabilitada para vos. La latencia por sí sola los distingue antes de que leas un solo flag.

**Q38.** (a) Bajar `ndots` a `1` (o `2`) para que los nombres que contienen un punto se prueben primero como absolutos; (b) acortar la lista `search` a los dominios genuinamente necesarios. Un tercer arreglo, por aplicación, es agregar un punto final a los nombres completamente calificados. En una plataforma de contenedores que no controlás, no podés editar el `resolv.conf` del nodo — fijás `dnsConfig.options` (`ndots`) y `dnsConfig.searches` en la especificación del pod, que es el override soportado por carga de trabajo. Notá que el arreglo del punto final debe verificarse por cada biblioteca cliente.

**Q39.** Línea correcta: `hosts: files dns` (o, con `systemd-resolved`: `hosts: files resolve [!UNAVAIL=return] myhostname dns`). `[NOTFOUND=return]` después de `files` significa "si la fuente `files` no encontró la clave, detené toda la búsqueda y devolvé no-encontrado" — así que DNS solo se alcanza cuando `files` devuelve algún *otro* estado, lo cual efectivamente nunca pasa. `NOTFOUND` = la fuente funcionó y la clave genuinamente no está. `UNAVAIL` = la fuente en sí no pudo consultarse (servicio caído, módulo faltante). Retornar ante `NOTFOUND` es casi siempre un bug; retornar ante todo **excepto** `UNAVAIL` (`[!UNAVAIL=return]`) es el idioma que realmente querés cuando una fuente debe ser autoritativa con un fallback.

**Q40.** No. Vaciar limpia **tu** caché; el TTL de 300 s del registro significa que otros resolvers y clientes de toda la flota legítimamente conservan la respuesta vieja por hasta cinco minutos más (más cualquier TTL de cacheo negativo del SOA de la zona). La secuencia planificada correcta es: **bajar el TTL bastante antes** (al menos un período del TTL viejo antes del cambio, por ejemplo a 60 s), esperar a que el TTL viejo expire en todas partes, hacer el cambio de IP, verificar, y después volver a subir el TTL. Vaciar cachés locales es una remediación para un cambio no planificado, no un sustituto de la gestión del TTL. Si `nscd` es la caché, `nscd -i hosts` invalida la tabla de hosts (y `nscd -g` muestra estadísticas); `sssd` cachea por separado y necesita `sss_cache`.

**Q41.** `systemd-resolved` (verificá con `systemctl is-active systemd-resolved`, `ls -l /etc/resolv.conf`); `NetworkManager` (el encabezado `# Generated by NetworkManager`, `nmcli general status`, el ajuste `dns=` en `NetworkManager.conf`); `resolvconf`/`openresolv` (`ls /etc/resolvconf/resolv.conf.d/`, `command -v resolvconf`); y el cliente DHCP `dhclient`/`dhcpcd` (`ps -ef | grep -E 'dhclient|dhcpcd'`, `/etc/dhcp/dhclient.conf`). Un cloud-init o un runtime de contenedores es un quinto candidato en imágenes de nube.

**Q42.** Enmascara el problema real en vez de arreglarlo: el demonio administrador sigue creyendo que es dueño del archivo, así que su escritura falla y el estado de DNS del sistema diverge silenciosamente de lo que la red proveyó de verdad. Concretamente, los dominios de búsqueda y servidores provistos por VPN y DHCP nunca toman efecto, el split DNS deja de funcionar, `resolvconf` y NetworkManager registran errores de escritura que nadie lee, y el próximo administrador no puede editar el archivo y no tiene ninguna razón obvia de por qué. Configurá el administrador (`dns=none`, `resolved.conf.d`, `ipv4.ignore-auto-dns`) en su lugar.

**Q43.** Fijar `ipv4.dns` **agrega** tus servidores a la lista de la conexión; los servidores provistos por DHCP se siguen fusionando (sujeto a `ipv4.dns-priority`), así que un servidor DHCP todavía puede ser consultado. `ipv4.ignore-auto-dns yes` le dice a NetworkManager que **descarte** por completo los servidores DNS y dominios de búsqueda provistos por DHCP para esa conexión, dejando solo lo que configuraste. Normalmente se fijan ambos juntos.

**Q44.** Nadie — `/etc/resolv.conf` se convierte en un archivo plano, estático, propiedad del administrador, típicamente escrito por gestión de configuración (Ansible, Puppet, una construcción de imagen). Esa es una configuración de producción legítima y común para servidores con direccionamiento estático, precisamente porque es determinista. Es una mala elección para laptops y para cualquier host que use VPNs o DNS provisto por DHCP, donde el resolver debe cambiar con la red.

**Q45.** Host con systemd-resolved → `/etc/systemd/resolved.conf.d/*.conf` (después reiniciar el servicio). Host con NetworkManager `dns=default` → el perfil de conexión, vía `nmcli connection modify ... ipv4.dns ... ipv4.ignore-auto-dns yes` (almacenado bajo `/etc/NetworkManager/system-connections/`). Host Debian con `resolvconf` → `/etc/resolvconf/resolv.conf.d/{head,base,tail}`, después `resolvconf -u`. Servidor mínimo con solo `dhclient` → `/etc/dhcp/dhclient.conf` con `supersede domain-name-servers` / `prepend domain-search`, o un `/etc/resolv.conf` estático si la interfaz está configurada estáticamente. En ninguno de estos cuatro la respuesta duradera es editar `/etc/resolv.conf` a mano.

</details>
