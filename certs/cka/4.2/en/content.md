# 4.2 Create and manage Kubernetes clusters using kubeadm

## What is kubeadm?

`kubeadm` is the official Kubernetes tool for bootstrapping clusters adhering to project best practices. It does not install or manage container runtimes, configure underlying network fabrics (handled by CNI plugins), or provision cloud infrastructure. Its responsibility is establishing a minimally functional control plane and joining worker nodes to the cluster topology.

`kubeadm` provides two primary commands:

- `kubeadm init` — Bootstraps the initial control-plane node.
- `kubeadm join` — Joins worker or additional control-plane nodes to an existing cluster.

And key lifecycle maintenance commands:

- `kubeadm upgrade` — Upgrades cluster components to target versions.
- `kubeadm certs` — Manages cluster certificate rotation and expiration.
- `kubeadm token` — Manages bootstrap tokens.
- `kubeadm reset` — Reverts modifications executed during `init` or `join` operations.
- `kubeadm config` — Inspects and migrates configuration files used during bootstrapping.

## Prerequisites Before `kubeadm init`

On **all** nodes (control plane and worker instances):

```bash
# Disable host swap (kubelet fails to start when swap is active unless configured explicitly)
swapoff -a
sed -i '/ swap / s/^/#/' /etc/fstab

# Load required network kernel modules
cat <<EOF | tee /etc/modules-load.d/k8s.conf
overlay
br_netfilter
EOF
modprobe overlay
modprobe br_netfilter

# Apply sysctl network parameter configurations required by CNI drivers
cat <<EOF | tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-iptables  = 1
net.bridge.bridge-nf-call-ip6tables = 1
net.ipv4.ip_forward                 = 1
EOF
sysctl --system
```

Additionally, a **CRI-compliant container runtime** (`containerd`, `CRI-O`) must be installed and active, with `kubeadm`, `kubelet`, and `kubectl` binaries installed matching target minor versions:

```bash
apt-get update
apt-get install -y kubelet kubeadm kubectl
apt-mark hold kubelet kubeadm kubectl
```

## `kubeadm init`: Control Plane Bootstrapping

```bash
kubeadm init \
  --pod-network-cidr=10.244.0.0/16 \
  --apiserver-advertise-address=192.168.1.10 \
  --kubernetes-version=v1.35.0
```

`--pod-network-cidr` is mandatory if your chosen CNI plugin requires explicit subnet allocations (e.g. Flannel uses `10.244.0.0/16`; Calico frequently defaults to `192.168.0.0/16`). Mismatched CIDRs leave Pods stuck in `ContainerCreating` states.

Initialization output summary:

```
Your Kubernetes control-plane has initialized successfully!

To start using your cluster, you need to run the following as a regular user:

  mkdir -p $HOME/.kube
  sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
  sudo chown $(id -u):$(id -g) $HOME/.kube/config

Then you can join any number of worker nodes by running the following on each as root:

kubeadm join 192.168.1.10:6443 --token abcdef.0123456789abcdef \
    --discovery-token-ca-cert-hash sha256:1234...
```

Immediately after `init`, **clusters lack Pod-to-Pod networking** until a CNI plugin is installed:

```bash
kubectl apply -f https://raw.githubusercontent.com/flannel-io/flannel/master/Documentation/kube-flannel.yml
```

Nodes remain in `NotReady` states until CNI plugins are fully operational:

```bash
kubectl get nodes
# NAME     STATUS     ROLES           AGE   VERSION
# master   NotReady   control-plane   2m    v1.35.0
```

### Artifacts Generated by `kubeadm init`

- TLS certificates stored in `/etc/kubernetes/pki/` (CA, etcd, apiserver, etc.).
- Kubeconfig credentials in `/etc/kubernetes/` (`admin.conf`, `kubelet.conf`, `controller-manager.conf`, `scheduler.conf`).
- Static pod manifests in `/etc/kubernetes/manifests/` for `kube-apiserver`, `kube-controller-manager`, `kube-scheduler`, and local `etcd`.
- A `ConfigMap` named `kubeadm-config` inside namespace `kube-system` retaining cluster configuration settings.

## `kubeadm join`: Adding Nodes

### Worker Nodes

Execute the join command generated during `kubeadm init`. If tokens expire:

```bash
kubeadm join 192.168.1.10:6443 \
  --token abcdef.0123456789abcdef \
  --discovery-token-ca-cert-hash sha256:1234567890abcdef...
```

### Additional Control-Plane Nodes (High Availability)

To join additional control plane nodes, pass `--upload-certs` during initial `init` execution (or run `kubeadm init phase upload-certs --upload-certs` on an active master node), then run:

```bash
kubeadm join 192.168.1.10:6443 \
  --token abcdef.0123456789abcdef \
  --discovery-token-ca-cert-hash sha256:1234... \
  --control-plane \
  --certificate-key f8902e...
```

Omitting `--control-plane` registers nodes as standard worker nodes.

## `kubeadm token`: Managing Bootstrap Tokens

Bootstrap tokens expire after 24 hours by default. Useful commands:

```bash
kubeadm token list
kubeadm token create                      # Creates a new token with default TTL
kubeadm token create --ttl 0              # Creates a non-expiring token
kubeadm token delete abcdef.0123456789abcdef
```

Regenerate join commands complete with active tokens and CA hash values:

```bash
kubeadm token create --print-join-command
```

## `kubeadm certs`: Expiration and Renewal

Certificates generated by `kubeadm init` expire after 1 year (excluding the root CA, which is valid for 10 years).

```bash
kubeadm certs check-expiration
```

```
CERTIFICATE                EXPIRES                  RESIDUAL TIME
admin.conf                 Jul 15, 2027 10:00 UTC   364d
apiserver                  Jul 15, 2027 10:00 UTC   364d
...
```

Renew all control plane certificates:

```bash
kubeadm certs renew all
```

Restart static pod components (e.g. moving manifest files out of `/etc/kubernetes/manifests/` and back, or restarting `kubelet`) to apply renewed certificates.

## `kubeadm upgrade`: Upgrading Cluster Versions

Follow these steps per node, **starting exclusively on the primary control plane node**:

```bash
# 1. Upgrade the kubeadm package first
apt-mark unhold kubeadm
apt-get install -y kubeadm=1.35.1-1.1
apt-mark hold kubeadm

# 2. Inspect the upgrade plan
kubeadm upgrade plan
```

```bash
# 3. Apply the upgrade (primary control plane node only)
kubeadm upgrade apply v1.35.1
```

For secondary control-plane or worker nodes, run `upgrade node` instead of `upgrade apply`:

```bash
kubeadm upgrade node
```

### Complete Upgrade Workflow per Node

```bash
kubectl drain <node> --ignore-daemonsets --delete-emptydir-data

apt-mark unhold kubelet kubectl
apt-get install -y kubelet=1.35.1-1.1 kubectl=1.35.1-1.1
apt-mark hold kubelet kubectl
systemctl daemon-reload
systemctl restart kubelet

kubectl uncordon <node>
```

Key Version Skew Rules:

- `kubeadm` **cannot skip minor versions** during upgrades (e.g. upgrading directly from 1.33 to 1.35 is prohibited; upgrade to 1.34 first).
- `kube-apiserver` must be the highest version in the cluster topology; control plane components cannot be newer than the API server.
- `kubelet` versions may lag up to 2 minor versions behind `kube-apiserver`.
- Upgrade `kubeadm` before upgrading `kubelet` and `kubectl` on every node.

## `kubeadm config`

Inspect configuration settings generated during initialization:

```bash
kubeadm config print init-defaults      # Print default init configurations
kubeadm config print join-defaults      # Print default join configurations
kubeadm config images list              # List control plane container images
kubeadm config images pull              # Pre-pull control plane images
```

Advanced cluster bootstrapping uses YAML `ClusterConfiguration` manifests:

```bash
kubeadm init --config kubeadm-config.yaml
```

---

## `kubeadm reset`: Reverting Node Configurations

```bash
kubeadm reset
iptables -F && iptables -t nat -F && iptables -t mangle -F && iptables -X
rm -rf /etc/cni/net.d
```

`reset` purges `/etc/kubernetes/` directories and halts the `kubelet` service, but does not flush `iptables` or uninstall installed packages.
