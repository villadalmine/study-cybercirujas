# 363.2 Ceph Storage Clusters — Guided Exercises

These exercises walk you through building, operating and diagnosing a small but production-representative Ceph cluster with `cephadm` (the container-based orchestrator used by Ceph Octopus and later). Execute the numbered steps in order. After each block, answer the verification questions; the full answer key is collapsed at the end.

## Lab environment

You need **three nodes** running a recent distribution (RHEL/Rocky 9, Ubuntu 22.04, or similar), each with:

- `podman` (or `docker`), `python3`, `systemd`, `chrony`/`ntpd` time sync, and passwordless `sudo`.
- One OS disk **plus at least one blank, unpartitioned data disk** (`/dev/vdb`) that Ceph may consume.
- Hostnames `ceph-node1`, `ceph-node2`, `ceph-node3` resolvable by all peers; management IPs `192.168.10.11/12/13`.
- `cephadm` installed on `ceph-node1` (`curl -fsSL https://download.ceph.com/rpm-18.2.4/el9/noarch/cephadm -o /usr/sbin/cephadm && chmod +x /usr/sbin/cephadm`, or your distro package).

> All `ceph`/`rbd`/`rados` commands below are run from `ceph-node1`. With cephadm you either enter the shell container (`cephadm shell`) or install the client packages so the binaries exist on the host. Every command assumes root or `sudo`.

## Exercise 2 — Add hosts and provision OSDs

1. Distribute the cluster SSH public key generated by cephadm to the other two nodes, then register them:
   ```bash
   ceph cephadm get-pub-key > /tmp/ceph.pub
   ssh-copy-id -f -i /tmp/ceph.pub root@ceph-node2
   ssh-copy-id -f -i /tmp/ceph.pub root@ceph-node3

   ceph orch host add ceph-node2 192.168.10.12
   ceph orch host add ceph-node3 192.168.10.13
   ceph orch host ls
   ```

2. Inspect what block devices the orchestrator considers available:
   ```bash
   ceph orch device ls
   ```
   A device is only offered when it is unpartitioned, has no filesystem, and is not already an OSD (`AVAILABLE = Yes`).

3. Create OSDs. Either target one device explicitly or let cephadm consume every free disk:
   ```bash
   # Explicit:
   ceph orch daemon add osd ceph-node1:/dev/vdb

   # Or declarative, cluster-wide:
   ceph orch apply osd --all-available-devices
   ```

4. Confirm the OSDs joined the CRUSH hierarchy and the cluster is healthy:
   ```bash
   ceph osd tree
   ceph -s
   ```
   Expected `ceph osd tree`:
   ```
   ID  CLASS  WEIGHT   TYPE NAME            STATUS  REWEIGHT  PRI-AFF
   -1         0.29279  root default
   -3         0.09760      host ceph-node1
    0    hdd  0.09760          osd.0            up   1.00000  1.00000
   -5         0.09760      host ceph-node2
    1    hdd  0.09760          osd.1            up   1.00000  1.00000
   -7         0.09760      host ceph-node3
    2    hdd  0.09760          osd.2            up   1.00000  1.00000
   ```

**Questions**
- Q2.1 — What three conditions must a disk meet before `ceph orch device ls` marks it `AVAILABLE`?
- Q2.2 — Which on-disk storage backend does a modern cephadm OSD use by default, and which tool actually prepares the disk (LVM layout, key, metadata)?
- Q2.3 — In `ceph osd tree`, what do the columns `STATUS` (`up`/`down`) and `REWEIGHT` mean, and how do they differ from an OSD being `in`/`out`?
- Q2.4 — What does the difference between `ceph orch daemon add osd` and `ceph orch apply osd` imply for future disks inserted into a host?

## Exercise 3 — Monitor quorum, managers, and the CRUSH map

1. Grow the monitor and manager quorum to three so the control plane tolerates a node loss:
   ```bash
   ceph orch apply mon 3
   ceph orch apply mgr 3
   ceph mon stat
   ceph mon dump
   ```
   Expected `ceph mon stat`:
   ```
   e3: 3 mons at {ceph-node1=[v2:192.168.10.11:3300/0,v1:192.168.10.11:6789/0],
   ceph-node2=[...],ceph-node3=[...]}, election epoch 12, leader 0 ceph-node1,
   quorum 0,1,2 ceph-node1,ceph-node2,ceph-node3
   ```

2. List and inspect manager modules (the dashboard, autoscaler and alerting all live here):
   ```bash
   ceph mgr module ls
   ceph mgr services
   ```

3. Read the CRUSH topology and export the compiled map for offline editing:
   ```bash
   ceph osd crush tree
   ceph osd crush rule ls
   ceph osd crush rule dump replicated_rule

   ceph osd getcrushmap -o /tmp/crush.bin
   crushtool -d /tmp/crush.bin -o /tmp/crush.txt
   sed -n '/^rule replicated_rule/,/^}/p' /tmp/crush.txt
   ```
   You should see a rule whose `step chooseleaf firstn 0 type host` distributes replicas across **hosts**.

**Questions**
- Q3.1 — With three monitors, how many must be reachable to form quorum, and why is an even number of monitors discouraged?
- Q3.2 — Which consensus/replication algorithm keeps the monitors' cluster map consistent?
- Q3.3 — In the default `replicated_rule`, what does `step chooseleaf firstn 0 type host` guarantee about where the replicas of an object land, and what would change if `type` were `osd`?
- Q3.4 — Why does Ceph document CRUSH as an algorithm rather than a lookup table — what does a client avoid contacting when locating an object?

## Exercise 4 — Pools and placement groups


## Exercise 6 — RADOS Block Device (RBD)

   ```bash
   rbd ls rbdpool
   ```

## Exercise 7 — CephFS, plus live diagnostics and recovery

1. Create a CephFS volume (this creates data + metadata pools and deploys an MDS), then mount it:
   ```bash
   ceph fs volume create shared
   ceph fs ls
   ceph fs status shared
   ceph orch ps --daemon-type mds

   # Kernel mount using the admin secret:
   mkdir -p /mnt/cephfs
   mount -t ceph :/ /mnt/cephfs -o name=admin,secret=$(ceph auth get-key client.admin)
   df -h /mnt/cephfs
   ```

2. Watch cluster events and per-OSD utilisation while the cluster works:
   ```bash
   ceph -w &          # streaming event log; Ctrl-C / kill when done
   ceph osd df
   ceph osd perf
   ```

3. Exercise object I/O directly against RADOS (bypassing RBD/CephFS) and read pool stats:
   ```bash
   rados -p appdata put greeting /etc/hostname
   rados -p appdata ls
   rados -p appdata stat greeting
   rados df
   ```

4. Change runtime configuration centrally and confirm it, then trigger integrity checks:
   ```bash
   ceph config set osd osd_max_backfills 4
   ceph config get osd osd_max_backfills
   ceph config dump | grep backfill

   ceph pg dump_stuck
   ceph pg deep-scrub 2.1a          # replace 2.1a with a real PG id from `ceph pg ls`
   ```

5. Simulate and recover from an OSD outage:
   ```bash
   ceph osd out osd.2
   ceph -s                          # watch remapped/backfilling PGs
   ceph osd in osd.2
   ceph osd unset noout             # (only if a maintenance flag was set)
   ```

**Questions**
- Q7.1 — Why does CephFS require an MDS while RBD does not, and what is stored in the CephFS *metadata* pool versus the *data* pool?
- Q7.2 — In an MDS cluster, what is the difference between an **active** and a **standby** (or standby-replay) MDS?
- Q7.3 — Where does `ceph config set osd osd_max_backfills 4` store the value, and how does that centralised config database differ from editing `/etc/ceph/ceph.conf`?
- Q7.4 — What is the difference between a regular *scrub* and a *deep-scrub* of a placement group?
- Q7.5 — What is the difference between marking an OSD `out` and marking it `down`, and which one triggers data rebalancing?

<summary><strong>Answer key</strong></summary>

### Exercise 1
- **A1.1** — After bootstrap you have exactly one **MON** (monitor) and one **MGR** (manager); cephadm also starts supporting containers (a `crash` agent, `node-exporter`, `prometheus`, `grafana`, `alertmanager`) and a bootstrapped `ceph.conf`. The essential missing type is the **OSD** (Object Storage Daemon) — with zero OSDs there is no place to store data.
- **A1.2** — `HEALTH_WARN` means a non-fatal condition that degrades resilience or capacity but does not (yet) risk data. Here `OSD count 0 < osd_pool_default_size 3` warns that no data-bearing daemons exist. `HEALTH_ERR` is reserved for conditions that block I/O or risk data loss (e.g. PGs `inactive`/`incomplete`, a full OSD).
- **A1.3** — `ceph orch ls` lists **services** (the declarative specs the orchestrator maintains, e.g. `mon`, `mgr`, `osd`, and how many are running vs desired). `ceph orch ps` lists the **individual daemon instances/processes** (one row per container) with their host, version and status.
- **A1.4** — cephadm writes `/etc/ceph/ceph.conf` and `/etc/ceph/ceph.client.admin.keyring` on the bootstrap host. The keyring holds the **`client.admin`** identity, the super-user cephx key with full `mon/osd/mgr/mds allow *` capabilities.

### Exercise 2
- **A2.1** — The disk must be (1) unpartitioned / have no partition table in use, (2) carry no existing filesystem or LVM/other signature, and (3) not already be claimed as an OSD. It also must be large enough (≥ a few GiB). Only then is `AVAILABLE = Yes`.
- **A2.2** — Modern OSDs use **BlueStore**, which writes directly to the raw block device (managing its own space and metadata in RocksDB), replacing the older FileStore-on-XFS. cephadm prepares the disk with **`ceph-volume`** (typically `ceph-volume lvm`), which creates the LVM layout, stores the OSD key and metadata, and registers the OSD.
- **A2.3** — `STATUS up/down` reflects whether the OSD daemon is currently **running and heartbeating** with peers. `in/out` (surfaced via `REWEIGHT`, where `0` ≈ out) reflects whether CRUSH should **place data** on it. `REWEIGHT` is a 0–1 override on how much data the OSD receives relative to its CRUSH weight. An OSD can be `up` but `out` (running, receiving no data) or `down` but still `in` (crashed, data still assigned to it, triggering recovery).
- **A2.4** — `daemon add osd` is a one-shot action on a specific device. `apply osd --all-available-devices` installs a **persistent OSD spec/service**: cephadm keeps it reconciled, so any *new* blank disk later inserted into a managed host is automatically turned into an OSD.

### Exercise 3
- **A3.1** — With 3 monitors you need a **majority = 2** reachable to keep quorum (tolerating 1 loss). Even numbers are discouraged because they raise the failure count needed to lose quorum by zero while adding a machine (4 mons still only tolerate 1 loss, same as 3) and increase the chance of split-brain-adjacent ties — odd counts give the best failure tolerance per node.
- **A3.2** — The monitors maintain the cluster maps using **Paxos** (a distributed consensus algorithm), which guarantees a single consistent, ordered history of map updates across the quorum.
- **A3.3** — `step chooseleaf firstn 0 type host` selects replica targets by descending to a **leaf OSD in a distinct `host` bucket** for each replica, so the copies of any object land on **different hosts** — one host can fail without losing all replicas. With `type osd`, replicas would only be guaranteed on different OSDs, possibly all on the same host, defeating host-level fault tolerance.
- **A3.4** — CRUSH lets any client **compute** the placement of an object deterministically from the object name, the pool, and the cluster map — so it never has to consult a central **metadata/lookup server** to find data. This removes a bottleneck and single point of failure and scales placement with the cluster.

### Exercise 4
- **A4.1** — A **Placement Group** is a logical shard of a pool: each object is hashed to a PG, and the PG (not the individual object) is mapped by CRUSH onto a set of OSDs. PGs collapse potentially billions of object→OSD mappings into a manageable number of PG→OSD mappings, which is what the cluster tracks, peers, replicates, scrubs and rebalances. Too few PGs → uneven data distribution; too many → excessive peering/memory overhead.
- **A4.2** — With `size 3` you have 3 replicas; `min_size 2` means writes are accepted as long as **at least 2** replicas are available, so you can lose **1** replica and keep serving I/O. If availability drops below `min_size` (only 1 copy left), the affected PGs go **inactive/read-restricted** to protect against acknowledging a write that exists on a single, possibly-failing OSD.
- **A4.3** — For `k=2, m=1`: usable/raw = k/(k+m) = **2/3 (~67% efficiency)**, versus 33% for 3× replication. It can survive **m = 1** OSD failure per PG. (Erasure coding trades CPU and higher `min_size`/recovery cost for much better space efficiency.)
- **A4.4** — The PG autoscaler adjusts **`pg_num`** (the number of placement groups per pool) based on actual and expected usage relative to cluster capacity. The **`target_size_ratio`** (or `target_size_bytes`) property tells it a pool is expected to hold a large share of the data so it can be pre-sized appropriately.

### Exercise 5
- **A5.1** — cephx authenticates the **identity** of clients and daemons using shared secret keys and session tickets (Kerberos-like), preventing unauthorised actors from talking to the cluster and letting the cluster mutually authenticate its own daemons. By itself it is **not** wire encryption of payload data — on-the-wire encryption is the separate `msgr2` secure mode (`ms_cluster_mode`/`ms_client_mode = secure`).
- **A5.2** — `osd 'allow rwx pool=appdata'` grants `client.app` **read, write and execute (class method) access to object data, but only in the `appdata` pool**. It cannot touch objects in any other pool. (`mon 'allow r'` lets it read the cluster map enough to locate that pool's OSDs.)
- **A5.3** — Because cephx is mandatory (auth enabled by default), **every** participant — each MON/OSD/MGR/MDS and every client — must present a valid key to join or use the cluster. `client.admin` is special because it holds `allow *` on all subsystems: it is the administrative super-user, so its keyring must be tightly protected and never shipped to application clients.
- **A5.4** — A raw `allow rwx pool=...` is a static, hand-written capability. A **`profile`** (e.g. `profile rbd`) is a named, maintained capability template that expands to exactly the permissions that use case needs (RBD image locking, the `rbd_directory`/`rbd_children` objects, class methods, etc.), so it is less error-prone and stays correct as Ceph evolves.

### Exercise 6
- **A6.1** — The image is stored as **many RADOS objects**, not one. `order 22` means each backing object is 2²² = **4 MiB**; a 1 GiB image is therefore ~**256 objects** (`rbd_data.<id>.*`), striped across the pool's PGs/OSDs for parallelism. Objects are only created when data is actually written.
- **A6.2** — Thin provisioning means the image advertises 1 GiB of logical capacity but consumes real space **only as blocks are written**. `rbd create --size 1024` allocates almost nothing up front; `rados df`/`ceph df` grow as you write into `/mnt/rbd`.
- **A6.3** — The kernel `rbd` driver exposes the image as a host block device (`/dev/rbd0`) using the in-kernel RBD client — good for mounting on the host. `librbd` is the userspace library that hypervisors like **QEMU/KVM** link directly, giving each VM the image without a host kernel mapping and enabling advanced features (client-side caching, live features) that may lag in the kernel client.
- **A6.4** — A snapshot must be **protected** so it cannot be deleted while clones depend on it (its blocks are the parent for copy-on-write). **Copy-on-write** means the clone initially stores **no data of its own** — it references the parent snapshot's objects and only allocates new objects for blocks it modifies, so a fresh clone is nearly free in space.

### Exercise 7
- **A7.1** — CephFS is a **POSIX filesystem**, so it needs directory trees, inodes, permissions, and file locking — the **MDS (Metadata Server)** manages that namespace. RBD is a flat block device with no filesystem semantics inside Ceph, so it needs no MDS. The **metadata pool** stores the filesystem's inode/dentry/journal data (small, latency-sensitive); the **data pool** stores the actual **file contents** as RADOS objects.
- **A7.2** — An **active** MDS is currently serving a portion of the filesystem namespace (handling client metadata ops). A **standby** MDS is idle, ready to take over if an active one fails; a **standby-replay** MDS additionally tails a specific active MDS's journal so it can fail over much faster with a warm cache.
- **A7.3** — `ceph config set osd osd_max_backfills 4` stores the value in the **centralised configuration database held by the monitors** (visible via `ceph config dump`), applied cluster-wide and at runtime without restarts. Editing `/etc/ceph/ceph.conf` only affects the **local host's** daemons/clients, is read mainly at start-up, and is not distributed by the cluster — the mon config DB is the preferred, authoritative source.
- **A7.4** — A regular **scrub** compares object **metadata** (existence, size, attributes) across replicas to catch inconsistencies cheaply and frequently. A **deep-scrub** additionally reads the **full object data and compares checksums** across replicas, detecting silent bit-rot — it is far more I/O-intensive and runs less often.
- **A7.5** — Marking an OSD **`out`** tells CRUSH to stop placing data on it, which **triggers rebalancing/backfill** of its PGs onto other OSDs (the daemon may still be running). Marking it **`down`** just means the daemon is not heartbeating; if it stays `down` past `mon_osd_down_out_interval` the cluster automatically marks it `out` (unless `noout` is set), and *that* out transition is what starts the data migration.
